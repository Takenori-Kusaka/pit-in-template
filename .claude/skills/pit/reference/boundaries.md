# 役割境界と委譲の制限

`CLAUDE.md`「行ってはならない作業」「一律で AI に委譲できない領域」「判断の確定と委任」の詳細です。規則の索引は `CLAUDE.md` にあります。

ピットイン方式（標準）では、人間と AI の役割分担および委譲してはならない領域を厳格に定義しています。**AIの自律レベルにかかわらず変わりません**（第5章 5.5 / 5.8.3）。

## 1. 一律で AI に委譲できない領域（第5章 5.8.3）
- **安全に関する最終的な判断**
- **人間のレビューを経ない安全関連コードの変更**
- **形式的な検証活動そのものの代替**
- **挙動の非決定性を隠す目的の実装**

## 2. 判断の確定は席の責任者が行う（第5章 5.5）
席（ロール）には、結果責任を負う**責任者**（記名の自然人）と、作業を行う**担い手**（人または AI）がいます。**人に固定するのは判断の確定であり、席の作業ではありません**。

次の4種類の判断の確定（ゲートの判定と、R1・R2 の決定）は、席の責任者（人）が記名で行います。AI の担い手へ移しません。
- **何を作るか、どの順序で作るか（価値判断 / 席：価値責任者）**
- **どの設計を採るか、何を捨てるか（技術判断 / 席：技術判断者）**
- **成果物が仕様どおりに動くかの確認（理解の確認 / 席：独立レビュア）**
- **判断と検証の記録が完備しているかの確認（記録の確認 / 席：出荷判定者）**

席の作業は担い手が行います。自席の運用形態と委任の範囲は「このプロジェクトの構成」にあります。
- **承認済みの受入基準とスコープの内側にある作業上の選択は、協働の席でも、自分で決めて記録します。選択のたびに人へ戻しません**。記録先はコミットのメッセージ、または PR の「変更の概要」です。人は、変更ごとの確定の場で、記録された選択をまとめて確認します。
- **人へ戻すのは次の3つです**。(a) 人が確定する判断（標準 第5章 5.5.5 の6項目。R1 の決定と例外承認、委任の範囲と条件の決定と拡大、機械の規則で判定できないリスク区分の確定、G-7 の記名・G-8・本番環境への反映の承認、適合性確認の承認、コア機能の理解の確認と安全に関する最終的な判断。ゲートの判定と R2 の決定も人が確定する） (b) 受入基準・スコープ・公開インタフェース・データ形式を変える選択 (c) 取り消せない操作。戻す先は受信箱のラベルです（価値判断 `state:needs-po` / 技術判断 `state:needs-tech` / 事業決裁 `state:needs-owner` / 強制層 `state:needs-platform`）。
- **委任の範囲に当たるかどうかを、自分で判定しません**。機械の規則によります（`node scripts/gate/verify-gate-contract.mjs --delegation`）。規則で分類できない変更は協働として扱い、人の確定を受けます。
- **委任の範囲の変更を、自分でマージしません**。PR を出した後の該当は、ワークフロー（`.github/workflows/delegation.yml`）が、既定ブランチの構成と規則で判定します（`scripts/gate/check-delegation.mjs`）。結果は必須でないステータス `delegation-eligibility` に出ます。判定の結果は3つです。
  - **開発者の席の規則にだけ該当する変更**: 変更ごとの検証は担い手が行います。独立レビュー（G-6）は、独立レビュアが人として事前に承認します。現在のブランチ保護のままマージされます。人の事前確認を経ていない変更ではありません。
  - **独立レビュアの席の規則にも該当する変更**（G-6 の判定の時点を事後へ移す委任）: **マージの実行は既定で無効です**。組織が有効化するまで、協働として扱い、人の承認を待ちます。有効な場合も、マージするのはワークフローだけで、機械は承認を付けません。この変更だけが「人の事前確認を経ていない変更」です。開発者の席の規則に当たらない変更（開発者の席はこの変更について協働）は、開発者の席の責任者（人）が検証して承認するまでマージされません。
  - **該当しない変更**: 協働として扱い、人の確定を受けます。
- 委任の範囲の変更では、経路が有効かどうかにかかわらず、すべてのコミットへトレーラ `Delegated: <規則ID>` を書きます。トレーラは、変更ごとの検証を担い手へ委ねたことの識別です。開発者の席の規則に当たる変更では、担い手が PR の「検証方法と結果」へ実行結果の証拠を書きます。テンプレートの既定の権限設定（`.claude/settings.json` の許可リスト）に `gh pr ready` は無いため、組織が許可を足すまでは、Draft から Ready にするのは人です（担い手は設定を変えずに、Ready にしてよい状態であることを報告します）。人確定・協働の変更では、この欄を書くのも Ready にするのも人です。判定を通すために、変更を分割したり、リスク区分を低く書いたりしません。トレーラ `Delegated` を持つ変更を R1・R2 と記録すると、出荷判定の証跡で委任の条件に反する変更になります。
- 運用形態は上限の宣言です。R1 の決定と例外承認は人確定で、AI は結論を起案しません。上限を案件の判断で引き上げません。緩める向きの変更を AI が決めません（`/process-change`）。責任者・決定者・承認者の欄へ、AI の名義を書きません。
- **AI の確認は検出の層です。承認・通過・独立レビュー済みと記録しません**。適合性確認が失効した担い手（モデルの版・指示資産の版・権限のいずれかが変わった担い手）の確認は、検出の層に数えません。
- **確認する側では、作成側の説明文・主張・推論の過程を、判断の前に読みません**（入力の分離）。読むのは仕様・受入基準・差分です。文脈を分けただけの AI の確認を「独立レビュー」と呼びません。独立は、席の責任者が作成を指示した者と別の人である場合にだけ成立します。

## 3. その他の委譲制限（第5章 5.4.3 の不変条件3・4）
- **認証・認可・個人データ・外部との契約に関わる決定**
- **適用範囲（標準の適用境界）そのものの拡大**

結果責任（A）は常に席の責任者（人）に紐づきます。AI は担い手として実行（R）だけを担います。

## 行ってはならない作業の理由

| 禁止事項 | 標準の所在 | 理由 |
| --- | --- | --- |
| 受入基準を確定せずに実装を始める | 第5章 5.8.5 の禁止事項1 | 何をもって完了とするかが不定になる |
| AI が生成した受入基準を、人の G-2・G-4 の判定を経ずに確定とする | 第5章 5.8.5 の禁止事項2、第4章 G-2 | 受入基準の確定は、人が版を特定して記名する行為である。読まずに承認しないことは、禁止ではなく推奨である |
| **テストの失敗を、テスト側の変更で解消する** | 第5章 5.8.5 の禁止事項3 | 検証の放棄であり、実装の完了ではない |
| 差分を確認せずに承認する | 第5章 5.8.5 の禁止事項4 | 独立レビューの前提が崩れる |
| **独立レビューの挙動要約を AI に生成させる** | 第5章 5.8.5 の禁止事項5 | 要約は理解の証拠であり、生成物は証拠にならない |
| カバレッジ閾値・静的解析の重大度・除外設定を機能変更と同じ PR で変える | 第4章 G-5「基準値と除外設定の変更」 | 以後のすべての通過を無効化する |
| **事前承認のない外部パブリックホスト（個人用 Claude Artifacts や公開 Pastebin 等）へ決裁資料やログを配置（発行）する** | 第5章 5.5.1 (c) | 組織の管理外への発行は取り消せない操作である。機密情報や意思決定の証跡が流出する |

標準の禁止事項の番号は、標準の一覧(第5章 5.8.5、第8章「テーラリングの禁止事項」)だけが持ちます。このテンプレートは独自の通し番号を持ちません。

## ラベルによる引き渡しの理由

次の2行は、標準 第3章 3.5.5 の要求事項です(`CLAUDE.md`「ラベルによる引き渡し」)。

| 規則 | 標準の所在 | 理由 |
| --- | --- | --- |
| **判断依頼と引き渡しは `state:*` ラベルを貼って行う。コメントや `@mention` だけで済ませない** | 第3章 3.5.5 要求事項3 | 相手のポーリングのクエリに現れず、すべての受信箱から消えて作業が滞留する |
| **差し戻し(`qm-blocked`)に対応したら、そのラベルを剥がし、`dev-done` を貼る** | 第3章 3.5.5 要求事項2 | 復路の引き渡しが欠け、独立レビュアの受信箱に現れず、作業が止まる |

## テンプレートの運用の規則の理由

次の規則は標準の要求事項ではなく、このテンプレートの運用の規則です(`CLAUDE.md`「テンプレートの運用の規則」)。

| 規則 | 関係する標準の所在 | 理由 |
| --- | --- | --- |
| 完了の条件を曖昧さなく書けない機能は、書けるところまで分解してから実装へ渡す | なし | 完了の条件の無い実装は、5.8.5 の禁止事項1 に近づく |

5.8.5 の禁止事項3 は、自己修正のロック中にフック(`.claude/hooks/guard-write.mjs`)がテストへの書き込みを遮断します。ロックは `scripts/gate/self-heal.mjs` が始めて終えます。遮断は段階に依らず有効です(構成の guard の上書きで強制層を一時緩和しても外れません)。強制層そのものの遮断も、事業ステージ(PoC を含む)に依らず有効です(標準 第8章 軸B)。

## AI レビューの扱い

AI によるレビューは**検出の層**であり、監査の入力です。判定には数えません。承認(approve)もしません。独立レビュー(G-6)の代替にも、未達の解消にもなりません。記録には「AI レビュー通過」ではなく、**指摘の内容と採否**を残します。
