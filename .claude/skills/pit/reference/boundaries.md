# 役割境界と委譲の制限

`CLAUDE.md`「行ってはならない作業」「一律で AI に委譲できない領域」「判断の確定と委任」の詳細です。規則の索引は `CLAUDE.md` にあります。

ピットイン方式（標準）では、人間と AI の役割分担および委譲してはならない領域を厳格に定義しています。**AIの自律レベルにかかわらず変わりません**（第5章 5.5 / 5.8.3）。

## 1. 一律で AI に委譲できない領域（第5章 5.8.3）
- **安全に関する最終的な判断**
- **人間のレビューを経ない安全関連コードの変更**
- **形式的な検証活動（テストや静的解析など）そのものの代替**（例：テストを動かさないまま通過とする等）
- **挙動の非決定性（AIの気まぐれやエラーなど）を隠す目的の実装**

## 2. 判断の確定は席の責任者が行う（第5章 5.5）
席（ロール）には、結果責任を負う**責任者**（記名の自然人）と、作業を行う**担い手**（人または AI）がいます。**人に固定するのは判断の確定であり、席の作業ではありません**。

次の4種類の判断の確定（ゲートの判定と、R1・R2 の決定）は、席の責任者（人）が記名で行います。AI の担い手へ移しません。
- **何を作るか、どの順序で作るか（価値判断 / 席：価値責任者）**
- **どの設計を採るか、何を捨てるか（技術判断 / 席：技術判断者）**
- **成果物が仕様どおりに動くかの確認（理解の確認 / 席：独立レビュア）**
- **判断と検証の記録が完備しているかの確認（記録の確認 / 席：出荷判定者）**

席の作業は担い手が行います。自席の運用形態と委任の範囲は「このプロジェクトの構成」にあります。
- **承認済みの受入基準とスコープの内側にある作業上の選択は、協働の席でも、自分で決めて記録します。選択のたびに人へ戻しません**。記録先はコミットのメッセージ、または PR の「変更の概要」です。人は、変更ごとの確定の場で、記録された選択をまとめて確認します。
- **人へ戻すのは次の3つです**。(a) 人が確定する判断（上の4種類の確定、R1 の決定、例外承認） (b) 受入基準・スコープ・公開インタフェース・データ形式を変える選択 (c) 取り消せない操作。戻す先は受信箱のラベルです（価値判断 `state:needs-po` / 技術判断 `state:needs-tech` / 事業決裁 `state:needs-owner` / 強制層 `state:needs-platform`）。
- **委任の範囲に当たるかどうかを、自分で判定しません**。機械の規則によります（`node scripts/gate/verify-gate-contract.mjs --delegation`）。規則で分類できない変更は協働として扱い、人の確定を受けます。
- **委任の範囲の変更を、自分でマージしません**。PR を出した後の該当は、ワークフロー（`.github/workflows/delegation.yml`）が、既定ブランチの構成と規則で判定します（`scripts/gate/check-delegation.mjs`）。結果は必須でないステータス `delegation-eligibility` に出ます。判定の結果は3つです。
  - **開発者の席の規則にだけ該当する変更**: 変更ごとの検証は担い手が行います。独立レビュー（G-6）は、独立レビュアが人として事前に承認します。現在のブランチ保護のままマージされます。人の事前確認を経ていない変更ではありません。
  - **独立レビュアの席の規則にも該当する変更**（G-6 の判定の時点を事後へ移す委任）: **マージの実行は既定で無効です**。組織が有効化するまで、協働として扱い、人の承認を待ちます。有効な場合も、マージするのはワークフローだけで、機械は承認を付けません。この変更だけが「人の事前確認を経ていない変更」です。開発者の席の規則に当たらない変更（開発者の席はこの変更について協働）は、開発者の席の責任者（人）が検証して承認するまでマージされません。
  - **該当しない変更**: 協働として扱い、人の確定を受けます。
- 委任の範囲の変更では、経路が有効かどうかにかかわらず、すべてのコミットへトレーラ `Delegated: <規則ID>` を書きます。トレーラは、変更ごとの検証を担い手へ委ねたことの識別です。開発者の席の規則に当たる変更では、担い手が PR の「検証方法と結果」へ実行結果の証拠を書きます。テンプレートの既定の権限設定（`.claude/settings.json` の許可リスト）に `gh pr ready` は無いため、組織が許可を足すまでは、Draft から Ready にするのは人です（担い手は設定を変えずに、Ready にしてよい状態であることを報告します）。人確定・協働の変更では、この欄を書くのも Ready にするのも人です。判定を通すために、変更を分割したり、リスク区分を低く書いたりしません。トレーラ `Delegated` を持つ変更を R1・R2 と記録すると、出荷判定の証跡で委任の範囲の逸脱になります。
- 運用形態は上限の宣言です。R1 の決定と例外承認は人確定で、AI は結論を起案しません。上限を案件の判断で引き上げません。緩める向きの変更を AI が決めません（`/process-change`）。責任者・決定者・承認者の欄へ、AI の名義を書きません。
- **AI の確認は検出の層です。承認・通過・独立レビュー済みと記録しません**。適合性確認が失効した担い手（モデルの版・指示資産の版・権限のいずれかが変わった担い手）の確認は、検出の層に数えません。
- **確認する側では、作成側の説明文・主張・推論の過程を、判断の前に読みません**（入力の分離）。読むのは仕様・受入基準・差分です。文脈を分けただけの AI の確認を「独立レビュー」と呼びません。独立は、席の責任者が作成を指示した者と別の人である場合にだけ成立します。

## 3. その他の委譲制限（第3章 3.4.1）
- **認証・認可・個人データ・外部との契約に関わる決定**
- **適用範囲（標準の適用境界）そのものの拡大**

結果責任（A）は常に席の責任者（人）に紐づきます。AI は担い手として実行（R）だけを担います。

## 行ってはならない作業の理由

| # | 禁止事項 | 理由 |
| --- | --- | --- |
| 1 | 受入基準を確定せずに実装を始める | 何をもって完了とするかが不定になる |
| 2 | AI が生成した受入基準をそのまま承認する | 価値判断を委譲したことになる |
| 3 | **テストの失敗を、テスト側の変更で解消する** | 検証の放棄であり、実装の完了ではない |
| 4 | 差分を確認せずに承認する | 独立レビューの前提が崩れる |
| 5 | **独立レビューの挙動要約を AI に生成させる** | 要約は理解の証拠であり、生成物は証拠にならない |
| 6 | カバレッジ閾値・静的解析の重大度・除外設定を機能変更と同じ PR で変える | 以後のすべての通過を無効化する |
| 7 | **`state:*` ラベルを貼らず、コメントや `@mention` だけで判断依頼や引き渡しを済ませる** | 相手の polling クエリに現れず、すべての受信箱から消えてタスクが滞留（orphan化）するため |
| 8 | **差し戻し（`qm-blocked`）対応後に、そのラベルを剥がし忘れる、または `dev-done` を貼り忘れる** | 復路の伝達が不完全となり、QMの受信箱に現れずプロセスが完全停止するため |
| 9 | **事前承認のない外部パブリックホスト（個人用 Claude Artifacts や公開 Pastebin 等）へ決裁資料やログを配置（発行）する** | 組織の管理外に機密情報や意思決定証跡が流出し、ガバナンスとセキュリティが破綻（インシデント化）するため |

禁止事項3は、自己修正のロック中にフック(`.claude/hooks/guard-write.mjs`)がテストへの書き込みを遮断します。ロックは `scripts/gate/self-heal.mjs` が始めて終えます。遮断は段階に依らず有効です(探索ステージで強制層を無効にしても外れません)。

## AI レビューの扱い

AI によるレビューは**検出の層**であり、監査の入力です。判定には数えません。承認(approve)もしません。独立レビュー(G-6)の代替にも、未達の解消にもなりません。記録には「AI レビュー通過」ではなく、**指摘の内容と採否**を残します。
