# 人へ戻す場合と受信箱の運用

`CLAUDE.md`「人へ戻す3つの場合」「受信箱とラベル」の詳細です。規則の索引は `CLAUDE.md` にあります。ロールごとの受信箱のコマンド、引き渡しのラベル、エスカレーションの段階とラベルは、構成から導出する `node scripts/gate/next.mjs --role <ロール>` が出します。

## ロール間非同期メッセージング(Label Mailbox 連携)

物理隔離された各ロール（PO, Dev, Review, Ship, Owner, Audit, Platform。技術判断者はレーンの写像による）は、直接の同期通信や割り込み（指示を直接仰ぐ行為）を行わず、GitHubラベルをメッセージバスとした非同期・ポーリングベースの連携（[Label Mailbox仕様](https://takenori-kusaka.github.io/process-compass/phase5-implementation/label-mailbox/)）を使用する。

- 開発に着手した際、Draft PR の状態では **`state:needs-dev`** ラベルを維持すること。
- 実装・単体テスト（CI緑）が完了し、`human-verify` 用手順を提示する際（標準の PR 運用は「human-verify を記録して Ready にする際」と定める。このテンプレートは Ready 化を人に残すため、提示の時点へ移している。テンプレート独自）、開発者（Dev）は `state:needs-dev` を剥がし、**`state:dev-done`** ラベルを付与して独立レビュア（Review）へ引き渡すこと。`state:dev-done` の受け手は独立レビュアだけであり、出荷判定者には渡さない（標準 第3章 3.5.5）。ただし G-6 が省略・未達の構成では独立レビュアの受信箱が無く、`state:dev-done` は出荷判定者が受ける。出荷判定者は PR に G-6 の省略・未達を開示したうえで扱い、`state:ready-to-merge` は使わない。開発者が自ら `state:ready-to-merge` を付けて確認の段を飛ばさないこと（同 3.5.5 のラベルの語彙）。受け手は `node scripts/gate/next.mjs --role <ロール>` の受信箱が構成から出す。
- 独立レビュアは、G-6 の判定記録を作成した後に限り **`state:ready-to-merge`** を付与して出荷判定者（Ship）へ渡す。出荷判定者はこのラベルを付けない。出荷判定者が記録の突合で BLOCK 3類型を検出したら `state:qm-blocked` を付けて開発者へ差し戻す。出荷判定（G-7）は出荷の範囲ごとに行い、このラベルでは起動しない（`/pit` の出荷の段が出す）。既定ブランチへの取り込みが出荷を起動する構成では、G-7 の判定記録の後にマージする。
- 独立レビューにおいて差し戻し（`state:qm-blocked`）が発生した場合、Devは対応を最優先する。ただし着手の前に、下の「拾った作業単位に着手する前に」の確認(`--pickup state:qm-blocked`)を行う。対応が完了しCIが全緑になったら、必ず `state:qm-blocked` を剥がして再度 **`state:dev-done`** に戻すこと（復路の徹底）。
- 次の3つの場合に限り、自走を停止し、受信箱のラベルを付与して人の判断を待つこと（標準 第5章 5.5.1）。(a) 人が確定する判断（ゲートの判定、R1・R2 の決定、例外承認。標準 第5章 5.5.5 の6項目の全体は `boundaries.md`）に当たる場合 (b) 受入基準・スコープ・公開インタフェース・データ形式を変える選択が必要になった場合 (c) 取り消せない操作（取り消せない効果を、他の者の操作を介さずに生じさせる操作。効果の判定の基準は、取り消せない時間帯が存在すること。取り消し操作を用意したことを理由に外さない。データの削除・本番デプロイ・課金の書き込み・スキーマ変更・外部への発行は例であり、これに限らない。反映・発行・マージ・配備の起動そのものを後段で人が自ら行う上流の編集は当たらない。承認・レビュー・環境の承認のような門は、人が自ら行うことに当たらない。既定ブランチへの取り込みや push が配備・公開を直接起動する構成では、その取り込み・push が当たり、自分でマージしない。後段に人だけが通せる門が残ることを理由に、止めずに行わない）が必要になった場合。付与するラベルは、価値判断が **`state:needs-po`**、取り消せない操作と事業決裁が **`state:needs-owner`**。**承認済みの受入基準とスコープの内側にある作業上の選択は、これに当たらない**。自分で決めて記録し、選択のたびに人へ戻さないこと。
- 技術設計の判断（G-3。アーキテクチャ・技術選定・ADRの採否）が必要になった場合は、**`state:needs-tech`** を付与して技術判断者へ引き渡すこと。技術判断者が開発者とレーンを共有する体制でも、**セッションを分けて**受け取ること。
- **遮断の解除・閾値の緩和・強制層の縮小**を見つけた場合は、差分が主張と一致するかまでを確認し、許容してよいかは判断しないこと。引き渡し先は `state:needs-platform`（取り消せない操作に当たる場合と、ガード・検証ゲート・重要テストの削除（統制の弱化）の場合は `state:needs-owner` も併記。取り消せない操作は、取り消せない効果を、他の者の操作を介さずに生じさせる操作であり、列挙は例示である。効果の判定の基準は、取り消せない時間帯が存在すること。取り消し操作を用意したことを理由に外さない。一覧に無いことを理由に外さない。統制の弱化の併記は、取り消せない操作の定義によらない）。**引き渡し先が分からないことを、自分で決める理由にしないこと**（特定できない場合は `state:needs-po`）。

直接の指示やメッセージを待つのではなく、定期的に自分のメールボックス（`gh` polling コマンド）を自律的に監視し、仕事を拾って処理すること。

## 拾った作業単位に着手する前に

受信箱から作業単位を拾ったら、着手の前に、そのラベルへの遷移の前提の判定記録があるかを確かめます。**ラベルが遷移していて判定記録が無い作業単位は、未判定のまま渡ったものとして扱い、着手せず、判定者へ差し戻します**。 <!-- 根拠: 標準 第3章 3.5.5 要求事項5 -->

```bash
node scripts/gate/next.mjs --pickup <ラベル> <対象> [--from <前のラベル>]
# 例: --pickup state:needs-dev F-012 --from state:needs-tech / --pickup state:ready-to-merge "PR #34"
```

| ラベル | 対象 | 前提の判定記録 |
| --- | --- | --- |
| `state:needs-dev` | 機能 `F-NNN`。`--from` に `state:needs-dev` へ替える前のラベル(作業単位のラベルの履歴で確かめる) | `--from state:needs-tech` なら G-3 の通過(標準 第3章 3.5.5 の状態の遷移)。どの経路でも G-2・G-4 の通過(構成で有効なもの。標準 第5章 5.8.5 の禁止事項1)。`--from state:needs-po`・`state:needs-owner` の判断・決裁の記録は様式が無く、機械では読まない。`--from` が無い・機能へ対応づけない作業単位は `[判定できない]` |
| `state:ready-to-merge` | PR | G-6 の通過(承認者本人の挙動要約つきの承認) |
| `state:qm-blocked` | PR | G-6 の差し戻し。無ければ `[判定できない]`(出荷判定者の記録の突合による差し戻しは機械で確かめない) |
| 上記以外の引き渡しのラベル | — | 求めない。開発者・AI維持管理者・誰でも付けられ、付ける契機を判定に限らないため |

前提の判定記録は、最新の判定で読みます。通過の後に差し戻しの記録があれば、その通過は効いていません。構成にゲートのキーが無いときは `[判定できない]` です。

| 出力 | 終了コード | すること |
| --- | --- | --- |
| `[着手してよい]` | 0 | 着手する |
| `[着手しない]` | 3 | 着手しない。作業単位に「判定記録が無いため着手しない」と書き、出力の差し戻す先の受信箱のラベルへ替える。判定記録は判定者本人が書く。AI の担い手は記録を作らない |
| `[判定できない]` | 4 | 着手しない。推測で進めず、理由を利用者へ伝える |

**終了コードが 0 でなければ、出力の形によらず着手しません**。開いている PR の判定はマージの前で写しが無いため、`--pickup` は PR のレビューを `gh api` で読みます(`--offline` では読みません)。判定者の本人性と承認者の人数は確かめません(G-5 と出荷の証跡の集約が見ます)。`--pickup` は、`/process-change` の種別 `intake`(準拠テンプレートの更新の取り込み)とは別物です。

## 統制の弱化を見つけたら

**遮断の解除・閾値の緩和・強制層の縮小**を見つけた場合は、差分が変更の主張と一致するかまでを確認し、**許容してよいかを判断してはなりません**。 <!-- 根拠: IMPL-0015 -->

| 対象 | 付与するラベル |
| --- | --- |
| 強制層(`.claude/**` 等)の縮小 | `state:needs-platform` |
| 配備の環境の保護規則の削除・ルールセットへの迂回の主体の追加(遮断の解除の例。統制の弱化。配備の起動が取り消せない操作に当たるかは、上の (c) の定義（標準 第5章 5.5.1）により、この行は配備の起動を対象としない) | `state:needs-platform` |
| 取り消せない操作に当たる(取り消せない効果を、他の者の操作を介さずに生じさせる操作。効果の判定の基準は、取り消せない時間帯が存在すること。取り消し操作を用意したことを理由に外さない。例示の一覧に無いことを理由に外さない) | 上に加えて `state:needs-owner` |
| ガード・検証ゲート・重要テストの削除(統制の弱化。取り消せない操作の定義によらず併記する。当たるかは列挙で決めず、削除によって止めていたものを止めなくなるかで判断する) | 上に加えて `state:needs-owner` |
| 弱化の範囲そのものの適否 | `state:needs-po` |

**引き渡し先が分からないことを、自分で決める理由にしてはなりません**。特定できない場合は `state:needs-po` を付与します。兼務していても、ラベルを経由させて引き渡しを記録します([第3章 3.5.5](https://takenori-kusaka.github.io/process-compass/phase4-process-design/roles-responsibilities/))。 <!-- 根拠: IMPL-0015 -->

## 停止の申し立て(`state:stop-requested`)

品質・安全・法令上の異常を認めたら、**誰でも**対象の PR へ `state:stop-requested` を付けて止められます(標準 第7章 7.11)。付けた時点で G-5(`pr-rules`)が失敗し、マージが保留されます。

- 付けるときは、PR のコメントへ申し立てた者(記名)と、認めた異常を書く。匿名で付けない(退けた解除の上申で、誰の見解を退けたかを追うため)
- 受信箱は事業決裁者(層1 の項目4「停止の申し立ての解除」の権限者が別にいれば、その席)。**AI の担い手はラベルを外さず、解除の記録も書かない**
- 解除は、権限者が解除の記録(テンプレ4 の節「停止の申し立ての解除」)を既定ブランチへ入れて行う。ラベルを外しただけでは解けない
- 申し立ては拒否権ではない。申し立ての件数を、申し立てた者・受けた者・チームの評価の減点に使わない
- 保証の開示に載った未達・未測定についての出荷判定者の見解は、申し立てでなく G-8 の異議で扱う

## 受信箱を見る範囲

**自分のロールのブロックだけを実行してください**。他のロールの受信箱を見た時点で文脈は合流し、分離は成立しなくなります([第3章 3.5.3](https://takenori-kusaka.github.io/process-compass/phase4-process-design/roles-responsibilities/))。ディレクトリが分かれていても、複数のレーンの受信箱を見た時点で文脈は合流します。

状態ラベルの付いていない Issues/PRs(孤児)の再配分は価値責任者の義務です。**再配分した仕事を自ら拾ってはなりません**。再配分の権限と、仕事を拾う権限は別です。 <!-- 根拠: 標準 第3章 3.5.5 要求事項7 -->

## エスカレーション

段階と判定する者、付与するラベルの表は `node scripts/gate/next.mjs --role <ロール>` が出します。発火条件と閾値は[第7章 7.6](https://takenori-kusaka.github.io/process-compass/phase4-process-design/exception-escalation/)、実際の宛先は D-0 体制図の節6「平常時のエスカレーション」(標準の表3)によります。**ラベルの付与だけで報告を済ませてはなりません**。エスカレーションレポートの5項目(状態・原因・事業影響・リカバリ選択肢3案・推奨と決裁事項)を書きます。**推奨と決裁事項は人が記入します**。 <!-- 根拠: 標準 第7章 7.6 -->

出荷判定(G-7)では、範囲のエスカレーションの記録(起票と判定)を判定記録と突き合わせて全件確かめる(出荷判定者。標準 第7章 7.8)。専用のラベルは足さない(7.6)。

レポートの書き方は次のとおりです。分量は上限です(標準 第7章 7.6)。

| 項目 | 書き方 |
| --- | --- |
| 1. 状態 | 3行以内。基準を満たさない点を数値で示す |
| 2. 原因 | 5行以内。直接原因と、判明していれば背景要因 |
| 3. 事業影響 | 表で書く。期日・費用・利用者・契約への換算 |
| 4. リカバリ選択肢 | 表で書く。3案の各案について、到達点・費用・期日・残るリスク |
| 5. 推奨と決裁事項 | 3行以内。**人が記入する** |

項目1〜4の草案は、AI の担い手に生成させてよいです。項目5は、推奨の提示が結果責任を負う者の行為であるため、人が記入します。

エスカレーションの運用で守る規則は次の3つです(標準 第7章 7.6)。判定する者と応答期限の実際の宛先は、D-0 体制図の記名によります。

- **起票した者は、自分の起票を判定しません**。兼務で同じ人が起票と判定を担う体制では、自己の判定であることを D-0 の記載のとおり開示します
- 応答期限を過ぎても、承認とみなしません。代理の判定者の指名を求めます(標準 第3章 3.9.3)
- 段階2 の事業決裁者の決定は、非同期の持ち回りでよいです。ただし、リスク区分 R1 の変更に係る決定には使いません

### 期日に間に合わない見込みのとき(標準 第2章 2.10.6)

価値責任者が、2.10.4 の2指標(残る作業単位の個数と実測スループットから見た残る期間)で見込みを評価します。**間に合わない見込みが立った時点で手続を始め、期日の到来を待ちません**。選ぶ順序は、範囲を削る、期日を動かす、基準を下げる、の順です。**順序を入れ替えません**。範囲は調整枠(SC-B)から先に削り、SC-M へ手を付けません。手順2(期日)と SC-M の変更は、価値責任者が決めません。事業決裁者の判断に回します。

新しい記録は作りません。次の既存の記録に残します。

- 手順1 で削った SC-B・SC-P と残りは、上のレポートの項目1(状態)・項目2(原因)に書きます
- 手順1 の調整は、様式 04 の「価値責任者の調整」の理由に「2.10.6 手順1」と書きます
- 調整の途中で SC-M に触れる疑いが出たら、手順1 で進めず、2.10.5 の表の行4 へ回します

見込みの評価そのものと、手順を選んだ順序を記録する義務は課されていません(ADR-0178)。機械は、見込みの評価も順序の遵守も確かめません(層の帰属を機械が読めないため)。確かめる者: 価値責任者(手続を開始し、手順を選ぶとき)。 <!-- 根拠: 標準 第2章 2.10.6 -->

### 判定・決定の期限を過ぎたとき(PR を持たないゲートと会議体。標準 第3章 3.9.3)

PR のゲート(G-6・G-3・G-2/G-4)の期限の超過は、機械が検出して D-0 節6 の宛先へ通知します。**PR を持たないゲート(G-1・G-5・G-7・G-8・SG)と会議体の決定の期限は、機械が数えません**。人が次のとおり運用します。

- 上程した者が、上程の Issue のコメントに、上程の日と D-0 節5 の期限を書きます
- 期限を過ぎたら、上程した者が D-0 節6 の「ゲート判定・会議体の決定が期限を超過」の宛先へ、記名で知らせます
- 宛先の者の務めは、代理の判定者・決定者の指名です。通知を受けて終わりにしません
- 期限を過ぎても、承認とみなしません(上の規則2点目)

確かめる者: 上程した者と D-0 節6 の宛先。機械は確かめません。 <!-- 根拠: 標準 第3章 3.9.3 -->

## 人の判断待ちを出したあと

`node scripts/gate/next.mjs` が「人の判断待ち」を出した状態は終端です。AI の担い手はコマンドを実行せず、待つ席の受信箱のラベルを付けて渡します。人が判断して記録した後に、もう一度 `node scripts/gate/next.mjs` を実行します。

## 指示資産の提供者依存の棚卸し

指示資産(`CLAUDE.md`・`AGENTS.md`・`.claude/skills/` ほか)のうち、特定の提供者の書式・機能に依存する記述を識別し、印を付けます。四半期の棚卸し(標準 第3章 3.11.4)のときに行います(標準 第3章 3.12.3 要求事項6)。機械の検査は無く、棚卸しを行う者が目で確かめます。

依存先の一覧(単一障害点の一覧を含む)は、四半期の棚卸し・ステージ移行ゲートの判定時・体制の変化点の時に、`node scripts/gate/aggregate-evidence.mjs` を実行して再生成する(第3章 3.12.11 要求事項5)。

- 観点の例: 提供者固有のファイル名・設定のキー・フック・ツールの名前、特定のモデルの名前や版の指定、提供者だけが解釈する記法
- 印の付け方の例: 該当の記述の直後へ、`<!-- 提供者依存: <提供者名> -->` のような注記を置く。注記の書式は組織で決めてよい
- 印を付けた記述は、別の提供者へ切り替えるときに書き換える対象の一覧になる。退出の予行(標準 第3章 3.12.3 要求事項7)で、切り替えた場合に何が変わるかを試した記録と合わせて読む

## 全社の統制の更新を受けるとき(標準 第3章 3.12.9)

全社の側が新しい検査ルールを配るとき、開発組織の側は猶予を置いて必須へ上げる。猶予なしの昇格で、案件が一斉に止まることを避けるためである。

- 新しい検査は、**まず警告として入れる**(合否に使わないジョブ、または結果を記録だけするステップ)。警告の間も結果は見える状態に保つ
- 昇格の予定日は、全社の側の通知(Issue)で受け取り、その Issue に残す。**構成には持たせない**(ADR-0184。予定日で阻止を切り替える仕組みは持たない)
- 予定日に必須へ上げる変更は、通常の変更として PR で行う。昇格の変更の承認の経路は、採用者の定めによる。猶予の長さと予定日をエージェントが決めない(統制の緊急度は全社の側が決める)
- セキュリティ上の重大な事象に対応する統制は、猶予を置かずに入れてよい(標準 第3章 3.12.9)
- 確かめる者: AI運用担当者(全社の統制の更新を受けるとき)。機械は確かめない
