# 人へ戻す場合と受信箱の運用

`CLAUDE.md`「人へ戻す3つの場合」「受信箱とラベル」の詳細です。規則の索引は `CLAUDE.md` にあります。ロールごとの受信箱のコマンド、引き渡しのラベル、エスカレーションの段階とラベルは、構成から導出する `node scripts/gate/next.mjs --role <ロール>` が出します。

## ロール間非同期メッセージング(Label Mailbox 連携)

物理隔離された各ロール（PO, Dev, Review, Ship, Owner, Audit, Platform。技術判断者はレーンの写像による）は、直接の同期通信や割り込み（指示を直接仰ぐ行為）を行わず、GitHubラベルをメッセージバスとした非同期・ポーリングベースの連携（[Label Mailbox仕様](https://takenori-kusaka.github.io/process-compass/phase5-implementation/label-mailbox/)）を使用する。

- 開発に着手した際、Draft PR の状態では **`state:needs-dev`** ラベルを維持すること。
- 実装・単体テスト（CI緑）が完了し、`human-verify` 用手順を提示する際（標準の PR 運用は「human-verify を記録して Ready にする際」と定める。このテンプレートは Ready 化を人に残すため、提示の時点へ移している。テンプレート独自）、開発者（Dev）は `state:needs-dev` を剥がし、**`state:dev-done`** ラベルを付与して独立レビュア（Review）へ引き渡すこと。`state:dev-done` の受け手は独立レビュアだけであり、出荷判定者には渡さない（標準 第3章 3.5.5）。ただし G-6 が省略・未達の構成では独立レビュアの受信箱が無く、`state:dev-done` は出荷判定者が受ける。出荷判定者は PR に G-6 の省略・未達を開示したうえで扱い、`state:ready-to-merge` は使わない。開発者が自ら `state:ready-to-merge` を付けて確認の段を飛ばさないこと（同 4.3.1）。受け手は `node scripts/gate/next.mjs --role <ロール>` の受信箱が構成から出す。
- 独立レビュアは、G-6 の判定記録を作成した後に限り **`state:ready-to-merge`** を付与して出荷判定者（Ship）へ渡す。出荷判定者はこのラベルを付けない。出荷判定者が記録の突合で BLOCK 3類型を検出したら `state:qm-blocked` を付けて開発者へ差し戻す。出荷判定（G-7）は出荷の範囲ごとに行い、このラベルでは起動しない（`/pit` の出荷の段が出す）。既定ブランチへの取り込みが出荷を起動する構成では、G-7 の判定記録の後にマージする。
- 独立レビューにおいて差し戻し（`state:qm-blocked`）が発生した場合、Devは対応を最優先する。対応が完了しCIが全緑になったら、必ず `state:qm-blocked` を剥がして再度 **`state:dev-done`** に戻すこと（復路の徹底）。
- 次の3つの場合に限り、自走を停止し、受信箱のラベルを付与して人の判断を待つこと（標準 第5章 5.5.1）。(a) 人が確定する判断（ゲートの判定、R1・R2 の決定、例外承認。標準 第5章 5.5.5 の6項目の全体は `boundaries.md`）に当たる場合 (b) 受入基準・スコープ・公開インタフェース・データ形式を変える選択が必要になった場合 (c) 取り消せない操作（取り消せない効果を、他の者の操作を介さずに生じさせる操作。効果の判定の基準は、取り消せない時間帯が存在すること。取り消し操作を用意したことを理由に外さない。削除・本番デプロイ・課金の書き込み・スキーマ変更・外部への発行は例であり、これに限らない。反映・発行・マージ・配備の起動そのものを後段で人が自ら行う上流の編集は当たらない。承認・レビュー・環境の承認のような門は、人が自ら行うことに当たらない。既定ブランチへの取り込みや push が配備・公開を直接起動する構成では、その取り込み・push が当たり、自分でマージしない。後段に人だけが通せる門が残ることを理由に、止めずに行わない）が必要になった場合。付与するラベルは、価値判断が **`state:needs-po`**、取り消せない操作と事業決裁が **`state:needs-owner`**。**承認済みの受入基準とスコープの内側にある作業上の選択は、これに当たらない**。自分で決めて記録し、選択のたびに人へ戻さないこと。
- 技術設計の判断（G-3。アーキテクチャ・技術選定・ADRの採否）が必要になった場合は、**`state:needs-tech`** を付与して技術判断者へ引き渡すこと。技術判断者が開発者とレーンを共有する体制でも、**セッションを分けて**受け取ること。
- **遮断の解除・閾値の緩和・強制層の縮小**を見つけた場合は、差分が主張と一致するかまでを確認し、許容してよいかは判断しないこと。引き渡し先は `state:needs-platform`（取り消せない操作に当たる場合と、ガード・検証ゲート・重要テストの削除（統制の弱化）の場合は `state:needs-owner` も併記。取り消せない操作は、取り消せない効果を、他の者の操作を介さずに生じさせる操作であり、列挙は例示である。効果の判定の基準は、取り消せない時間帯が存在すること。取り消し操作を用意したことを理由に外さない。一覧に無いことを理由に外さない。統制の弱化の併記は、取り消せない操作の定義によらない）。**引き渡し先が分からないことを、自分で決める理由にしないこと**（特定できない場合は `state:needs-po`）。

直接の指示やメッセージを待つのではなく、定期的に自分のメールボックス（`gh` polling コマンド）を自律的に監視し、仕事を拾って処理すること。

## 統制の弱化を見つけたら

**遮断の解除・閾値の緩和・強制層の縮小**を見つけた場合は、差分が変更の主張と一致するかまでを確認し、**許容してよいかを判断してはなりません**。 <!-- 根拠: IMPL-0015 -->

| 対象 | 付与するラベル |
| --- | --- |
| 強制層(`.claude/**` 等)の縮小 | `state:needs-platform` |
| 取り消せない操作に当たる(取り消せない効果を、他の者の操作を介さずに生じさせる操作。効果の判定の基準は、取り消せない時間帯が存在すること。取り消し操作を用意したことを理由に外さない。例示の一覧に無いことを理由に外さない) | 上に加えて `state:needs-owner` |
| ガード・検証ゲート・重要テストの削除(統制の弱化。取り消せない操作の定義によらず併記する) | 上に加えて `state:needs-owner` |
| 弱化の範囲そのものの適否 | `state:needs-po` |

**引き渡し先が分からないことを、自分で決める理由にしてはなりません**。特定できない場合は `state:needs-po` を付与します。兼務していても、ラベルを経由させて引き渡しを記録します([第5章 4.7](https://takenori-kusaka.github.io/process-compass/phase5-implementation/label-mailbox/))。 <!-- 根拠: IMPL-0015 -->

## 停止の申し立て(`state:stop-requested`)

品質・安全・法令上の異常を認めたら、**誰でも**対象の PR へ `state:stop-requested` を付けて止められます(標準 第7章 7.11)。付けた時点で G-5(`pr-rules`)が失敗し、マージが保留されます。

- 付けるときは、PR のコメントへ申し立てた者(記名)と、認めた異常を書く。匿名で付けない(退けた解除の上申で、誰の見解を退けたかを追うため)
- 受信箱は事業決裁者(層1 の項目4「停止の申し立ての解除」の権限者が別にいれば、その席)。**AI の担い手はラベルを外さず、解除の記録も書かない**
- 解除は、権限者が解除の記録(テンプレ4 の節「停止の申し立ての解除」)を既定ブランチへ入れて行う。ラベルを外しただけでは解けない
- 申し立ては拒否権ではない。申し立ての件数を、申し立てた者・受けた者・チームの評価の減点に使わない
- 保証の開示に載った未達・未測定についての出荷判定者の見解は、申し立てでなく G-8 の異議で扱う

## 受信箱を見る範囲

**自分のロールのブロックだけを実行してください**。他のロールの受信箱を見た時点で文脈は合流し、分離は成立しなくなります([第5章 4.5.1](https://takenori-kusaka.github.io/process-compass/phase5-implementation/label-mailbox/))。ディレクトリが分かれていても、複数のレーンの受信箱を見た時点で文脈は合流します。

状態ラベルの付いていない Issues/PRs(孤児)の再配分は価値責任者の義務です。**再配分した仕事を自ら拾ってはなりません**。再配分の権限と、仕事を拾う権限は別です。 <!-- 根拠: 標準 第3章 3.5.5 要求事項7 -->

## エスカレーション

段階と報告先、付与するラベルの表は `node scripts/gate/next.mjs --role <ロール>` が出します。発火条件と閾値は[第7章 7.6](https://takenori-kusaka.github.io/process-compass/phase4-process-design/exception-escalation/)、実際の宛先は D-0 体制図の節6「平常時のエスカレーション」(標準の表3)によります。**ラベルの付与だけで報告を済ませてはなりません**。エスカレーションレポートの5項目(状態・原因・事業影響・リカバリ選択肢3案・推奨と決裁事項)を書きます。**推奨と決裁事項は人が記入します**。 <!-- 根拠: 標準 第7章 7.6 -->

## 人の判断待ちを出したあと

`node scripts/gate/next.mjs` が「人の判断待ち」を出した状態は終端です。AI の担い手はコマンドを実行せず、待つ席の受信箱のラベルを付けて渡します。人が判断して記録した後に、もう一度 `node scripts/gate/next.mjs` を実行します。
