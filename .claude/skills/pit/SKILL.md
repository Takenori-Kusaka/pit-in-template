# 次の一手を出す

プロセスの全体を覚えておく必要はありません。次の一手は、状態から機械が出します。

## 手順

### 1. 状態を出す

```bash
node scripts/gate/next.mjs
```

自分のロールが分かっている場合は、ロールを指定します。ロールの判定するゲート・判定してはならないゲート・受信箱のコマンド・引き渡しのラベルも出ます。

```bash
node scripts/gate/next.mjs --role <ロール>
```

### 2. 出力に従う

| 出力 | すること |
| --- | --- |
| `[次のコマンド]` | そのコマンド(スキル)を実行する。「読む:」の行があれば、そのファイルを読んでから実行する |
| `[人の判断待ち]` | **終端です**。コマンドを実行しない。待つ席の受信箱のラベルを付けて渡し、利用者へ「誰の何の判断を待っているか」を伝える |
| `[判定できない]` | 推測で進めない。理由を利用者へ伝え、人に状態を確かめてもらう |
| `[完了]` | その機能について、することはない |

機能が複数ある場合は、機能ごとに一手が出ます。1つにまとめないでください。

冒頭の「判定記録:」の行は、判定記録をどこから読んだかです。出所は3つで、どれも**記録が無い = 未判定**です。基底ブランチの `docs/gates/`(様式)、記録用ブランチ `records` の `records/gates/`(様式)、同じブランチの `records/reviews/pr-<番号>.json`(承認レビューの写し。マージを契機に機械が置く)。写しからは、1行目に宣言行(`G-4: 通過` / `G-4: 差し戻し / 基準 N / 期限 YYYY-MM-DD`)を持つ判定者本人のレビューを G-2・G-3・G-4 の記録として、承認者本人の挙動要約つきの承認を G-6 の記録として読みます。宣言行の無い承認は取り込みの事務であり、G-2・G-4 に数えません。G-2・G-4 の宣言行つきの承認は G-6 に数えません。レビューの `commit_id` が取り込んだ版と異なる通過は「確定していない版を取り込んだ」として未判定に戻り、次の一手に「版を特定し直して宣言し直す」が出ます。記録用ブランチが無い構成では、その旨が1行出て、`docs/gates/` だけで従来どおり動きます。写しを機能へ対応づけられない(PR 本文の `Spec:` トレーラ・タイトル・ブランチ名に F-NNN が無い、オフラインで本文を取れない)場合は注記に出て、推測で割り当てません。

「人の判断待ち」の「その後」には、記録の受け皿が出ます。対象が PR として存在する判定(G-6。仕様が PR の G-2・G-4)は、その PR への判定者本人のレビュー。それ以外は、様式を `records/gates/` へ置いて `records` ブランチへ push します(`/gate <ゲート>`)。

「注記(段階を止めない)」には、体制の変化点の後に生じた状態が、担当の席と次の一手つきで出ます。検出率の測定値の失効(AI の層・人の層)、後継不在の席、依存先の欄の空欄・代替なし・退出未実施、席の責任者本人の力量の確認の未確認・失効と、確認した者が名簿の外の記録、実環境の統制(ブランチ保護・PR のレビューの取得・ship-evidence の成果物)の未確認、記録用ブランチの所見(`env-check` の `findings`)のうち一致しないもの(records の保護の欠落・既定ブランチの bypass actor。AI維持管理者の席へ)と API で取れないもの(機械の承認の数え方。組織の設定の画面で人が確かめる)、10名以上の規則です。10名以上の規則には、直近の出荷の集約の出力(`evidence/evidence.json`)が手元にあれば、項目1 の件数(「同じ所属の承認者だけ N 件(#…)」、出荷判定者の所属)を集約と同じ文で添えます(集約の後に既定ブランチが進んでいれば、その旨も出ます)。**注記を消すのは人の作業**(tally のやり直し、D-0 節15 の受容、`/process-change` での記入、実環境での `env-check`)であり、AI の担い手は解消したことにしません。出荷の証跡の集約(項目4・6・7)と同じ読み取りです。構成に `coreReviewerCount`(第8章 軸C「高」)がある体制では、G-6 の注記に「**コア機能の独立レビューは N 名**(パス: …)」が常駐します(パスが未宣言なら「確かめられない」と出る。コア機能のパスは、確約範囲・コア指定のパス `delegation.protectedPaths` と区分の下限の規則 `riskFloor.rules` のパス)。層1 項目4「AI の利用の拡大」の水準が `認めない` で始まる組織では、委任の登録が構成で拒否されることと、構成に委任の登録が残っていればその旨が注記に出ます。委任の規則の承認が決定者と同一人物だった変化点も注記に出ます。

### 3. 利用者へ示す

出力のうち、利用者に関係する行をそのまま示します。言い換えて要約しないでください。

## このスキルがしないこと

- 状態を推測で補うこと。出力に無い一手を足すこと
- 人の判断待ちを飛ばして、次の段階のコマンドを実行すること
- PR・ラベル・CI の状態の判定(`next.mjs` はローカルの git と、記録用ブランチにあるマージ時点の写しだけを見ます。開いている PR のレビューは見ません。見ていないものは出力の末尾に出ます)
- ネットワークを使うのは、記録用ブランチが手元に無いときの fetch 1回と、写しの PR 本文の補完(`gh api`)だけです。セッションの開始時(`--brief`)と `--offline` では行いません
