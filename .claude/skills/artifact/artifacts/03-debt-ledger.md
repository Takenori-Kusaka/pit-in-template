# テンプレ3: 技術負債台帳

- 様式の正本: `templates/03-debt-ledger.md`(欄はここで確かめる。この補助ファイルは欄を列挙しない)
- 置き場: `docs/debt-ledger.md`
- 標準: 第6章 テンプレ3、第7章 7.3(例外承認)・7.3.2(未解決事項)

## 目的・読み手・形式

- 目的: 受容した妥協・仮実装(負債)、例外承認(例外)、未解決事項(未解決)を、**区分を分けて**1か所に残す。ゲートを止めるべきものと止めないものを見分けるため
- 読み手: 開発者・品質保証・価値責任者。G-7 の突合で出荷判定者、G-5 の PR の検査(変更規模の例外)で機械
- 形式: 1行=1件。区分は「負債 / 例外 / 未解決」のいずれか。区分「例外」の行は、対象・状態・承認した者・理由・期限の5事項を持つ

## 作成の手順

1. 台帳が無ければ `cp templates/03-debt-ledger.md docs/debt-ledger.md`
2. 負債: AI の生成の過程で見つけた妥協・仮実装はすべて記録する。「受容した理由」が書けない負債は受容しない(その場で直すか、仕様へ戻す)
3. 例外: 基準を満たさないまま進めると**人が決めた後に**書く。どの経路(例外承認・前提の受容・未解決事項)を使うかを、その場の判断で決めない。経路の詳細: `.claude/skills/gate/reference/exception-paths.md`
   - 対象は `PR #<番号>` かコミットの識別子(先頭7桁以上)。内容や備考に番号を書くだけでは対応づかない
   - ゲートの判定基準(全ゲート共通の通過条件を含む)を満たさないまま、その判定を進める例外は、変更でなく判定が対象。`G-<N> <判定記録の対象>`(例: `G-2 F-001`、`G-1 P-001`)と書く。PR の番号を先に取る必要は無い。1行が1つのゲートの1つの対象を指す(「F-001 の出荷まで」のような範囲は書かない)
   - 状態は `未返却` とだけ書く。承認した者は名簿の人の記名。**AI の名義・作成を指示した者は対応づかない**
   - 期限は日付(YYYY-MM-DD)と回収責任者
4. 未解決: 次工程の材料が未完成であることは、当該ゲートの差し戻し理由にせず、ここへ置く
5. 回収したら状態を `返却済` へ替える。回収済みの行を、別の変更の例外として使い回さない

## レビューの観点

- 区分が由来と合っているか(例外承認を「負債」として書いて報告の対象から外していないか)
- 例外の行の5事項に空欄が無いか。承認した者が作成を指示した者でないか
- 受容した理由と、顕在化の兆候が書かれているか

## 機械の検査

- 出荷判定の証跡の集約(`node scripts/gate/aggregate-evidence.mjs`): 台帳の有無、例外承認の行の対応づけ(対象・状態・承認した者・理由・期限・作成を指示した者との別)、未回収の一覧(保証の開示の項目5)
- 同じ集約が、対象がゲートの判定(`G-2 F-001`)の行を変更の行と分けて照合する。有効な行のうち、承認した者・理由・期限を欠く行、承認した者が名簿の人でない・AI の名義である行を欠落にする。成立した行は保証の開示の項目5 に出る
- G-5 の `pr-rules`(`scripts/gate/check-pr.mjs`): 変更規模の上限を超えた PR を、**基底ブランチの**台帳にその PR を対象とする有効な例外の行がある場合だけ通す。同じ PR で足した行は数えない。例外の行は、先に別の PR で基底へ入れる
- 承認した者が例外承認の権限を持つかは、機械では確かめない(内部監査)
