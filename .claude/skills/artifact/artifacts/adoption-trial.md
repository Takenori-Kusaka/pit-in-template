# 導入前の検証(附属書I I.11)

- 様式の正本: `templates/adoption-trial-criteria.md`(合否の基準)。記録の様式はコマンドが出す
- 置き場: `docs/adoption-trial/`(criteria.md・injection-seal.json・findings-*.json・injection-result.json・seeded-errors.json・drills.json・record-*.md・runs/)。出荷の集約の記録の置き場であり、記録だけのコミットとしてコミットする。測定の記録 `seeded-errors.json` は、出荷の集約が項目6 に読む(`evidence/seeded-errors.json` より先。`evidence/` は `.gitignore` の下で CI に届かない)
- 標準: 附属書I I.10〜I.12

## 目的・読み手・形式

- 目的: 採用の判断の時点の証拠を、採用者のコードと人と構成で作る。効果と人の挙動は確かめられない(残余リスクとして範囲と期限を付けて受容する)
- 読み手: 採用判断者(最終決裁者 = 層1 の記名者)、品質保証部門(見解を添える)
- 形式: 附属書I「導入前の検証の記録」の節1〜9。1件の測定(E2)

## 作成の手順

| 手順 | 担い手 | AI の担い手がしてよいこと | してはならないこと |
| --- | --- | --- | --- |
| 合否の基準 | 採用者(人) | `node scripts/gate/adoption-trial.mjs init` で様式を写す | 基準・記入日時・記入者を書く。基準のコミットの前に run する |
| 欠陥注入 | 注入する者(人)と見つける者(別の人。G-6 を2名で行う体制では2名) | 見つける者の AI の層として指摘を出す | 注入の記録(manifest)を読む・リポジトリに置く |
| 封じる・集計する | 注入した者 | `seal --manifest <リポジトリの外の所在>` → コミット → 見つける者の記録をコミット → `tally --manifest <所在>` → `seeded-errors.json` をコミット | 封じた後に注入の記録を書き換える。見つける者の記録をコミットせずに集計する(未測定になる) |
| 演習 | 判断を担う席の人 | `docs/adoption-trial/drills.json` の形を示す(`{ "drills": [{ "type": "E", "at": "YYYY-MM-DD", "result": "<処理できた量>", "judgement": "<判断の記録の所在>", "record": "<報告書の所在>", "seat": "<席(省略可)>" }] }`) | 処理できた量・判断の記録を推測で書く。実施日を未来にする(数えない) |
| 実環境の統制の確認(要件⑦) | 採用者・品質保証部門(人。実環境の gh を使える人) | コマンドの形を示す(`node scripts/gate/adoption-trial.mjs env-check --by <氏名> [--repo owner/name] [--pr N]`)。出力を読んで未確認の項目を伝える | 自分で実行して確認済みにする。記録(`env-check.json`)を書く・書き換える。模擬の gh の結果を実環境の確認として扱う |
| 実行 | 誰でも | `node scripts/gate/adoption-trial.mjs run` | 止まらなかった場面を伏せる・記録を書き換える |
| D-0 表7 への転記 | D-0 の責任者 | 記録の節4 の案内(席・量・実測の日)を示す | 表7 を AI が書く。構成(`/process-change`)へ量を入れる(表7 は手で書く表) |
| 採否と受容 | 最終決裁者(層1 の記名者) | — | 節0 の欄(実施者、下流の指標の基準値、工数の実績、理解の確認の記録、人事評価の規程と様式の写しの所在)と節9 の受容者・期限を埋める |
| 記録の確かめ | 第三者(品質保証部門・監査) | `node scripts/gate/adoption-trial.mjs verify <記録>` | 要約値の節(節10)を書き換える |

1. 基準はコミットしてから run する。コミットされていない・記入日時がコミットより後・コミットの後に書き換えた、のいずれかなら run は実行しない。実行の後に基準を改めた記録は「採用の証拠に数えない」と出る
2. 場面集11件は、リポジトリの一時の複製で、実際のゲートの検査に通す(本物の gh を呼ばない)。区分の下限の規則(構成の `riskFloor`)が無い・受容しない条件に印が無いと、該当の場面は「止まらなかった」と出る
3. 製品のコードが無いリポジトリ(テンプレートそのもの)での記録は「採用者の環境の証拠ではない」と出る
4. 止まらなかった場面は、手で代える手順を採用の条件にする(受容で終わらせない)
5. 見つける者の誰かが注入した者と同じ層、見つける者の記録がコミットされていない層、見つける者の記録が封じた時点より前の層は、`docs/adoption-trial/seeded-errors.json` に `blind: false` と理由だけを書く。出荷の集約はその層を未測定として扱う。測定の記録はコミットする。出荷の集約は、記録の置き場に記録があるとき `evidence/seeded-errors.json` を読まない(測定時点が新しくても採らない)。`method` と `blind: true` の印の無い記録、コミットされていない記録、測定時点が判定の日より後の記録は「出所を検証できない」として数えない
11. **G-6 を2名で行う体制(構成 `review.reviewerCount` が 2)では、人の層を2名で見つける**。`findings-human.json` に `finders: ["A", "B"]` と、指摘ごとの `by` を書く。検出率は和集合、各人の検出数は参考値として記録の節2 に出る。全員が注入した者と別の人であること(1人でも同一なら、その層は目隠しを満たさない)
12. AI の層の測定の記録には、測定した担い手の識別(席・モデル・指示資産の版)が入る。識別が変わると(同じ日の世代交代でも)出荷の集約はその値を失効として扱う。変化点の後は tally をやり直す
13. 人の層の測定の記録には、見つける者と各人の指摘(注入の添字)が入る。出荷の集約は、測定した見つける者と現在の独立レビュアの席の責任者・名簿の対応を項目6 に出す。全員が名簿(体制の内)から離れた層、層1 の「人の層の再測定の契機」(席の責任者の交代 / 見つける者の離脱)に当たる層は失効。一部が離れた層は残る者の指摘の和集合で読み直す(記録に各人の指摘が無い旧い記録は失効)。席の責任者が測定に含まれないときは注記(再測定の契機)。`/pit` も同じ注記を出す
14. **実環境の統制の確認(要件⑦)**は、採用者が自分のリポジトリの実環境の gh で `env-check` を実行する。読むのは、既定ブランチに効いているルールセット(要求する承認の数が構成の `review.reviewerCount` 以上、`regulated` では最後の push の後の承認・コードオーナー・push で古い承認を無効にする設定、必須チェック gate-g5)、マージ済みの PR のレビュー(`gh api …/pulls/N/reviews`。gate-g5 が `PR_REVIEWS` に渡す形)、gate-g5 の成功した実行の成果物(license-scan・test-results。ship-evidence が取り込む形)の3項目。結果は `docs/adoption-trial/env-check.json`(記録の置き場。コミットする)。確認した者の記名(`--by`)を要し、AI の名義は受け付けない。gh が無い・未認証・模擬の gh では各項目が「読めない」と出て未確認のまま残る(exit 1)。`run` は記録の節3 に写し、基準の行(第6巡の様式)があれば節6 で比べ、未確認なら節9 の受容の対象に出す。出荷の集約は項目4 に出す。記録の時点の承認者の数・ルールセットが現在の構成と違えば未確認へ戻る。記録の各項目には API の応答の識別(`evidence`: ルールセットの id、PR のレビューの id と最後の提出時刻、gate-g5 の実行の id と URL と成果物の id、応答の取得時刻)が入り、識別の無い確認済みは「実環境の証拠を欠く」として未確認に倒れる(env-check の時点でも、読む側でも)。査察は識別を GitHub の画面(Rulesets・PR のレビュー・Actions の実行)と突合する
6. 記録の名前は秒までの時刻。同じ名前の記録があれば上書きせずに止まる(1秒おいて実行し直す)
7. 演習の報告書(`docs/drills/`)と退出の予行の記録(`docs/exit-rehearsal.json`)も記録の置き場であり、記録だけのコミットでよい。評価用の基準集合(`docs/eval-baseline/` など)は評価の入力であり記録ではないため、PR で入れる(記録だけのコミットに混ぜると、出荷の集約が欠落にする)
8. 記録の末尾(節10)に、入力と本文の要約値がある。人が書いてよいのは、`<!-- human-fields start -->` から `<!-- human-fields end -->` までの表の、印に書いた列(節0 の「記入」、節9 の「受容者」「期限」)だけ。それ以外を書き換える、または節10 の後ろへ所見・判定を書き足すと、`verify` が不一致を出し、記録として数えない(要約値は全文が対象。記録の末尾は節10)。所見・判定は別の文書に書く
9. 以前の実行の後に基準を改めた記録の「採用の証拠に数えない」は、`runs/` と git の履歴(記録のコミットの時刻と、その時点の基準)の両方から判定する。`runs/` を消しても消えない
10. 類型F の演習は、`drills.json` と `docs/exit-rehearsal.json` の同じ演習(同じ実施日で提供者が矛盾しない)を節4 で1行にまとめる。判断の記録は退出の予行の記録の値を優先し、無ければ演習の記録の値

## レビューの観点

- 席に就く予定の人が実施したか(記録の節0 の実施者の欄)。注入した者と見つける者が別の人か。G-6 を2名で行う体制では見つける者が2名か(記録の節2 に各人の検出数が出る)。節0 の欄(Q10・Q11・Q15・Q17 の証拠の所在)が埋まっているか
- 類型E の結果が D-0 表7 へ転記され、実測の日が書かれているか(記録の節4 に「転記は不要」と出るか)
- 止まらなかった場面と確かめていない場面に、手で代える手順があるか
- 残余リスクの受容者が層1 の項目4 の権限者で、期限が再判定日より前か

## 機械の検査

```bash
node scripts/gate/adoption-trial.mjs env-check --by <氏名>   # 実環境の統制の確認(人が実環境の gh で実行する。AI は実行しない)
node scripts/gate/adoption-trial.mjs run    # 基準の確認 → 場面集 → 実環境の統制の記録 → 演習の記録 → 成立判定 → docs/adoption-trial/record-*.md
```

- レビューの観点に足す: 実環境の統制の確認(節3)が3項目とも確認済みか。未確認のまま採用の判断を進めるなら、節9 の受容の行に受容者と期限があるか
