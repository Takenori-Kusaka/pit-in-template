# テンプレ7: 実装計画(plan)

- 様式の正本: `templates/07-implementation-plan.md`(欄はここで確かめる。この補助ファイルは欄を列挙しない)
- 置き場: `specs/F-NNN/plan.md`
- 書く手順の詳細: `.claude/skills/task-breakdown/SKILL.md`(このファイルより、そちらの手順を優先する)
- 標準: 第6章 テンプレ7、第4章 G-4・「タスクの分割基準」

## 目的・読み手・形式

- 目的: 機能仕様をレビューの単位へ分解し、各タスクがどの受入基準に対応するかを明示する。G-4 の基準「1タスク=1レビュー単位」を突合できる形にする
- 読み手: 価値責任者(G-4 で判定する)、AI の担い手(タスクの順に実装する)、レビュア
- 形式: タスクの表(ID・内容・対応する受入基準・変更の対象パス・依存・並列可否)、粒度の自己点検、実装順序

## 作成の手順

1. `/task-breakdown F-NNN` を実行する。手順はそのスキルが持つ
2. 1タスク = 1レビュー単位。上限は構成の `task`(既定 400行・15ファイル・30分で読み切れること)。詳細: `.claude/skills/implement/reference/task-size.md`
3. 上限を超えそうなタスクは、行数に合わせて細切れにしない。関心事で分ける。それでも超えるなら、例外承認を経て超過レビューにする(人が決める)
4. 各タスクは単独でビルドと G-5 が通る。新しいインタフェースは利用箇所と同じタスクに含める
5. タスクの ID(`Task-N`)は、コミットと PR のトレーラ `Spec: F-NNN / Task-N` が指す。ID を付け替えない

## レビューの観点

- 各タスクが、どの受入基準に対応するかを書いているか(G-4 基準1・2)
- 各タスクの規模が分割基準の範囲か(G-4 基準4)。関心事を混ぜていないか
- 依存の順序が正しいか。依存の無いタスクを並列可としているか
- 分割しすぎていないか(単独で意味を持たない変更が無いか)

## 機械の検査

- `next.mjs`: 「タスク」の表の `Task-N` の行と依存を読み、既定ブランチのトレーラから取り込み済みのタスクを判定する
- G-5 の `pr-rules`(`scripts/gate/check-pr.mjs`): PR のトレーラが指すタスクが、この表にあるかを確かめる。PR の変更規模を、構成の上限(基底ブランチの値)で検査する
- 粒度の自己点検の内容の妥当性は、機械では確かめない(判定者が確かめる)

## 関係するスキルとゲート

- `/task-breakdown`(作成)、`/implement`(次の工程)
- G-4 機能仕様承認(`/gate G-4`)
