# 障害時に使う記録

障害時に新しい様式は作りません。既存の成果物を、次の順に引きます。

- 標準: 運用フェーズ「インシデント対応とポストモーテム」、第6章 テンプレ0(障害時の指揮系統)・テンプレ5
- 置き場: D-0 体制図 `docs/D-0-governance.md`(障害時の指揮系統)、運用引き継ぎ文書 `docs/handover.md`(監視・連絡先・復旧手順)、技術負債台帳 `docs/debt-ledger.md`

## 目的・読み手・形式

- 目的: 検知から復旧、ポストモーテム、恒久層への書き戻しまでを、既存の記録で回す。**一次分析は AI、対処の判断は人**
- 読み手: 当番(重大度の判定・初動・エスカレーションの権限を持つ)、エスカレーション先、コア機能の理解保持者
- 形式: 平常時のエスカレーションと障害時の指揮系統は D-0 の別の表。ポストモーテムの様式は運用フェーズの標準にある(Sev1・Sev2 は必須)

## 手順(AI の担い手がすること・しないこと)

| 工程 | AI の担い手 | 人 |
| --- | --- | --- |
| 検知・一次分析 | ログ・指標の横断検索、影響範囲の推定、直近の変更の照合 | 分析の妥当性の確認、**重大度の判定**(当番が単独で即断。迷ったら高い方) |
| 連絡 | D-0 の障害時の指揮系統と、引き継ぎ文書の連絡先を引いて示す | 連絡する |
| 対処 | 対処案と切り戻しの手順を示す | **対処の決定と実行**。本番への変更は人が承認する(取り消せない操作) |
| 修正 | 修正の PR を作る(G-5 と事後のレビューを省かない) | 確認を待てない場合の例外承認(人確定) |
| 記録 | タイムラインの下書き | 事実の確認、再発防止策の決定 |

- コア機能の障害は、理解保持者が対応する。AI の推測だけで本番を触らない
- 確認を待てない緊急の修正は、例外承認(標準 第7章 7.3)を経る。台帳の区分「例外」に、その PR を対象として人が記録する。回収の期限までに独立した人が事後に確認する(`artifacts/03-debt-ledger.md`)
- AI が使えない期間(提供者の障害・利用上限)は、変化点に数えず、`/process-change` の種別 `outage` で期間と扱いを記録する(`.claude/skills/process-change/kinds/outage.md`)
- 体制の変化を伴う場合(当番の交代ではなく席の責任者の交代など)は `/process-change`

## ポストモーテムと書き戻し

1. Sev1・Sev2 は復旧後3営業日以内に、個人を責めない前提で書く
2. 再発防止は仕組み(監視・CI・手順)の変更にする。「注意する」「周知する」を再発防止策にしない
3. 学びは恒久層のコンテキスト(`context/standards/` など)へ PR で書き戻す。受容した残りは技術負債台帳へ
4. Sev1 の事後レビューは、D-0 の定期の見直しの契機である
5. 引き継ぎ文書の手順が古かった場合は、`/artifact 05` で直す

## レビューの観点

- 重大度の判定と、本番への操作を人が行ったか
- 緊急の修正に、例外承認の記録(台帳の行)があるか
- 再発防止が仕組みの変更か

## 機械の検査

- 障害対応そのものを検査する仕組みは、このテンプレートに無い
- 緊急の修正の PR も G-5 を通る。出荷判定の証跡の集約は、例外承認の行が対応づかない未確認の変更を欠落にする
