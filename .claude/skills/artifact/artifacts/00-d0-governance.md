# テンプレ0: 意思決定・エスカレーション体制図(D-0)

- 様式の正本: `templates/00-d0-governance.md`(欄はここで確かめる。この補助ファイルは欄を列挙しない)
- 置き場: `docs/D-0-governance.md`
- 標準: 第6章 テンプレ0、第3章 3.13(体制の変化点)

## 目的・読み手・形式

- 目的: **誰が決めるか**と、**どこまでなら自分で決めてよいか**を1つの文書で確定させる。案件で最初に作る成果物で、企画承認(G-1)の前提条件
- 読み手: 全関係者と監査。判断が必要な場面で、決定者・権限境界・通知先と応答期限を引く
- 形式: 平常時のエスカレーション(様式の節6)と障害時の指揮系統(節7)を**別の表**にする。個人名は節1(現任者)と節13(改訂履歴の「決定した者」)だけに書き、ほかの表は役割名で書く
- 規模によらず必須。人数が少ないほど兼務が増え、誰が決めるかが曖昧になるため

## 作成の手順

1. `cp templates/00-d0-governance.md docs/D-0-governance.md`
2. `node scripts/init/generate-profile.mjs --answers process.config.json` で、構成から生成する区間(節1 の責任者の表、節12 の担い手と運用形態、節13 の改訂履歴、節3 の2行の決定者)を書き込む。**この区間は手で書かない**
3. 席の責任者と人の名簿は、人が決めた後に `/process-change`(初回の記入。種別 `accountable`)で構成へ入れる。補助ファイル: `.claude/skills/process-change/kinds/accountable.md`。**氏名を推測で埋めない**
4. 生成区間でない節(節3「決定の権限」の生成されない行、権限境界、判定の期限、エスカレーション、障害時の指揮系統と有事の決定者、代行者と代理者の確認の状態、会議体の対応づけ、節12 の縮退の3列、節15 の組織継続の状態の受容、冒頭の層1 の版)は、人が記入する。AI は叩き台を示してよいが、権限境界の数値と決定者は人が決める(下の「手で書く節と版」)
5. frontmatter の承認者・承認日・承認の範囲・次回の見直し期日は、承認した人が書く
6. 体制が変わったら、最初のゲート判定より前に `/process-change` で改訂する。成立済みの判定記録は書き換えない

## 手で書く節と版

- 節3「決定の権限」のうち、構成から書き込まれるのは「体制と運用形態」と「標準変更カタログへの登録」の2行の決定者だけ(変えるときは `/process-change` の種別 `governance`)。**ほかの行(例外承認、要件・受入基準の確定、出荷の可否など)は手で書く欄であり、`/process-change` の種別は無い**
- 手で書く欄を記入・変更しても、**frontmatter の `version` を上げない**。版を上げるのは体制の変化点を反映する `/process-change` だけである。構成の `d0Version` と一致しない版は `check-d0` が失敗させ、判定記録の「参照した D-0 の版」との照合も崩れるため
- 手で書く欄の変更は PR で入れ、変更の経緯は PR と git の履歴に残す。決定者を変える場合は、変更前の決定者と、D-0 の承認者(frontmatter の `approver`)が PR で確かめる
- `next.mjs` は、節3 の「決定」が空欄の行を数えて出す(手で書く欄であることと、版を上げないことを添える)。例外承認の決定者が空欄のまま、例外承認の行を記録しない

## 組織継続の側の欄(#288)

- 冒頭の層1 の版: `docs/quality-assurance-policy.md` の版と記名日。無い組織は「層1 なし」。層1 の版の更新は体制の変化点
- 節7 の有事の事象の表: 重大事故・情報漏えい・契約変更・規制変更ごとに、停止・切替・顧客説明の決定者を役割名で書く。組織に及ぶ事象は層1 の項目4 を引き、別の決定者を書かない。**12欄の空欄は記載の欠落**(出荷の集約が失敗させ、`check-d0` も表示する)。該当しない事象は「層1 の項目4 による」と書く
- 節9 の代理者(後継候補。席ごとに複数行可)の確認の状態と確認日: 確認済み / 暫定任命 / なし。**確認済みで確認日が層1 の力量の確認の周期の内の候補の数が、層1 の最低数に満たない席は「後継不在」と出る**。確認は自己申告では認めない
- 節9 の「席の責任者本人の力量の確認」(第3章 3.4.3 要求事項1)は生成区間。記録は `/process-change`(種別 `accountable` の `seats.<席>.competence`)で構成へ書く。**手で書かない**(`check-d0` が失敗する)。記録の無い新任の責任者は「未確認(確認を経ない任命)」、周期を過ぎた確認は「失効」として、出荷の集約の項目7 と `/pit` に出る。第6巡より前の様式の D-0 には目印が無い。`templates/00-d0-governance.md` の節9 から目印の行を写し、`node scripts/init/generate-profile.mjs --answers process.config.json` で区間を書き込む(`check-d0` が注意で案内する)
- frontmatter の `project_id` は、様式の初期値(`P-001`)のままなら生成時に構成の案件 ID で埋まる。人が別の値を書いた D-0 は上書きされず、`check-d0` が構成との不一致を注意として出す
- 節12 の縮退の3列: AI の担い手を置いた席ごとに、処理できる量を**実測**で書き、実測の日を併記する(実測が無ければ「未確認」)。見積りを書かない。層1 の縮退の実測の頻度を過ぎた量は「未確認」へ戻る。量の更新は変化点に数えない
- 節15 の受容: 証跡の集約が出す単一障害点の一覧に対して、層1 の項目4 の権限者が期限つきで記名する。**期限を過ぎた受容は記載の欠落**。AI はこの表を埋めない

## レビューの観点

- 決定の種類ごとに、決定者が1名に特定されているか(合議体・「チーム」を決定者にしていないか)
- 権限境界が数値で書かれているか。境界を超えたときの通知先と応答期限があるか
- 平常時と障害時が別の表か。障害時の指揮を職位でなく、知識と状況の把握度で割り当てているか
- 兼務を明記しているか。3名以上で兼務禁止の組(開発者 × 独立レビュア など)を同じ人が兼ねていないか
- AI の名義が、責任者・決定者・承認者の欄に無いか
- 節9 の代理者の確認の状態が、証拠(AI を使わない成果物・面前の演習)に基づくか。節12 の処理できる量が実測か

## 機械の検査

```bash
node scripts/gate/check-d0.mjs              # frontmatter の承認・見直し期日、生成区間と構成の一致
node scripts/gate/verify-gate-contract.mjs  # 構成と変化点の記録の連鎖
```

- `gate-entry` ワークフローも、frontmatter の欠落と見直し期日の経過で失敗する
- 権限境界の数値の妥当性と、決定者が実在の人かは、機械では確かめない(内部監査)
- 節9・節12・節15 と冒頭の層1 の版は、出荷判定の証跡の集約(`aggregate-evidence`)が読み、単一障害点の一覧と保証の開示の項目5・7 へ出す。期限切れの受容だけを欠落にする
