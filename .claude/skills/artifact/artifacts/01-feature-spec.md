# テンプレ1: 機能仕様書(spec)

- 様式の正本: `templates/01-feature-spec.md`(欄はここで確かめる。この補助ファイルは欄を列挙しない)
- 置き場: `specs/F-NNN/spec.md`
- 書く手順の詳細: `.claude/skills/spec-write/SKILL.md`(このファイルより、そちらの手順を優先する)
- 標準: 第6章 テンプレ1、第4章 G-2・G-4、EARS 記法ガイド

## 目的・読み手・形式

- 目的: 何を作るかを、**検証できる受入基準**で確定させる。受入基準を確定せずに実装を始めない(禁止事項1)
- 読み手: 価値責任者(判定する)、AI の担い手(実装とテストの入力にする)、独立レビュア(G-6 で仕様と実装の一致を確かめる)
- 形式: 受入基準は「条件 + 期待動作」で書く。曖昧語を使わない。コア / 非コアの指定、スコープの層(G-4 で判定者が記入)、スコープ外、前提・依存、未確定事項を持つ

## 作成の手順

1. `/spec-write F-NNN` を実行する。手順はそのスキルが持つ
2. 受入基準の叩き台は AI が書いてよい。**AI が生成した受入基準をそのまま承認しない**(禁止事項2)。価値責任者が読み、直す
3. 未確定事項は `[NEEDS CLARIFICATION]` として残す。G-2・G-4 の通過までに解消する
4. 暗黙の前提は、案件層のコンテキスト(`context/projects/`)へ登録し、ID を併記する
5. 完了の条件を曖昧さなく書けない機能は、書けるところまで分解してから実装計画へ渡す

## レビューの観点

- 受入基準が「条件 + 期待動作」になっているか。1つの基準に複数の期待動作を混ぜていないか
- 企画書の観点3(受益者と価値)に書いた価値のうち、受入基準へ対応するものが1件も無い項目が残っていないか(G-2 基準1。内容の良否ではなく対応の有無)
- スコープ外(やらないこと)が書かれているか
- 合意した範囲がスコープの3層(SC-M・SC-P・SC-B)へ割り当てられているか(G-2 基準5)
- 公開インタフェース・データ形式を変える基準は、R1 の変更として扱う必要がないか

## 機械の検査

```bash
node scripts/gate/spec-lint.mjs specs/F-NNN   # 曖昧語(語の一覧の正本はスクリプト)
```

- G-5 の `spec-lint` ジョブが同じ検査を PR で行う
- G-5 の `pr-rules` は、トレーラ `Spec: F-NNN / Task-N` が指す仕様の実在を確かめる
- `next.mjs` は「受入基準」の表の記入済みの行を数える。内容の妥当性は判定しない
