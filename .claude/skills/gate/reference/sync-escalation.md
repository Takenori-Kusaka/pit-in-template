# 同期の場へのエスカレーション(標準 第3章 3.10.10。IMPL-0218)

事前レビュー期間の非同期のコメントで、非同期のまま決めてはならない対立が起きたときの手順です。**機械は往復を数えません**。Issue のコメントは平らで、どのコメントがどの論点に属するかが構造に無く、「同一論点の応酬」の判断は意味を読むためです(往復の交互の回数で近似すると、論点が違う往復を数え、誤った保留を促します。採らない)。判断するのは起案者、確かめるのは決定者(判定当日)です。

## 上げる条件(いずれかに該当した時点。判定日を待たない)

| 条件 | 上げる先 |
| --- | --- |
| 同一論点のスレッドで応酬が3往復を超えた(暫定。標準 EV-0002) | 設計の変更を伴うなら B-3、投資・期日・範囲に及ぶなら B-2、それ以外は決定者が招集する臨時の場 |
| リスクの受容可否について、必須応答ロールと起案者の判断が分かれた | 同上(受容の主体を確定する) |
| 対立が判定基準の解釈に及んでいる | 標準を所管する部門(EN-3)。個別案件の判定と分ける |
| 反対意見が代替案として設計の変更を求めている | B-3 設計審査会 |

## 手順(起案者が行う)

1. 対象の上程の Issue(ラベル `pre-review`)に、同期の場へ上げる旨と上げる先、条件のどれに当たるかをコメントで書く
2. **判定を保留にする**。判定予定日 T を過ぎるときは、Issue の「判定予定日 T」の欄を改め(日付を直し)、保留にした旨を同じコメントに書く。同期の場を開けないことを理由に、非同期のまま判定しない
3. 同期の場を開く。結論は、**根拠と反対意見をあわせて**記録する
4. 結論を、元の非同期のスレッド(上程の Issue の該当のコメント)へ書き戻す。**記録を伴わない口頭の合意を、有効な合意として扱わない**

## 確かめる者

決定者が、判定当日に、保留の記録と書き戻しの有無を見て確かめる(manual)。機械の検査は無い。
再開後に締切の通知の日がずれるのは、Issue の「判定予定日 T」の欄から日付を求めているためである。欄を改めると締切の日が変わり、通知の印は締切の日ごとに別になるため、新しい締切で、これから来る時点の2営業日前・前営業日・締切後の通知が一度ずつ出る(同じ締切では重ねて出さない)。欄を改めた時点で過ぎている時点の通知は出ない。この出し直しは事前レビューの workflow による(結線待ちで、実物の GitHub では確かめていない)。
判定資料の Issue の本文にある T は起票時の値のまま残る。欄を改めたら、資料の本文の T は起案者が直す。

## 理由のない反対を意見として扱わないとき(標準 第3章 3.10.4。IMPL-0231)

意見には賛否と理由をあわせて書く決まりで、**理由のない反対は意見として扱わない**。ただし、扱わないと決めるのは起案者だけではできない(起案者は意見の採否に利害を持つ)。機械は意見の様式の欄の空欄を注意で示すだけで、意見として扱わないかを決めない。

1. 起案者が、応答の宣言行に「意見として扱わない」旨と理由を添える。書き方は次のとおりで、宣言行(`応答: <意見のコメントの URL>`)の同じ行の後ろに付ける。応答として数えるかどうかは、これまでどおり宣言行の URL だけで決まる(添えた文は読まない)

```text
応答: https://github.com/<org>/<repo>/issues/<番号>#issuecomment-<id> 意見として扱わない(理由: 反対の理由が書かれていない。賛否の欄の「反対」だけで、理由と代替案の欄が空)
```

2. 決定者が、判定の当日に、扱わなかった意見の有無と理由を上程の Issue で読み、判定記録の既存の欄で確かめた旨を書く。工程ゲートで判定記録を様式で残すときは「確認した項目」へ、会議体 B-1〜B-4 の判定は「意見を述べた者と賛否・理由」の欄へ。様式に欄は足さない
3. 決定者が理由を妥当と読めないときは、その意見を扱う(判定を進める前に、起案者へ応答を求める)

確かめる者は決定者(manual)。「理由が無い」かどうかの判断は意味を読むため、機械は決めない。
