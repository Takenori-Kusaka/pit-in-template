# 判定記録の共通の欄

`/gate` の手順4 の詳細です。ゲートに固有の欄(G-6 の挙動要約、G-8 の異議など)は、各ゲートの補助ファイルにあります。

## 共通の欄

| 欄 | 書くこと |
| --- | --- |
| ゲート | G-1〜G-8・SG |
| 対象 | 案件 ID / 機能 ID / PR の番号(`PR #<番号>`)/ コミットの識別子 / タグ。G-2・G-4 は、機能 ID と、確定した受入基準の版(コミットの識別子 `F-012 / 1a2b3c4`、または仕様の PR の番号 `F-012 / PR #34`。標準 第4章 G-2)。承認レビューで判定した場合は、レビューの識別子を併記してよい。マージ後のコミットの識別子は機械が併記する(段階 2) |
| 判定者 | **1人**。合議体にしない。席の責任者(人)。**AI を判定者に書かない**。機械が出してよい欄(レビューの `user.id` と名簿の席から。出所を併記) |
| 判定日時 | 判定者が書く。承認レビューで判定した場合は、機械がレビューの `submitted_at` から出してよい(出所を併記) |
| 結果 | 通過 / 差し戻し。判定者が書く。**欄には「通過」か「差し戻し」の語だけを書く**(下記) |
| 確定の形態 | 人確定 / 協働 / 委任 のいずれか1つ(下記)。判定者が選ぶ |
| 参照した D-0 の版 | 判定の時点の `docs/D-0-governance.md` の `version`。構成の `d0Version` と一致すること。機械が出してよい欄(基底ブランチの構成から。出所を併記) |
| 変更のリスク区分 / 確定した者 | 変更を対象とする判定でだけ書く。確定した者は人が記名する。**AI が自分の名義を書かない**。作成側の自己記載のままなら「自己記載」 |
| 差し戻し理由 | 判定基準の項目番号で示す。再提出の期限を添える(標準 第4章「工程ゲートの判定の語彙」) |
| 確認した項目 | 判定基準の表 |

## 機械が出す欄と、人が書く欄(ADR-0070)

| 機械が出す欄(推定を含まない写し。出所を併記する) | 人が書く欄(判定者本人が自分の言葉で。AI に生成させない) |
| --- | --- |
| 判定者(アカウントの数値の識別子と名簿の席)、判定日時、提出日時、対象(PR 番号・コミットの識別子・レビューの識別子)、結果(宣言行から写す)、参照した D-0 の版、承認の数、作成を指示した者との別 | 挙動要約、確認した項目、確認していない事項、差し戻し理由(項目番号と再提出の期限)、決断の記録、比較した選択肢の採否の理由、リスク区分の確定者の記名 |

- 機械が出す欄は、判定の草案を起こす文脈(判定者以外。AI の担い手でよい)が PR の記録と基底ブランチの構成から埋める。**判定者本人の手入力でなくてよい**。欄の数は減らない。変わるのは欄の出所だけ
- 人が書く欄を、機械が PR 本文・Issue のコメント・AI の出力から写してはならない。附属書C の「AI 転記」に当たる。結果を機械が写すのは、判定者本人が書いた宣言行(下記)からだけ <!-- 根拠: 標準 第4章「判定の成立」 -->

## 受け皿が承認レビューのゲート

人が書く欄の受け皿は 2 つに限る(標準 第4章「判定の成立」)。PR 本文(作成側の欄)と Issue のコメント(コミットに固定されず削除できる)は受け皿にしない。

| 判定 | 受け皿 |
| --- | --- |
| 対象が PR として存在する判定(G-6。G-2・G-3・G-4 で仕様・ADR が PR として存在する場合) | **判定者本人のレビューの本文**(下の雛形) |
| それ以外(G-1・G-7・G-8・SG、例外承認、停止の解除、対象が PR でない場合、ホスティングがレビューを記録として保てない場合) | **様式**(`templates/04-gate-record.md`)。後退経路であり、レビューと様式を選べる場面は無い |

レビューの条件(G-2・G-3・G-4):

- 判定者本人のレビューであること。**状態は問わない**(APPROVED / CHANGES_REQUESTED / COMMENTED)。PR の作成者本人は APPROVED を出せないが COMMENTED は出せる(2026-10-23 の実機確認)。作成者本人の判定者は COMMENT で提出する
- 本文の 1 行目に宣言行を書く。続けて「確認した項目」を基準の項目番号で書く。宣言行の無い承認は取り込みの事務であり、G-2・G-4 に数えない

```markdown
G-4: 通過
確認した項目: 基準1(受入基準の形式)、基準2(タスクの表と受入基準の対応)、基準3(コア指定)、基準4(規模の見込み)、基準5(スコープの層)
```

```markdown
G-4: 差し戻し / 基準 2 / 期限 2026-10-30
確認した項目: 基準1、基準3、基準5
差し戻し理由: 基準2。Task-3 が受入基準 AC-4 に対応していない
```

- 対象の版はレビューの `commit_id`。人は「機能の ID + PR 番号」を書き、マージ後のコミットの識別子は機械が併記する(段階 2)。レビューの後に push があれば、集約が「確定していない版を取り込んだ」として欠落に数える(段階 2)
- **この承認を、G-6 の独立した人の確認に数えない**。受入基準の確定であり、別の人による確認ではない(ADR-0060)

レビューの条件(G-6)は `gates/G-6.md`(挙動要約。変更要求には満たさない基準の項目番号と期限)。

**段階 1 の制約**: `next.mjs` と出荷の証跡の集約は、まだレビューの写し(記録用ブランチ `records` の `records/reviews/pr-<番号>.json`)を読まない(段階 2)。それまでは、レビューの本文に加えて様式を `docs/gates/` に置く。様式の機械が出す欄は草案の文脈がレビューから埋め、人が書く欄には「レビュー <識別子> の本文のとおり」と所在を書く(本文を写さない)。結果欄は宣言行から 2 値の語だけを写す。判定者は様式へ書かず、下の「記録だけの PR の届け方」で承認だけを行う。段階 2 で様式は不要になる。

## 記録だけの PR の届け方

記録だけのコミット(様式、停止の解除・例外承認の台帳)を基底ブランチへ入れる操作に、標準は記名者以外の承認を課さない。GitHub のルールセットはパス単位の免除を持たないため、承認を強制する構成では記録だけの PR にも承認 1 件が残る(`.github/rulesets/README.md`「記録だけの PR にも承認 1 件が残る」)。残る承認を、記名者本人の操作にする手順:

1. **記名者は push しない**。判定の草案を起こす文脈(AI の担い手)が、機械が出す欄を埋めた様式をブランチ `docs/gate-<ゲート>-<対象>` へ push し、PR を開く(PR の本文は様式どおり。記録だけの PR も G-5 の `pr-rules` の検査は同じ)。`require_last_push_approval` の下では、記名者が push すると自分で承認できなくなる
2. 記名者は、人が書く欄(結果・確認した項目・差し戻し理由・決断の記録)を、**その PR の上で自分の名義のレビューのコメントとして書く**(口頭・チャットで草案の文脈へ渡さない)。草案の文脈は、そのコメントの文を一字も変えずに様式へ写して push する。記名者は、様式の文が自分のコメントと一致することを確かめる。記名者のコメントが PR に残るため、代筆の有無を後から確かめられる
3. 記名者本人が承認し、マージする。承認者 = 記名者が、帰属の裏づけになる
4. 記名者と同じアカウントで草案の文脈が push する体制(認証情報を共有する体制)、承認者 2 名の構成、1 名体制で `checks-only.json` を使う構成では、記名者以外の承認が付くか、承認が無い。**他者の承認は、ファイルの取り込みの事務であり、判定ではない**。承認者は記録の中身を判定していない。裏づけの無い記録は、記名が自己申告であることを保証の開示へ出す(段階 2 で集約が照合する)
5. 停止の解除と例外承認の台帳は、現行どおり基底ブランチへ先に入れる(G-5 は基底ブランチの記録だけを読む)。この PR も同じ手順で届ける

## 結果欄には2値の語だけを書く

- 結果欄は `通過` または `差し戻し` の語だけにする。`next.mjs` は完全一致で読み、注記を足した値(例: 「通過(判定者の申告を転記)」)や様式の文言のままの値を通過に数えない。その場合は、記録の所在と「結果欄が2値のどちらでもない」理由を出す
- 判定者の申告を AI の担い手が転記した旨、確認の経緯、条件などの注記は、結果欄ではなく**本文の節**(「人が判断する項目」の下、または「添付」の節)へ書く
- 判定者の発言を転記して記録を起こす場合も、結果欄の確定は判定者本人が行う。判定者が確かめていない申告を、結果欄へ書かない
- 結果欄を書き誤った記録を見つけても、AI の担い手は書き換えない。判定者へ戻し、判定者本人が結果欄を直す(2値のどちらとも読めない記録は、判定として成立していない)

## 確定の形態

判定者の席の運用形態(`process.config.json` の `seats[].mode`)と、その変更のリスク区分で決まります。**席の宣言は上限です**。変更ごとのリスク区分の判定がそれを下げます。

| 確定の形態 | 書く場面 |
| --- | --- |
| 人確定 | 人が判断し、理由を自分で書いた。**R1 の決定と例外承認は、席の宣言にかかわらず人確定**。G-8 と SG も同じ |
| 協働 | AI が起案した判断の案と根拠を、人が変更ごとに確認して確定した |
| 委任 | 登録した範囲で先へ進めた変更を、独立レビュアの席の責任者が**事後の抜き取りで確かめた記録**(G-6 だけ。`gates/G-6.md`) |

- どの形態でも、判定者の欄には席の責任者(人)を書く。AI の確認を判定として記録しない
- 協働で確定した判定でも、挙動要約と判定の記名は人が行う。AI が起案した文面を、人の要約として残さない

## 参照した D-0 の版

体制の変化点(`/process-change`)の後は、改訂後の版を参照して判定します。改訂前の版を参照した新しい判定記録は、証跡の集約で欠落になります。**成立済みの判定記録の版は、変化点の後も書き換えません**。

## 判定基準の表を展開する(ADR-0048)

- `scripts/vendor/tailoring-kb.json` の `gates` から、対象のゲート(例: `g-spec-cycle` が G-4)の `criteria` を引く。ゲートの ID は各ゲートの補助ファイルにある
- 基準を2つの表へ分ける
  1. **機械で確かめられる基準** → `## 機械が確認した項目 — 人は再確認しない` の表。「機械で確認した範囲」の列を必ず埋める(例: 「見たのは空欄でないことだけ。内容の妥当性は判定していない」)
  2. **人の判断が要る基準** → `## 人が判断する項目` の表。材料だけを書き、結論を書かない
- 振り分けた理由を「機械で確認した範囲」の列に書く
- 表の下に、次の注意書きを置く

```markdown
> ⚠️ 注意: この一覧は標準第4章の判定基準表のみを機械抽出したものです。表外の規定・解説については、必ず出所(上記 URL)を参照してください。
```

## PR を経ていないコミットで、トレーラを書き忘れた場合

PR を経ていないコミットは、リスク区分をトレーラ `Risk:`、作成側の検証の記載をトレーラ `Verification:` に持ちます。書き忘れたコミットは書き換えません。**判定記録の「対象」へコミットの識別子(先頭7桁以上)を書き、「変更のリスク区分」の欄へ区分を、「検証方法と結果」の節を足して検証の記載を書いて確定します**。この節は、書き忘れを補う場合にだけ足します。区分の確定は人が行い、記名します。

## 判定記録は、出荷ごとに要る

証跡の集約は、**当該出荷の範囲で追加された判定記録**だけを、今回の出荷の記録として数えます。過去の出荷の判定記録が残っていても、今回の記録が1件も無ければ欠落です。
