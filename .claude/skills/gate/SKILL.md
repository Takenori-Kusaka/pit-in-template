# ゲート判定を記録する

ゲートごとの知識は補助ファイルにあります。**指定されたゲートの1枚だけを読みます**。

## 判定の原則(全ゲート共通)

1. **記録をもって判定が成立する**。判定は、判定記録の作成をもって成立する(標準 第4章)。記録とは欄が埋まった記録であり、媒体は 2 つに限る。対象が PR として存在する判定(G-6、仕様・ADR が PR として存在する G-2・G-3・G-4)は**判定者本人のレビューの本文**、それ以外は**様式**(記録用ブランチ `records` の `records/gates/`。基底ブランチの `docs/gates/` へは出荷判定(G-7)の PR が複製する)。置き方はテンプレート独自。Issue・PR・ラベルの操作は事務であり、記録の無い期間は未判定
2. **判定は人が行う。このスキルが行うのは、材料と記録の様式を整えることだけ**。判定者・判定日時・対象・参照した D-0 の版は機械が出してよい欄(PR の記録から。出所を併記)。**結果の欄と判断の中身を先に埋めない**。確定の形態・異議・受容の記名を AI が書かない(`reference/recording.md`「機械が出す欄と、人が書く欄」)
3. **判定に持ち込むのは、当該ゲートの判定基準と全ゲート共通の通過条件だけ**。次工程の材料の未完成、基準に無い懸念、投資を続けるか(SG で扱う)、判定者の所属組織の内規(テーラリングで扱う)を持ち込まない
4. 全ゲート共通の通過条件: 当該の工程に関係する前提の充足状態が前提の台帳(`docs/assumptions.md`)に記録され、AS-1 以上に受容の決裁があること。前提の定義と観測の手がかりの要約は `.claude/skills/artifact/artifacts/10-assumption-ledger.md`(外部のサイトを読まずに記入できる)。台帳が無ければ、判定の材料を揃える前に作る。**前提が崩れていることを理由に判定を停止しない**。崩れている事実を台帳に可視化し、受容の決裁を求める(停止は申告そのものを止め、測定を無効にすることがある。前提の台帳の手引きも同じ扱い)
5. 判定は「通過 / 差し戻し」の2値。**条件付き通過は無い**。基準を満たさないまま進めるのは例外承認だけ(`reference/exception-paths.md`)
6. **AI による差分の要約は、判定資料の必須にしない。要約だけを読んで判定しない**(標準 第3章 3.10.12「重点箇所の提示」)。要約を材料に添付するときは、要約と原資料(差分・記録・ログ)の両方へ届く所在を並べる。判定記録の根拠には、要約ではなく原資料の該当箇所(パスと行、コミットの識別子、記録の所在)を書く(様式の「人が判断する項目」の列「根拠とした原資料の所在」)。この要約は、独立レビュアが自分の言葉で書く挙動要約(G-6)とは別のものである
7. **工程ゲート(G-1〜G-8)は単独判定である**(標準 第4章)。判定者は1人で、関係者の意見は、判定の前に公開された期限までの非同期のコメント期間に集める。判定会議は開かない。G-6 の承認者を2名とする体制でも同じで、2件の承認は2件の確認として数える。会議体の語彙(継続・中止・保留・差し戻し)は工程ゲートへ適用しない
8. **判定当日に議題を設けるとき(会議体 B-1〜B-4 の判定。工程ゲートは判定会議を開かないため当たらない)、議題は判定資料の未解決の論点と高リスクの事項に限る**(標準 第3章 3.10.7)。事前レビュー期間で解決した事項を再度扱わない。議題が判定資料の未解決の論点の一覧に載っているかを照らす
9. **ラベルが付いていても、判定者は検査の結果などの事実を自ら確かめる**(標準 第3章 3.5.5 要求事項8)。ラベルを事実の代わりにしない。ラベルの遷移は判定の成立要件ではない

## 手順

### 1. ゲートを決め、補助ファイルを読む

`node scripts/gate/next.mjs` の出力に「読む:」があれば、その1枚を読みます。無ければ、利用者が指定したゲートを使います。

| ゲート | 補助ファイル | 判定者の席 |
| --- | --- | --- |
| G-1 企画承認 | `gates/G-1.md` | 事業決裁者 |
| G-2 要件合意 | `gates/G-2.md` | 価値責任者 |
| G-3 技術設計判断 | `gates/G-3.md` | 技術判断者 |
| G-4 機能仕様承認 | `gates/G-4.md` | 価値責任者(または委譲先) |
| G-5 自動検証(CI) | `gates/G-5.md` | 機械(人の判定記録は作らない) |
| G-6 独立レビュー | `gates/G-6.md` | 独立レビュア |
| G-7 出荷判定 | `gates/G-7.md` | 出荷判定者 |
| G-8 リリース決裁 | `gates/G-8.md` | 事業決裁者 |
| SG ステージ移行 | `gates/SG.md` | ステアリングコミッティ(会議体) |

所在は、このスキルのディレクトリ(`.claude/skills/gate/`)からの相対です。判定者の席の責任者は `node scripts/gate/next.mjs --role <ロール>` で確かめます。

### 2. ゲートが有効かを確かめる

```bash
node -e "const c=require('./process.config.json');for(const[k,g]of Object.entries(c.gates))console.log(k,g.state,g.label)"
```

`required` または `simplified` のゲートだけ記録を作ります。省略したゲートの記録は作りません。未達のゲートは、未達のまま表示されます。

### 3. 受け皿を決め、様式またはレビュー本文の雛形から起こす

受け皿は 2 つです(`reference/recording.md`「受け皿が承認レビューのゲート」)。

| 判定 | 受け皿 | 起こし方 |
| --- | --- | --- |
| 対象が PR として存在する判定(G-6。仕様・ADR が PR として存在する G-2・G-3・G-4) | 判定者本人のレビューの本文 | 補助ファイルの雛形(宣言行 + 確認した項目。G-6 は挙動要約)を判定者へ示す。判定者が PR の上で自分で書く |
| それ以外(G-1・G-7・G-8・SG、例外承認、停止の解除、対象が PR でない場合) | 様式 | 記録用ブランチ `records` の上で、下のコマンドで起こす |

様式の置き場は、記録用ブランチ `records` の `records/gates/<ゲート>-<対象>-<日付>.md` です(例: `records/gates/g7-v1.4.0-2026-10-30.md`)。`records` ブランチは履歴を持たない(orphan)ブランチで、様式のファイルは基底ブランチから `git show` で写します。

```bash
git fetch origin records && git checkout records          # 無ければ: git checkout --orphan records && git rm -rf --quiet .
git show origin/main:templates/04-gate-record.md > records/gates/<ゲート>-<対象>-<日付>.md
```

レビューで判定したゲート(G-2・G-3・G-4・G-6)では、様式を置きません。`next.mjs` と出荷の証跡の集約は、記録用ブランチの写し(`records/reviews/pr-<番号>.json`)と様式(`records/gates/`)を `scripts/gate/records.mjs` で読みます。

### 4. 材料を集めて、突合の表を起こす

補助ファイルの「材料の集め方」に従います。共通の欄(確定の形態、参照した D-0 の版、リスク区分、判定基準の表の展開)の書き方は `reference/recording.md` にあります。

- 機械が出してよい欄(判定者・判定日時・対象・参照した D-0 の版)は、PR の記録と基底ブランチの構成から埋め、出所を併記する
- 機械で確かめられる基準は、機械が確かめた範囲を書く(「空欄でないことだけを見た」など)
- **確認を求める項目の並びは、週ごとに入れ替える**(標準 第5章 5.7.5。同じ並びに慣れた確認の形骸化を遅らせる)。レビュー本文の雛形と判定記録の草案で確認を求める項目を並べるときは、項目を1行ずつ(続きの行は字下げ)`node scripts/gate/review-order.mjs --gate <ゲート> --target <PR-番号など> --risk <R1〜R3> --date <今日の日付>` の標準入力へ渡し、出た順で並べる。項目の文と番号は変わらず、見出しと機械が読む欄は動かさない。項目は箇条書き(`-`)か基準の名で書き、番号つきの一覧(`1.` `2.`)にしない(Markdown は番号を振り直して表示するため、入れ替えた並びが番号の順に見える)。隣り合う週で並びが同じにならないよう、同じになる週は機械が回転して変える。**回すのは並びだけで、表現・強調は回さない**(標準 5.7.5 の「表現・強調」は降ろしていない)。**R3 は回さない**。`/human-verify` の検証の順序は検証の論理であり、回さない。慣れが遅れる効果は機械で確かめない
- 人の判断が要る基準は、**材料だけを書き、結論を書かない**

### 5. 判定者へ渡す

判定者(人)が判定し、結果・差し戻し理由・記名を書きます。レビューが受け皿のゲートでは、判定者が PR の上でレビューを提出します(状態は問わない。作成者本人は COMMENT でよい)。差し戻しの理由は、**判定基準の項目番号**で書きます(「もう少し検討してください」は理由にならない)。差し戻しでは、**再提出の期限**もあわせて決め、差し戻し理由の欄(レビューでは宣言行)に書きます(標準 第4章「工程ゲートの判定の語彙」)。

### 6. 記録を書いてからラベルを動かす

順序は「判定基準との突合 → **記録の作成** → `state:*` ラベルの遷移 → Issue・PR の事務」です。逆にしません。記録の無いまま次工程へ渡っている状態を見つけたら、着手せず判定者へ差し戻します。

様式は、**判定者本人が記録用ブランチ `records` へ直接 push します**(`reference/recording.md`「様式の届け方」)。PR も、他者の承認も要りません。`records-signed.json` を適用する構成では署名コミット(`git commit -S`)で push します。基底ブランチへは、出荷判定(G-7)の PR(`ship-evidence.yml` が push する `ship/<日付>` から出荷判定者が開く)が `records/gates/` を `docs/gates/` へ複製して運びます。承認レビューの写しは、マージを契機にワークフロー `record-copy.yml` が `records` へ置きます。人は何もしません。

例外承認の台帳(`docs/debt-ledger.md`)の行と停止の申し立ての解除は、効力を持つ記録です。対象の PR の上の記名者本人のレビュー(宣言行 `例外承認: <行の ID>` / `停止の解除: 解除`)で裏づけます。対象が PR でない場合と認証情報を共有する体制では、記名者本人が作成者または承認者となる PR で基底ブランチへ先に入れます(`reference/recording.md`「効力を持つ記録の届け方」)。名前の一致だけでは数えません。担い手の名義を共有する体制(標準 第3章 3.5.3)では、記名者本人のアカウントの操作だけでは数えず、名義を共有していない人の帰属の確認を要します。

### 7. 次の一手を示す

```bash
node scripts/gate/next.mjs
```

「人の判断待ち」が出たら、コマンドを実行せず、待つ席へ受信箱のラベルで渡します。

## 四半期の抽出(標準 第5章 5.7.4)

判定記録の人が書く欄の記述は、四半期ごとに抽出して人が確かめます。四半期が締まった後に `node scripts/gate/content-sampling.mjs --quarter <YYYYQn>` を実行します。その四半期の締めの時点のコミットの木にあり、直前の四半期の締めの時点に無かった判定記録が母集団です(境界は UTC。締めの後に遅れて入った記録は次の四半期に入ります。締めの後の名前の変更や遡った記録は、コミットの日付を偽らない限り効きません)。記録用ブランチを取得できない環境と浅いクローンでは、数えずに失敗します。スクリプトは、母集団の一覧から導いた種で5件(母集団が5件以下なら全件。前の四半期に所見があれば10件)を選び、`docs/content-sampling/<YYYYQn>.md` を起こします。**種と抽出する記録を、人や AI が選び直しません**(`--seed` は照合にだけ使い、違えば拒否されます)。確かめるのは、抽出した記録の判定者以外の人です(体制の内が1名なら本人で、その旨を書く)。確かめた者と所見は人が書き、AI は書きません。**書いてから1回のコミットで入れます**。起こし直し・書き換えは履歴で検出され、済ませたことに数えられません。誤字の訂正は、別の訂正の記録(`docs/content-sampling/<YYYYQn>-訂正-<N>.md`。訂正する箇所・理由・記名)を足し、抽出の記録と抽出の結果は変えません。`--verify <YYYYQn>` で検証します。直前の四半期の記録が無いか、空欄があるか、検証を通らなければ、`/pit` が注記に出します。所見で判定を自動で取り消しません。当事者がリポジトリを支配している以上、機械だけでは選び直しを止められません。止めるのは、判定者以外の確かめる者です(標準の EV-0249)

## 期限を超えたとき

判定の期限(G-2・G-3・G-8 は48時間、G-4 は24時間、G-6 は応答1営業日・判定2営業日、G-7 は3営業日。標準 第4章の各ゲート。案件の値は D-0 の節5)を超えても、**自動承認にしません**。D-0 の節6 の行「ゲート判定・会議体の決定が期限を超過」の判定する者(様式に予め書いた者は体制と運用形態の決定者。期限を超えた者と同じ人のときは組織上の任命権者。B-1 など決裁権限規程が決定者を定める会議体は、規程の代決の定め)へ通知し、代理判定者の指名を求めます(標準 第4章 共通ルール 2、第7章 7.5)。期限を過ぎたことも記録に残します。

レビューの指名先を確保できないとき(同時保有の上限を超えた通知は `scripts/gate/review-queue.mjs` が出します)は、新しい判定依頼を作らず、起案者へ差し戻します(標準 第4章「レビュー SLA と滞留の措置」)。

## 旧名 /gate-record

`/gate-record` は、このスキルの旧名です。同じ手順で、ゲートを指定して使います。
