# SG ステージ移行ゲート(SG-0〜SG-2)

- 判定者: ステアリングコミッティ(会議体 B-2)。期限: 会議体の開催周期
- 判定基準の所在: 標準 第2章 2.4「ステージ移行ゲート」、会議体の語彙と期限は第3章 3.7、予算と中止の判断基準は第7章 7.7
- 依存先の一覧(単一障害点の一覧を含む)は、この判定の時に `node scripts/gate/aggregate-evidence.mjs` を実行して再生成する(第3章 3.12.11 要求事項5)
- 工程ゲート(G-1〜G-8)とは別の軸。問いは「投資を継続するか、次ステージへ進むか」

| ゲート | 判定の値 | 主な判定基準 |
| --- | --- | --- |
| SG-0 探索完了 | S1 へ移行 / 継続検証 / 中止 | 事業仮説が実証データで支持されている。技術的実現性が確認されている(実装スタックの確定を含む)。次ステージの投資規模と体制が示されている |
| SG-1 価値確立完了 | S2 へ移行 / 継続 / 中止 | 実利用者における価値が実証されている。拡大に耐えるアーキテクチャが確定している。受入部門が要求を自らの言葉で再構成できている |
| SG-2 スケール完了 | 定常運用へ移行 / 改善継続 | 対象利用者層の品質基準を満たしている。運用体制が定常運用として成立している。受容した負債の返却計画が承認されている |

## 材料の集め方

1. D-0 体制図(SG の提出対象)と、`node scripts/gate/check-d0.mjs` の結果。`check-d0.mjs` が次回レビュー期日の超過で失敗したら、SG の判定を始めない(標準 第2章 2.8)。体制図を見直してから判定する
2. 判定基準ごとに、実証データ・判断記録・技術負債台帳・運用引き継ぎ文書の所在を並べる。**実証データの評価を AI が書かない**
3. 次ステージの予算(第7章 7.7 の4区分)の案。予算は SG の判定と同時に確定する
4. 前提の台帳の、関係する前提の行
5. 企画書の「見積りの記録」と、総費用の内訳の「G-1 の時点の見積り」。判定記録の「見積りと実績の差」(当初の見積り・実績・差と主な原因)と「参照した企画書の版」を書く材料(標準 第7章 7.7.9)
6. SG-0 で実装スタックが確定していない場合は、そのことを示す(SG-0 の通過後に未確定が残ると未達)。SG-0 の判定基準を増やさない
7. 「継続」で次ステージのスコープ3層を確定するときの規模の記録(標準 第2章 2.10.2 の要求事項4〜6)。実測の主体(作業単位を完了させる組織。交代していれば「実測なし」)を含める。層ごとの作業単位の個数、1件の作業単位の定義、単位期間の長さ、完了の条件、根拠とした実測スループット、同じ期間に閉じたが完了に当たらない作業単位の個数、計画容量。判定記録へ書く。作業単位へ分けていない要求は SC-M に入れず SC-P に置く(第2章 2.10.1)。実測スループットの値を AI が見積もって埋めない
8. 必達基準2(標準 第7章 7.7.3)。**SG では必達基準2 を判定しない**(次ステージの計画の大きさは標準 第2章 2.10.1・2.10.2 が受け持つ)。ステージの途中で不合格(乙・丙)と判定されて未解消のものがあれば、SG の判定は 7.7.5 の回数に数えず、判定記録の「到達の見込み」の節の「7.7.5 の回数」の欄に書いて引き継ぐ。端の取り方を置き換えるなら企画書の中止条件に事業決裁者の記名で書き、次のステージの途中の判定から効かせる。実測を AI が見積もって埋めない

9. SG-0・SG-1 の実証は、**実在の顧客・利用者の観測から得たものに限る**。AI が顧客を模して生成した出力を、実証に数えない(標準 第2章、第6章 D-0、ADR-0091)
10. 事業ステージの移行に伴って担当部門が変わる場合(SG-1)は、移管記録を判定要件とする(標準 第2章 2.7)。完了条件は5つ: (1) 受入部門が事業意図と価値仮説を自らの言葉で再構成した文書がある (2) 移管元がその確認をし、解釈の相違が解消されている (3) 持ち越し事項が一覧化され、それぞれに期限と責任者がある (4) 恒久層のコンテキストに、移管対象の用語・制約・判断基準が登録されている (5) 移管後の結果責任者が指名され、担当表に記録されている。**条件1を文書の受領で代替しない**。移管記録の様式と検査は、テンプレートに無い。判定者が、記録の所在を判定記録の「確認した事項」に書く
11. 中止の判断の運用(標準 第7章 7.7.3): 判定を中止と継続の二者択一にしない。範囲を縮小して継続する選択肢と、条件付きで保留する選択肢を、常に併置する。丙のまま継続と判定するときは、SC-M・予算・期日のいずれかを同時に変える。7.7.9 要求事項11 の受容(見積りの幅の上側を下回る額)を、必達基準2 の判定の入力にしない

## 判定記録の書き方

- 様式は `templates/04-gate-record.md`。置き場は記録用ブランチ `records` の `records/gates/sg<N>-<案件>-<日付>.md`(判定者本人が直接 push する。`../reference/recording.md`「様式の届け方」)。基底ブランチの `docs/gates/` へは出荷判定(G-7)の PR が複製する
- **ステージを前へ戻す判定(前倒しで要る SG)の記録は、効力を持つ記録である**(標準 第4章「判定記録を基底ブランチへ入れる操作」)。記録用ブランチの経路を使わない。判定者本人が作成者または承認者となる PR で、基底ブランチの `docs/gates/` へ入れる(`../reference/recording.md`「効力を持つ記録の届け方」の後退経路)。出荷の PR の複製で入った記録は、PR を開いた者・転記を確かめた者が判定者でない限り、G-5 の `pr-rules` と出荷の証跡の集約が帰属を確かめられないとして数えない
- 判定の値は、工程ゲートの2値ではなく、上の表の値(会議体の語彙)
- 確定の形態は**人確定に限る**。決断の記録(確認していない事項を空欄・「なし」にしない)と、比較した選択肢(2案以上。採否の理由は人が書く)が必須
- **SG-0 の決断の記録**(標準 第2章 2.6): 「確認した事項」には、基準「技術的実現性が確認されている」について依った探索の記録を挙げ、所在(パス・URL・文書番号)を書く。所在の無い「確認した」は、依った記録へ到達できない。「確認していない事項」には、確認していない技術的な問いごとに移し先(S1 の機能仕様の前提の ID、または実装計画の検証のタスク `F-NNN / Task-N`)を書く。探索の記録の置き場と様式は標準が課していないので、様式を足さない。所在へ届くか、問いが移ったかは、会議体の決定者が確かめる(機械は確かめない)
- 判定者の欄には、会議体の決定を記録する責任者(人)を書く。AI を書かない

## ステージの変更を構成へ反映する

- 判定の後、ステージの変更は `/process-change`(種別 `axis`、軸B の回答)で反映する。補助ファイル: `.claude/skills/process-change/kinds/axis.md`
- **ステージを前へ戻す変更は、SG の判定記録を要する**。`sgRecord` に、基底ブランチの `docs/gates/` 配下の実在する判定記録を書く。D-0 表1「体制と運用形態」の決定者の記名も要する。SG の記録は、出荷の PR の複製の前か後かに依らず、記録だけの PR で基底ブランチへ先に入れる(判定者本人が作成者または承認者となる PR。`../reference/recording.md`「効力を持つ記録の届け方」の後退経路)。`/process-change` の変化点を入れる PR では、決定者本人が作成者か承認者になる(作成者なら、決定者以外の人が承認する)

## 機械の検査

- `/process-change` は、`sgRecord` が `docs/gates/` 配下の実在する記録を指さない入力を拒否する
- G-5 の `pr-rules`(検査 6b)は、`sgRecord` の記録を最後に変えた PR(同じ PR で足したならその PR)の作成者・承認者に判定者のアカウントが無ければ失敗させる。出荷の証跡の集約は、範囲の中の該当の変化点を記載の欠落にする(process-compass #428)
- 判定の内容(実証データの十分性など)を機械は判定しない
