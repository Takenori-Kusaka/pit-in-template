# G-6 独立レビュー

- 判定者の席: 独立レビュア。期限: 応答1営業日 / 判定2営業日
- 判定基準の所在: 標準 第4章「G-6 独立レビュー」(判定基準1〜5、独立した人の確認の4条件、委任の変更は判定の時点を事後へ移す、未達のまま出荷する場合の例外承認)。知識ベースの ID は `g-indep-review`
- 受信箱: PR が `state:dev-done` になったら判定する

## 材料の集め方

1. `/human-verify` で手がかりを集める(受入基準とテストの対応 → 外部インタフェース → 差分の性質 → 実行トレース → 疑義のある箇所の実装)。**結論・要約は生成させない**
2. G-5 の `pr-rules` が PR へ出す「既存のテストの変更」の一覧を読む。削除・期待値の変更の候補ごとに、受入基準の変更に対応しているか(テストの失敗をテストの変更で解消していないか)を確かめる。一覧は合否を決めない。理由の欄の記載も担保にしない(AI が埋められるため)
3. G-5 の `dependency-diff` の一覧があれば、追加・更新した依存が必要かを確かめる(基準5)
4. コア機能の変更では、判断記録(ADR)の添付を確かめる(基準3)
5. **確認する側は、作成側の説明文・主張・推論の過程を判断の前に読まない**(入力の分離)。PR の「検証方法と結果」は作成側の記載であり、挙動要約ではない

## 判定記録の書き方(挙動要約)

- 挙動要約は、**レビュア自身が自分の言葉で1〜2文**で書く(基準2)。承認レビューの本文か、判定記録の「挙動要約」の節(対象へ `PR #<番号>`)。**AI に生成させない**(禁止事項5)。要約の無い承認は差し戻し扱い
- 承認を「独立した人の確認」に数えるのは、次をすべて満たす場合だけ(出荷判定の証跡の集約が数える)
  1. 承認した者が、人の名簿(`people[].accounts[]`)の人へ対応づく
  2. その人が、作成を指示した者(PR 本文の欄。未記入なら PR の作成者と開発者の席の責任者)でない
  3. G-6 が未達の体制では、外部の確認者である
  4. 承認した者自身の挙動要約を伴う
- 承認はレビュアごとの最後の状態で数える。承認の後に同じ人が変更要求を出した場合、取り下げられた承認は数えない
- AI と bot の承認は数えない。AI の確認は検出の層であり、「AI レビュー通過」と書かない。指摘の内容と採否を残す

## 委任で先へ進めた変更を、人の判定と同じ語で記録しない

- G-6 の判定の時点を事後へ移すのは、**独立レビュアの席が委任で、その席の規則に該当し、PR のリスク区分が R3 と記録された変更だけ**。この変更は事前の承認の記録を持たない(「人の事前確認を経ていない変更」と呼ぶのはこの変更だけ)
- **このスキルで、その変更の G-6 の通過記録を作らない**。`delegation.yml` が PR へ残す「承認ではない」という記録を、G-6 の通過として写さない
- 独立レビュアの席の責任者が事後に抜き取った変更だけ、確定の形態を「委任」とした判定記録を作る(対象へ `PR #<番号>`)。作成を指示した者と別の人を置けず、責任者本人が抜き取った場合は、その旨を書く。委任の記録は独立した人の確認に数えない
- 開発者の席の規則にだけ該当する変更は、独立レビュアが人として事前に承認する。G-6 は通常の判定であり、上の4条件を満たせば独立した人の確認に数える。トレーラ `Delegated` は別に数える
- 規則に当たるかは機械が判定する。**AI の担い手が「委任の範囲だ」と自分で判定しない**(`node scripts/gate/verify-gate-contract.mjs --delegation --base origin/main`)。該当しない・判定できない変更は協働として人の判定へ渡す

## 独立した人の確認を経ないまま出荷する場合(例外承認)

- G-6 を適用する体制では、独立した人の確認を経ておらず、G-6 を事後へ移してもいない変更は、**リスク区分を問わず記録の欠落**。G-6 が未達の体制では、R1 の変更が例外承認を要する
- 例外承認は**変更ごと**に、技術負債台帳の区分「例外」の行として置く(対象 `PR #<番号>` / 状態 `未返却` / 承認した者は名簿の人で作成を指示した者でない / 内容・理由 / 期限と回収責任者)。書き方: `.claude/skills/artifact/artifacts/03-debt-ledger.md`
- 例外承認は人確定。AI は結論を起案しない。例外承認は未達を解消しない(表示と開示は残る)

## 機械の検査

- ブランチ保護(ルールセット `team.json` / `regulated.json`): 作成者本人の承認と、最後の push の後の承認の欠落を止める。作成者が AI・bot の変更で、指示した者が承認する形は止めない(G-7 の集約で止める)
- 出荷判定の証跡の集約(`aggregate-evidence`): 上の4条件、委任の識別、例外承認の行の対応づけ
- 名簿のアカウントの記載が正しいかは、機械で確かめない(内部監査)

## 安全関連ソフトウェアを含む変更

G-6 に加えて、独立した安全性の評価を重ねます(附属書F)。G-6 へ吸収しません。
