# G-2 要件合意

- 判定者の席: 価値責任者。期限: 48時間
- 判定基準の所在: 標準 第4章「G-2 要件合意」(判定基準1〜6、前提の欄(基準3)、未確定事項(基準6))。知識ベースの ID は `g-req-agree`
- 判定の対象: 機能仕様書 `specs/F-NNN/spec.md`(補助ファイル: `.claude/skills/artifact/artifacts/01-feature-spec.md`)
- 探索ステージ(S0)では G-4 に統合される。有効かは構成で確かめる(`/gate` の手順2)

## 材料の集め方

1. `node scripts/gate/spec-lint.mjs --gate G-2 specs/F-NNN` を実行し、出力を「機械が確認した項目」へ写す(基準2・基準6)。**未確定事項が1件でも残れば、判定を始めない**(基準6。失敗の出力に件数と行が出る)
2. 判定基準ごとに材料を並べる
   - 基準1: 受入基準が「条件 + 期待動作」になっているか。あわせて、企画書の観点3(受益者と価値)の価値のうち、受入基準へ対応するものが1件も無い項目の有無(**対応の有無だけ**。受入基準の内容は判定しない)
   - 基準2: spec-lint の結果
   - 基準3: 暗黙の前提が、案件層のコンテキスト(`context/projects/`)へ登録済みか。差分の所在。前提の表の各行に案件層の ID があるか(**対応の有無だけ**。前提の内容が正しいかは判定しない)。前提の欄に書かれたものは、すべて確かめていないものとして読む。「確かめた / 想定」の区別は求めない
   - 基準4: スコープ外(やらないこと)の欄
   - 基準5: 合意した範囲の、スコープの3層(SC-M・SC-P・SC-B)への割り当て。**割り当てが無いと G-4 の範囲の判定が成立しない**
   - 基準6: 未確定事項(`[NEEDS CLARIFICATION]`)の件数(手順1 の出力)。閉じ方は3つ(決めて本文に書く / 確かめて本文に書く / 前提として引き受け、前提の表へ移す)。責任者と期限を付けて残したまま通さない。残したまま進めるなら例外承認(標準 第7章 7.3)
3. 前提の欄の外に、確かめていない推測が事実として書かれていないかを、判定者が本文を読んで確かめる(仕様の本文の承認)
4. 前提の台帳の、関係する前提の行を示す

## 判定記録の書き方

- 対象: 機能 ID と、確定する受入基準の版のコミットの識別子を「/」で区切って書く(例: `F-012 / 1a2b3c4`。標準 第4章 G-2)
- 判定者は価値責任者(人)。受入基準の確定は、人が版を特定して記名する行為である。AI の名義で確定しない(標準 第4章 G-2、第5章 5.5.6)。草案を読まずに承認しないことが望ましい(標準 附属書E E.3 の推奨)
- 確定の形態: 席の運用形態とリスク区分による(`reference/recording.md`)
- 差し戻しは基準の項目番号で書く

## 機械の検査

```bash
node scripts/gate/spec-lint.mjs --gate G-2 specs/F-NNN   # 曖昧語(検出語の正本は標準 第4章 G-2 の表。--terms で一覧)と、未確定事項の件数
```

- `next.mjs` は、受入基準の表に記入済みの行が無い機能、spec-lint が失敗する機能、未確定事項の印が残る機能を、G-2 待ちより前の段階として出す
- 機械が数えるのは未確定事項の印の件数まで。閉じ方が3つのどれに当たるか、前提の内容が正しいかは判定しない
- 成果物の使いやすさ・学びやすさは判定基準にしない(ADR-0051)

## 判定に持ち込まないもの

- 実装計画やテストの未完成(G-4 以降)
- 技術的な実現方法の是非(G-3)
