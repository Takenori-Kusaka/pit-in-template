# G-2 要件合意

- 判定者の席: 価値責任者。期限: 48時間
- 判定基準の所在: 標準 第4章「G-2 要件合意」(判定基準1〜5)。知識ベースの ID は `g-req-agree`
- 判定の対象: 機能仕様書 `specs/F-NNN/spec.md`(補助ファイル: `.claude/skills/artifact/artifacts/01-feature-spec.md`)
- 探索ステージ(S0)では G-4 に統合される。有効かは構成で確かめる(`/gate` の手順2)

## 材料の集め方

1. `node scripts/gate/spec-lint.mjs specs/F-NNN` を実行し、出力を「機械が確認した項目」へ写す(基準2)
2. 判定基準ごとに材料を並べる
   - 基準1: 受入基準が「条件 + 期待動作」になっているか。あわせて、企画書の観点3(受益者と価値)の価値のうち、受入基準へ対応するものが1件も無い項目の有無(**対応の有無だけ**。受入基準の内容は判定しない)
   - 基準2: spec-lint の結果
   - 基準3: 暗黙の前提が、案件層のコンテキスト(`context/projects/`)へ登録済みか。差分の所在
   - 基準4: スコープ外(やらないこと)の欄
   - 基準5: 合意した範囲の、スコープの3層(SC-M・SC-P・SC-B)への割り当て。**割り当てが無いと G-4 の範囲の判定が成立しない**
3. 未確定事項(`[NEEDS CLARIFICATION]`)の残りを数える
4. 前提の台帳の、関係する前提の行を示す

## 判定記録の書き方

- 受け皿: 仕様が PR として存在する場合は、**判定者本人のレビューの本文**。1 行目に宣言行 `G-2: 通過` または `G-2: 差し戻し / 基準 N / 期限 YYYY-MM-DD`、続けて「確認した項目」を基準の項目番号で書く。状態は問わない(判定者が PR の作成者本人なら COMMENT で提出する)。雛形と条件は `reference/recording.md`「受け皿が承認レビューのゲート」。仕様が PR として存在しない場合は様式(後退経路)
- この承認を G-6 の独立した人の確認に数えない(受入基準の確定であり、別の人による確認ではない)
- 対象: 機能 ID と、確定する受入基準の版を「/」で区切って書く。版はコミットの識別子(例: `F-012 / 1a2b3c4`)または仕様の PR の番号(例: `F-012 / PR #34`。標準 第4章 G-2)。PR の番号で書いた場合、マージ後のコミットの識別子は機械が写しから併記する
- レビューで判定した場合、様式は置かない。`next.mjs` と出荷の証跡の集約は、記録用ブランチ `records` の写し(`records/reviews/pr-<番号>.json`)を読む。仕様が PR として存在しない場合の様式は、記録用ブランチの `records/gates/` へ判定者本人が push する(`reference/recording.md`「様式の届け方」)
- 判定者は価値責任者(人)。受入基準の確定は、人が版を特定して記名する行為である。AI の名義で確定しない(標準 第4章 G-2、第5章 5.5.6)。草案を読まずに承認しないことが望ましい(標準 附属書E E.3 の推奨)
- 確定の形態: 席の運用形態とリスク区分による(`reference/recording.md`)
- 差し戻しは基準の項目番号で書く

## 機械の検査

```bash
node scripts/gate/spec-lint.mjs specs/F-NNN   # 曖昧語(検出語の正本は標準 第4章 G-2 の表。--terms で一覧)
```

- `next.mjs` は、受入基準の表に記入済みの行が無い機能、spec-lint が失敗する機能を、G-2 待ちより前の段階として出す
- 成果物の使いやすさ・学びやすさは判定基準にしない(ADR-0051)

## 判定に持ち込まないもの

- 実装計画やテストの未完成(G-4 以降)
- 技術的な実現方法の是非(G-3)
