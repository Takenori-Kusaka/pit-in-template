# G-4 機能仕様承認

- 判定者の席: 価値責任者(または委譲先)。期限: 24時間
- 判定基準の所在: 標準 第4章「G-4 機能仕様承認」(前提条件1、判定基準1〜6、受入基準とタスクの対応(基準6)、範囲内外の判定を機械が行わない理由、範囲外と判定した場合)と「タスクの分割基準」。知識ベースの ID は `g-spec-cycle`
- 判定の対象: 機能仕様書 `specs/F-NNN/spec.md` と実装計画 `specs/F-NNN/plan.md`(補助ファイル: `.claude/skills/artifact/artifacts/01-feature-spec.md`・`07-implementation-plan.md`)
- どの事業ステージでも省略できない

## 材料の集め方

1. `node scripts/gate/spec-lint.mjs --gate G-4 specs/F-NNN` を実行する(前提条件1・基準1・6)。**未確定事項が1件でも残れば、判定を始めない**(前提条件1。G-2 の後に仕様を改めた場合を含む。提出者へ差し戻す)
2. 判定基準ごとに材料を並べる
   - 基準1: 受入基準の形式(G-2 と同じ形式の確認)
   - 基準2: 実装計画のタスクの表。各タスクが1つのレビュー単位か、どの受入基準に対応するか
   - 基準3: コア / 非コアの指定の欄
   - 基準4: 各タスクの規模の見込みと、構成の上限(`process.config.json` の `task`)。基準値を超える見込みのタスクは、関心事が1つであること(行数に合わせて細切れにしていないこと)を確かめる。超過は失敗にならず、PR の「規模の確認」と区分の下限 R2 で扱う(例外承認は要さない)。関心事が混ざっていれば分け直す
   - 基準5: スコープの層の判定欄(SC-M / SC-P / SC-B / 範囲外)。**空欄なら判定を始めない**。AI は判定の草案を示してよいが、記入は判定者
   - 基準6: どのタスクの「対応する受入基準」にも現れない受入基準の一覧(手順1 の出力。`next.mjs` の G-4 待ちの詳細にも出る)。**機械は合否を出さない。判定者が一覧を見て判定する**。除外の欄は無い(既存のテストで満たす受入基準も、そのテストを参照するタスクに現れる)。対応の内容と束ね方は基準6 で判定しない(束ね方は基準2・4)
3. 前提の台帳の、関係する前提の行を示す

## 判定記録の書き方

- 対象: 機能 ID と、確定した受入基準の版のコミットの識別子を「/」で区切って書く(例: `F-012 / 1a2b3c4`。標準 第4章 G-2)。`next.mjs` は「対象」に機能 ID を含む通過の記録を読んで、実装の段階へ進める
- **次工程の材料の未完成を差し戻し理由にしない**。例: テストが未作成であることは G-4 の理由にならない(G-4 は仕様と分解の承認であり、実装の完了を求めない)
- 範囲外と判定した場合は、内側のループを止めず、影響の範囲に応じて経路を分ける(第2章 2.10.8)
- 確定の形態: 席の運用形態とリスク区分による(`reference/recording.md`)
- 引き受けた前提: 探索ステージ(S0)で G-2 を統合している場合、未確定事項から前提として引き受けた行の案件層の ID を、判定者が判定記録の「引き受けた前提」に書く(G-2 と同じ。標準 第4章 G-2「未確定事項(前提条件1)」)

## 機械の検査

```bash
node scripts/gate/spec-lint.mjs --gate G-4 specs/F-NNN   # 曖昧語、未確定事項の件数(前提条件1)、どのタスクにも現れない受入基準(基準6)
node scripts/gate/next.mjs        # 受入基準・タスクの表の記入、未確定事項、G-4 の記録の有無から段階を出す
```

- G-4 の後の PR では、G-5 の `pr-rules` が、トレーラ `Spec:` の指す仕様とタスクの実在、変更規模の上限を検査する
- 出荷判定の証跡の集約は、トレーラ `Spec: F-NNN` を持つ変更について、その仕様の G-4 の通過の記録が無ければ欠落にする(禁止事項1 の事後の検出)
- 範囲の内外の判断そのものは機械に委ねない(記入の有無だけを見る)
