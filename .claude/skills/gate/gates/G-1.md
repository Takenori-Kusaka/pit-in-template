# G-1 企画承認

- 判定者の席: 事業決裁者。期限: 既存の稟議の運用どおり
- 判定基準の所在: 標準 第4章「G-1 企画承認」(前提条件1、判定基準1〜4)。知識ベースの ID は `g-plan-approval`(`scripts/vendor/tailoring-kb.json` の `gates`)
- 判定の対象: 企画書 `docs/project-brief.md`(補助ファイル: `.claude/skills/artifact/artifacts/06-project-brief.md`)

## 前提条件(満たさなければ審議を始めない)

- D-0 体制図が承認済み(承認者と承認日時の記録)。`node scripts/gate/check-d0.mjs` が通ること
- 安全リスクアセスメントの適用条件に該当する案件では、承認済みのテンプレ9(`docs/safety-risk-assessment.md`)
- 前提条件は機械で検査し、人の判断を介在させない。前提条件を判定基準に混ぜない(相殺されて通過するため)

## 材料の集め方

1. `node scripts/gate/check-d0.mjs` と `node scripts/gate/check-g1.mjs` を実行し、出力をそのまま記録の「機械が確認した項目」へ写す
2. 企画書の観点1(戦略整合)・観点2(自社が勝てる理由)が空欄なら、**基準1 の判定へ進まない**。審議の前に差し戻す
3. 判定基準ごとに、企画書の該当する欄の所在を表へ並べる
   - 基準1: 投資対効果の欄(算定根拠・参照した過去案件・効果が出ない条件の3欄)
   - 基準2: 事業リスクの表(区分・顕在化しうる時期・方針・判断者。AI 利用のリスクを1行以上)と、品質の約束と保証範囲の4欄(層2)。事業決裁者は層2 を層1(`docs/quality-assurance-policy.md`)の項目1・3 に照らして承認する。層1 が無ければ保証範囲の欄は「層1 なし」(判定は進めてよい。その案件の出荷は品質保証の対象外と出る)
   - 基準3: コンテキスト基盤の初期整備費(ゼロでないこと)
   - 基準4: 指標の閾値と予算の4区分
4. 前提の台帳(`docs/assumptions.md`)の、企画に関係する前提の行を示す(全ゲート共通の通過条件)。台帳が無ければ、判定者へ渡す前に作る(`/artifact 10`。前提の定義と観測の手がかりは補助ファイルにある)。作れないまま判定を進めるなら、ゲートの判定を対象とする例外承認(台帳の「対象」に `G-1 <案件 ID>`)を人が決める(`../reference/exception-paths.md`)

## 判定記録の書き方

- 対象: 案件 ID(例: `P-001`)
- 確定の形態: 事業決裁者が選ぶ。投資の判断は人確定が通常
- 投資対効果が事業基準を満たすかは、社内基準との突合で事業決裁者が判定する。**AI は結論を書かない**
- 差し戻しは基準の項目番号で書く

## 機械の検査

```bash
node scripts/gate/check-d0.mjs    # 前提条件(D-0 の承認・見直し期日・生成区間)
node scripts/gate/check-g1.mjs    # 観点1・2 の空欄、層2 の4欄と AI の利用の3行の空欄、frontmatter、TBD / 未定 / ???
```

- `gate-entry` ワークフローも D-0 の前提条件を検査する
- 記述の内容の妥当性は機械が判定しない(第5章 5.7.4)

## 判定に持ち込まないもの

- 実装スタックの確定(SG-0 で扱う。G-1 の判定基準は実装スタックを含まない)
- 機能仕様の未完成(G-2 以降で扱う)
