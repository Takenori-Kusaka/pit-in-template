# G-7 出荷判定

- 判定者の席: 出荷判定者。期限: 3営業日
- 判定基準の所在: 標準 第4章「G-7 出荷判定」(判定基準1〜9、保証の開示、出荷判定者の署名の意味、未消化が残る場合、数値の十分性を判定させない)。知識ベースの ID は `g-ship`
- 判定の対象: 当該出荷の範囲の記録と、保証の開示

## 材料の集め方

1. 運用引き継ぎ文書 `docs/handover.md` があるか確かめる。無ければ先に `/artifact 05`(基準4)。集約の基準4 の行で、3項目(監視項目・障害時の連絡先・復旧手順)の未記入・置き場なしを確かめ、3項目の内容(閾値・連絡先へ届くか・切り戻しの実績)を読んで完備を判定する。機械は記入が在るかまでしか見ず、記入が在ることは完備を意味しない。基準3 の記録漏れ(台帳に無い妥協)は、機械が台帳の有無しか見ないため、出荷判定者が PR のチェック項目「受容した妥協・仮実装を技術負債台帳へ記録した」と台帳を突合する
2. 証跡を集約する。起点は前回のタグ、終点は今回の範囲。集約は記録用ブランチ `records` の様式(`records/gates/`)と写し(`records/reviews/`)を読むため、手元では先に `git fetch origin records:records` で取り込む

```bash
git fetch origin records:records
node scripts/gate/aggregate-evidence.mjs --from <前回のタグ> --to <終点> --exception-day <判定の日 YYYY-MM-DD>
```

`--exception-day` には判定の日(今日)を渡す。例外承認の回収の期限(第7章 7.3)は、この日と比べる。渡さないと範囲の終点のコミットの日で比べ、終点を切ってから判定までの間に期限を過ぎた行を見逃す。品質レポートの件数の句に、突合の日とその出どころが出る。`ship-evidence` ワークフローが渡すのは実行の日(UTC)であり、判定の日ではない。判定の日に流し直すか、手元で `--exception-day` を渡す

3. 出力(`evidence/evidence.json`・`evidence/quality-report.md`・`evidence/assurance-disclosure.external.md`)の「欠落」を読む。**欠落があれば、判定へ進む前に埋める**(欠落を判定記録で覆わない)
   - 基準5 の突合は、様式と写しのいずれかを変更ごとに引く。どちらも無い変更は欠落。写しの件数が出荷の範囲の変更の件数と一致しなければ欠落。写しが記録用ブランチに無い(`record-copy.yml` が失敗した)変更も欠落
   - gate-g5 の成功を持たない PR(結果の記録が無い PR を含む)は欠落。ブランチ保護が適用されていない、または使えない場合の事後の検出である
   - G-6 を適用する体制で、独立した人の確認を経ていない変更(G-6 を事後へ移した変更を除く)は欠落。例外承認の行が対応づけば欠落にしない(`gates/G-6.md`)
   - トレーラ `Spec: F-NNN` を持つ変更で、その仕様の G-4 の通過の記録が無いものは欠落
   - 確定した版の再確認で「未確認」の機能(品質レポートの「確定した版の再確認」の一覧)は欠落に数えられない。機能ごとに、一覧の判定記録の版と範囲の先端の `specs/F-NNN/spec.md` の受入基準・前提・スコープ外を突合する。通過の記録が無い機能(理由に「トレーラ Spec がこの機能を指す場合に限り」とあるもの)は、変更を対象とする G-4 の判定が要るかを確かめる
   - 宣言と実態のずれ(品質レポートの「宣言と実態のずれ」。人数・担い手の識別)は警告で、欠落に数えられない。出荷判定者は、ずれごとに体制の変化点(`/process-change`)の起票があるかを確かめる。機械は起票せず、起票されたかも確かめない
   - PR を経ないコミットで、トレーラ `Risk`・`Verification` が無いものは欠落(記録だけのコミットを除く)
   - 改訂前の D-0 を参照した新しい判定記録、当該出荷の範囲の判定記録が1件も無い状態は欠落
   - 組織継続の状態の受容(D-0 節15)の期限切れ(状態が解消していないもの)、成立しない停止の申し立ての解除の記録は欠落
   - D-0 節7 の有事の決定者(4事象 × 3決定)の空欄、企画書の識別子(QC-NN)を持たない壊してはならない品質条件、欠陥の台帳(`docs/defect-ledger.md`)が無いことは欠落
   - **出荷の範囲の PR(またはリリース)に未解除の停止の申し立てがあれば、集約が失敗する(保留)**。保留を解くのは解除の記録だけで、G-7 の署名と G-8 の受容は解かない。保留は差し戻しではない。判定記録を作らない
4. 基準1・2 は集約の「G-7 の基準ごとの確認範囲」の行を読む。基準1 は受入基準(F-NNN/AC-N)を参照するテストの数・実行して通過した数(`evidence/test-results.json`)・対応するテストの無い受入基準の数、基準2 は欠陥の台帳の事業ステージ別の区分ごとの未解決の件数。**件数の十分性と出荷の可否は機械が判定しない**。出荷判定者がトリアージ基準と突合する
5. 未消化のテストがある場合は、未消化を生じさせた側が、理由・実施した代替・**残存リスク**を判定記録の「未消化のテスト」の節へ書く(出荷判定者に書かせない)

## 判定記録の書き方

- 対象: 出荷の範囲(例: `v1.3.0..v1.4.0`)
- 置き場: 記録用ブランチ `records` の `records/gates/g7-<終点>-<日付>.md`。出荷判定者本人が直接 push する(`reference/recording.md`「様式の届け方」)
- **G-7 は記録と基準の突合に限る**。再テスト・再レビューを始めない。突合で疑義が出た箇所だけ確かめる
- 数値(カバレッジなど)を合格の根拠として書かない。書くのは、どの検査が実施され、どの記録が揃っているか。数値の十分性は G-1 と G-5 で終えている
- 保証の開示の7項目に記載の欠落が無いかを突合する(基準9)。「未測定」「記録なし」は値として受け入れる。**値の良否で差し戻さない**
- 保証の主張の成立判定(第4章 G-7。突合は2点だけ。署名の意味は変えない): (a) 開示に「保証の主張の成立判定」の出力があること (b) 層1 の「受容しない条件」に当たる事実が開示に無いこと。成立条件4 は、G-7 を記名する人が、範囲内の変更の作成を指示した者でも、G-6 の承認者でも、開発者の席・独立レビュアの席の責任者でもないことを見る(当たると、その出荷は品質保証の対象外になる。出荷は止まらない)。機械が照合した条件は出力の「受容しない条件」の行、印の無い条件は出荷判定者が開示と突合する。**当たる事実があれば差し戻す**(G-8 で受容できないため)。成立した件数が十分かは判定しない
- 基準6(AI 品質指標。標準 第4章 G-7「AI 品質指標の扱い」): 確かめるのは2つ。(1) G-1 の判定記録に、AI 品質指標の閾値が記録されていること。(2) AI 品質指標の比率を合否に用いていないこと。材料に比率を示す場合は傾向として示されていること。結果は判定記録の「チェックリスト突合」の基準6 の行に書き、根拠の所在を備考に書く。**値の良否は判定しない**。機械は欠落を数えない
- 基準7(安全関連ソフトウェアのみ。標準 第4章 G-7、附属書F F.7): 適用は、D-0 表10 の附属書F F.2 の回答が「はい」の案件、または安全重要度が CL2・CL3 の案件。どちらも人が記名した記録を読む。食い違い(CL1 以下で F.2 が「はい」、CL2 以上で「いいえ」)は適用ありとして扱い、備考に書く。適用があれば、F.7 の記録(安全関連部の切り分け・適用規格と安全度水準・適用した手法・故障挿入の結果・AI の利用・独立した評価)の6項目に欠落が無いかを、出荷判定者が読んで判定する。内容の妥当性は機械で閉じない。基準7 を例外承認で外した場合は、7.3 に従う(`../reference/exception-paths.md`)
- 基準8(知財潔白性。標準 第4章 G-7「知財潔白性」): 次を読んで判定する。(1) 依存関係のライセンス検査の結果。(2) 類似の検知の実施記録: 用いた手段・対象の範囲・実施日・結果(一致の件数と処置)の4事項。実施していない出荷は基準8 を満たさず、先へ進めるには例外承認による(「使用せず」と理由を書くだけでは通らない)。(3) 技術負債台帳の区分「類似検知」の行(技術負債台帳の様式)。期限を超過した未返却の行が残る間は出荷を止める。延長は例外承認の新しい行で受ける(`../reference/exception-paths.md`)。**検知の結果で出荷を止める判定はしない**(処理の完了か、期限つきの記録かを見る)。**案件の判定者に、検知が権利侵害に当たるかの法的評価を求めない**。確かめるのは、定めた措置を採ったかだけである
- 変異(ミューテーション)の一覧は、G-7 の証跡に集約されるが、**出荷判定者に読解を求めない**。差し戻しの判断は G-5 と G-6 で終える。一覧は、検査が実施された事実を示す材料にとどまる
- 契約への組み込みの類型(標準 第6章 テンプレ8): 出荷判定では**是正計画型と開示義務型**を基本とする。品質に関する比率指標を、金銭措置の条件にしない(金銭措置型は、稼働率など客観的に観測できる量に限る)
- 品質の軸(第8章 軸C)が「高」の案件の出荷判定には、記録の突合に加えて、限定的な抜き取り確認を行う。抜き取る範囲と件数は判定者が決め、判定記録の備考に書く。標準は件数を定めない
- 署名の意味: 事前に定めた出荷基準を満たしていることと、定めた検証の記録と成立しなかった統制の一覧が揃っていることの確認。**成果物の正しさの承認ではない**。対外文書へ品質の保証として書かない
- 異議は G-7 の記録に書かない(G-8 の決断の記録に、出荷判定者が書く。`gates/G-8.md`)

## 機械の検査

```bash
node scripts/gate/aggregate-evidence.mjs --from <起点> --to <終点> --exception-day <判定の日>   # 欠落があれば失敗する
```

- `ship-evidence` ワークフローが同じ集約を実行する(タグの push、または手動実行で起点と終点を指定)
- 委任で先へ進めた変更は、出荷ごとでなく期間ごとの保証の開示で扱う(`--period-from` / `--period-to`、ワークフロー `assurance-period`)

## 判定記録と写しを基底ブランチへ入れる(出荷の PR)

- `ship-evidence` が集約の後に、出荷のブランチ `ship/<日付>` を push し、題名と本文を入力済みの PR を開く URL を実行の要約と成果物 `ship-pr` に出す。**PR を開くのは出荷判定者(人)**。中身は、`records/reviews/*.json` → `docs/records/reviews/`、`records/gates/*.md` → `docs/gates/` の複製(追加だけ。既存のファイルは上書きしない)と、品質レポート `docs/evidence/<日付>-<範囲>.md`、証跡の一式(`evidence.json`・外へ渡す開示・取り込んだ入力の JSON)と digest の一覧(`manifest.json`)の写し `docs/evidence/<日付>-<範囲>/`。**写しは保管期間の充足を示さない**。保管期間の値は採用者が定める。リポジトリの外へ引き渡すときは、digest の一覧を照合に使える(引き渡しは求めない)。成果物 `ship-evidence` は保持の日数を明示せずリポジトリの設定に従う一時置きで、保管ではない。**一式を持たない、この変更より前の出荷の PR は、verify_pr で再検査すると「一式の欠け」で失敗する**。再検査しない。再検査や追加の確認が要るときは、`ship-evidence` を再実行して新しい出荷の PR を作る(検査を緩める分岐は持たない)
- 出荷の PR は、開いた人以外の人が承認する(GitHub では PR の作成者は自分の PR を承認できない)。この承認は**転記の確認**であり、判定ではない。承認者は、PR の上の `ship-evidence` の verify(複製が記録用ブランチと一致することの検査)の結果を確かめる。G-7 の判定は `records/gates/` の様式で成立している
- PR の上で CI(`ship-evidence` の verify ジョブ)が同じ集約を再実行し、複製が記録用ブランチと一致することを検査する(JSON は id・commit_id・submitted_at・user.id・body、md は内容)。不一致は失敗。人が書き換えた写しは欠落
- 人が開いた PR では gate-g5 と verify が自動で起動する(`GITHUB_TOKEN` は既定の設定で PR を作れず、作れる設定でも `GITHUB_TOKEN` で開いた PR は両方を起動しない。2026-10-24 の実機確認)。再検査だけなら `ship-evidence` の手動実行(`verify_pr` に PR の番号)
- G-7 の判定記録は出荷の PR より前に `records/gates/` へ置く(出荷の PR がそれを運ぶ)。PR のマージの後に G-8 の記録を書き、集約をもう一度実行する(`gates/G-8.md`)

## 出荷できない状態

構成に `shipBlocked` が立っている間(1〜2名で CL1 以上・規制業など)は、集約が失敗します。解消は体制を確保する変化点(`/process-change`)で、どの選択肢を採るかは人が決めます。
