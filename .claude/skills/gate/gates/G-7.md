# G-7 出荷判定

- 判定者の席: 出荷判定者。期限: 3営業日
- 判定基準の所在: 標準 第4章「G-7 出荷判定」(判定基準1〜9、保証の開示、出荷判定者の署名の意味、未消化が残る場合、数値の十分性を判定させない)。知識ベースの ID は `g-ship`
- 判定の対象: 当該出荷の範囲の記録と、保証の開示

## 材料の集め方

1. 運用引き継ぎ文書 `docs/handover.md` があるか確かめる。無ければ先に `/artifact 05`(基準4)
2. 証跡を集約する。起点は前回のタグ、終点は今回の範囲

```bash
node scripts/gate/aggregate-evidence.mjs --from <前回のタグ> --to <終点>
```

3. 出力(`evidence/evidence.json`・`evidence/quality-report.md`・`evidence/assurance-disclosure.external.md`)の「欠落」を読む。**欠落があれば、判定へ進む前に埋める**(欠落を判定記録で覆わない)
   - gate-g5 の成功を持たない PR(結果の記録が無い PR を含む)は欠落。ブランチ保護が適用されていない、または使えない場合の事後の検出である
   - G-6 を適用する体制で、独立した人の確認を経ていない変更(G-6 を事後へ移した変更を除く)は欠落。例外承認の行が対応づけば欠落にしない(`gates/G-6.md`)
   - トレーラ `Spec: F-NNN` を持つ変更で、その仕様の G-4 の通過の記録が無いものは欠落
   - PR を経ないコミットで、トレーラ `Risk`・`Verification` が無いものは欠落(記録だけのコミットを除く)
   - 改訂前の D-0 を参照した新しい判定記録、当該出荷の範囲の判定記録が1件も無い状態は欠落
4. 未消化のテストがある場合は、未消化を生じさせた側が、理由・実施した代替・**残存リスク**を判定記録の「未消化のテスト」の節へ書く(出荷判定者に書かせない)

## 判定記録の書き方

- 対象: 出荷の範囲(例: `v1.3.0..v1.4.0`)
- **G-7 は記録と基準の突合に限る**。再テスト・再レビューを始めない。突合で疑義が出た箇所だけ確かめる
- 数値(カバレッジなど)を合格の根拠として書かない。書くのは、どの検査が実施され、どの記録が揃っているか。数値の十分性は G-1 と G-5 で終えている
- 保証の開示の7項目に記載の欠落が無いかを突合する(基準9)。「未測定」「記録なし」は値として受け入れる。**値の良否で差し戻さない**
- 署名の意味: 事前に定めた出荷基準を満たしていることと、定めた検証の記録と成立しなかった統制の一覧が揃っていることの確認。**成果物の正しさの承認ではない**。対外文書へ品質の保証として書かない
- 異議は G-7 の記録に書かない(G-8 の決断の記録に、出荷判定者が書く。`gates/G-8.md`)

## 機械の検査

```bash
node scripts/gate/aggregate-evidence.mjs --from <起点> --to <終点>   # 欠落があれば失敗する
```

- `ship-evidence` ワークフローが同じ集約を実行する(手動実行で起点と終点を指定できる)
- 委任で先へ進めた変更は、出荷ごとでなく期間ごとの保証の開示で扱う(`--period-from` / `--period-to`、ワークフロー `assurance-period`)

## 出荷できない状態

構成に `shipBlocked` が立っている間(1〜2名で CL1 以上・規制業など)は、集約が失敗します。解消は体制を確保する変化点(`/process-change`)で、どの選択肢を採るかは人が決めます。
