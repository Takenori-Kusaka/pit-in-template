# 機能仕様を書く

**完了の条件を曖昧さなく書けない機能は、書けるところまで分解してから実装へ渡します**。エージェントが停滞する原因には、能力の不足のほかに、完了条件の不在があります(標準 附属書E E.3。測定に基づく記述ではありません)。

## 手順

### 1. 機能 ID を決める

`specs/` を見て、次の連番を採ります。`F-001` から始めます。ファイルは `specs/F-NNN/spec.md`。

### 2. テンプレートから起こす

`templates/01-feature-spec.md` を写します。

### 3. 受入基準を EARS 記法で書く

型の名前とひな形の正本は、標準 附属書B(規定)です。

| 型 | ひな形 | 使う場面 |
| --- | --- | --- |
| 常時(Ubiquitous) | システムは、常に〈動作〉すること | 無条件で成り立つ性質 |
| イベント駆動(Event-driven) | 〈トリガー〉のとき、システムは〈動作〉すること | 契機がある |
| 状態駆動(State-driven) | 〈状態〉の間、システムは〈動作〉すること | 状態に依存する |
| 望まない挙動(Unwanted) | もし〈異常条件〉なら、システムは〈防御動作〉すること | 異常系 |
| 機能限定(Optional) | 〈機能・構成〉を備える場合、システムは〈動作〉すること | 構成で変わる |

### 4. 曖昧語を排除する

受入基準に、合否を一意に判定できない表現は使えません(標準 第4章 G-2 基準2)。類は3つです。逃げ道になる句、程度を定めない副詞・形容詞、末尾を開いた列挙です。

CI の `spec-lint` は、標準 第4章 G-2 の検出語を受入基準の節から検出し、G-5 を失敗させます。検出語の一覧は `node scripts/gate/spec-lint.mjs --terms` で出します。検出語に無い語でも、類に当たる表現は G-2 で差し戻されます。

「適切にエラーを表示する」は基準になりません。「もし入力が空なら、システムは項目名を含むエラーメッセージを当該項目の直下に表示すること」なら基準になります。

### 5. スコープ外を書く

**書かれていない事項は、実装されるか否かが不定になります**。やらないことを明記してください。

### 6. 検証する

```bash
node scripts/gate/spec-lint.mjs   # 引数なし = CI と同じ範囲(機能仕様の置き場 specs/F-NNN/)
```

### 7. 次の一手を示す

```bash
node scripts/gate/next.mjs
```

出力された次の一手を利用者へ示します。「人の判断待ち」が出たら、コマンドを実行せず、待つ席へ受信箱のラベルで渡します。

## 草案を AI に書かせてよいか

書かせてよいです。受入基準の確定は、人が版を特定して判定記録へ記名する行為です(標準 第4章 G-2)。AI の名義で確定しません。草案を読まずに承認しないことが望ましいです(標準 附属書E E.3 の推奨)。

草案を出したあと、利用者へ次の1問を示します。標準 附属書B「草案を受け取ったときに確かめること」の推奨です。

- この基準をすべて満たしても、作りたかったものにならない場合はないか

そういう場合が見つかったら、基準を足すか、書き直します。暗黙の前提とスコープ外の事項は、問いとして足さず、G-2 の基準3・基準4 で確かめます。

## 完了の条件

- [ ] 受入基準ごとに「条件 + 期待動作」が書けている
- [ ] 曖昧語がない(`spec-lint` が通る)
- [ ] スコープ外が書かれている
- [ ] 価値責任者が承認した(G-2 / G-4)
