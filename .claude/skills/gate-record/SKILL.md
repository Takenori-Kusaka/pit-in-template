# ゲート判定を記録する

## 記録するもの

`process.config.json` で `required` または `simplified` になっているゲートすべてです。省略したゲートの記録は作りません。

## 判定の原則

1. **記録をもって判定が成立する**:
   ゲート判定は、**この判定記録ファイルを作成しレポジトリにコミットした時点で初めて公式に成立（通過/差し戻し）**します。Issue や PR の操作は単なる事務手続きです。記録が未作成の期間は「未判定（保留）」扱いとなります。
2. **判定に持ち込んではならないもの**:
   - **次工程の材料の未完成**: 例として、「Devのテストコードが未作成だから」という理由で G-4（機能仕様承認）を差し戻してはなりません。G-4 の目的は「仕様とタスク分解の承認」であり、実装が完了していることは要求されません。
   - **当該ゲートの判定基準に無関係な項目**: 属人的な好みや、該当ゲート의チェックリストにない項目を差し戻し理由にしないでください。
3. **全ゲート共通の通過条件**:
   当該の工程に関係する前提の充足状態が「前提台帳（assumptions.md）」に記録されており、AC-1（リスクあり）以上のものについて受容の決裁が取られていることを全ゲートで必ずチェックします。

## 手順

### 1. 有効なゲートを確認する

```bash
node -e "const c=require('./process.config.json');for(const[k,g]of Object.entries(c.gates))console.log(k,g.state,g.label)"
```

### 2. テンプレートから起こす

`templates/04-gate-record.md` を `docs/gates/<ゲート>-<対象>-<日付>.md` として写します。

例: `docs/gates/g4-F-012-2026-08-08.md`

### 3. 埋める

| 欄 | 内容 |
| --- | --- |
| ゲート | G-1〜G-8 |
| 対象 | 案件 ID / 機能 ID / タグ |
| 判定者 | **1人**。合議体にしない |
| 判定日時 | |
| 結果 | 通過 / 差し戻し |
| 確定の形態 | 人確定 / 協働 / 委任 のいずれか1つ。下の「確定の形態を記録する」による |
| 参照した D-0 の版 | 判定の時点の `docs/D-0-governance.md` の `version`。`process.config.json` の `d0Version` と一致していること |
| 変更のリスク区分 / リスク区分を確定した者 | 変更を対象とする判定でだけ書く。確定した者は人が記名する。**AI が自分の名義を書かない**。起案者の自己記載のままなら「自己記載」 |
| 差し戻し理由 | チェックリストの項目番号で示す |
| 確認した項目 | 判定基準のチェックボックス |

#### 確定の形態を記録する

判定者の席の運用形態(`process.config.json` の `seats[].mode`)と、その変更のリスク区分で決まります。**席の宣言は上限です**。変更ごとのリスク区分の判定がそれを下げます。

| 確定の形態 | 書く場面 |
| --- | --- |
| 人確定 | 人が判断し、理由を自分で書いた。**R1 の決定と例外承認は、席の宣言にかかわらず人確定**。G-8 とステージ移行の判断も同じ |
| 協働 | AI が起案した判断の案と根拠を、人が変更ごとに確認して確定した |
| 委任 | 登録した範囲で先へ進めた変更を、独立レビュアの席の責任者が**事後の抜き取りで確かめた記録**。作成を指示した者と別の人を置けず、責任者本人が抜き取った場合は、その旨を書く |

- どの形態でも、判定者の欄には席の責任者(人)を書く。**AI を判定者に書かない。AI の確認を判定として記録しない**
- 協働で確定した判定でも、挙動要約と判定の記名は人が行う。AI が起案した文面を、人の要約として残さない
- この欄を、エージェントが判定者に代わって埋めない。形態は判定者が選ぶ

#### 委任で先へ進めた変更を、人の判定と同じ語で記録しない

G-6 の判定を事後の抜き取りへ移した変更(独立レビュアの席の委任に当たり、R3 と記録された変更)は、**事前の承認の記録を持ちません**。「人の事前確認を経ていない変更」と呼ぶのは、この変更だけです。このスキルで、その変更の G-6 の通過記録を作ってはなりません。開発者の席だけの委任の変更は、独立レビュアの事前の承認の記録を持ちます(下記)。

| すること | しないこと |
| --- | --- |
| コミットのトレーラ `Delegated: <規則ID>` で、委任の変更を変更単位で識別する | 「承認」「通過」「独立レビュー済み」と記録する |
| 独立レビュアの席の責任者が事後に抜き取った変更について、確定の形態を「委任」とした判定記録を作る(「対象」へ `PR #<番号>`) | 抜き取られていない変更に判定記録を作る |
| AI の確認の結果は、指摘の内容と採否を残す | 「AI レビュー通過」と書く |

規則に当たるかどうかは、機械が判定します。**エージェントが「これは委任の範囲だ」と自分で判定してはなりません**。

```bash
node scripts/gate/verify-gate-contract.mjs --delegation --base origin/main
```

該当した場合に限り、表示された規則 ID をトレーラへ書きます。該当しない変更、判定できない変更は、協働として人の判定へ渡します。出荷判定の証跡の集約(`aggregate-evidence`)も、トレーラの規則 ID と変更したファイルを `delegation.rules` に照合し、範囲を外れた変更を欠落として扱います。

PR を出した後は、ワークフロー(`delegation.yml`)が、既定ブランチの構成と規則で該当を判定します(`scripts/gate/check-delegation.mjs`)。組織がマージの実行を有効化している場合、該当した変更は G-6 の判定を事後へ移して先へ進み、PR へ「人の事前確認を経ていない変更(G-6 の判定を事後の抜き取りへ移した変更)として、規則 <ID> により先へ進めた。承認ではない」と記録されます。**この記録を、G-6 の通過記録として写さないでください**。証跡の集約は、この経路で先へ進めた変更を、人の事前確認を経ていない変更に数え続けます。確定の形態が「委任」の G-6 の記録(事後の抜き取り)も、独立した人の確認には数えません。抜き取った変更の一覧として出します。独立レビュアの席の規則だけに当たる変更(開発者の席はこの変更について協働)は、開発者の席の責任者(人)の承認があるときだけマージされます。

開発者の席の規則にだけ該当する変更は、扱いが違います。独立レビュアが人として事前に承認するため、G-6 は通常の判定です。下表の条件を満たせば「独立した人の確認あり」に数えます。トレーラ `Delegated` は、変更ごとの検証を担い手へ委ねたことの識別として、別に数えます。独立した人の事前の承認が無い委任の変更は、「G-6 を事後へ移した変更」と「それ以外(独立した人の確認を経ていない変更)」に分けて表示されます。後者は、独立レビューを適用する体制では欠落です。

#### 独立レビュー(G-6)の記録で、証跡の集約が読むもの

出荷判定の証跡の集約は、承認を次の条件で「独立した人の確認」に数えます(標準 第4章 G-6 の4条件)。満たさない承認は、未確認の件数へ入ります。**独立レビュー(G-6)を適用する体制では、独立した人の確認を経ておらず、G-6 を事後へ移した変更でもない変更は、記録の欠落です**(例外承認の記録が対応づく変更を除く。リスク区分を問わない)。G-6 が未達の体制では、件数として開示します。

| 集約が読むもの | 置き場 | 無い場合 |
| --- | --- | --- |
| 承認した人 | 承認したアカウントを、人の名簿(`people[].accounts[]`)で人へ対応づける | 「承認者を名簿と対応づけられない」として未確認に数える |
| 作成を指示した者 | PR 本文の欄「作成を指示した者」 | PR の作成者(人のアカウントの場合)と、開発者の席の責任者を指示者とみなす |
| レビュアの挙動要約(G-6 基準2) | 承認レビューの本文。または、承認した人が判定者の G-6 の判定記録の「挙動要約」の節(記録の「対象」へ `PR #<番号>` を書く) | **その承認を数えない**(`no-reviewer-summary`)。要約を伴わない承認は差し戻し扱いである |
| 承認の状態 | レビュアごとの最後の状態。承認の後に同じ人が変更要求を出した場合、取り下げられた承認は数えない | — |
| G-6 の判定記録による確認 | PR の承認が無い変更、PR を経ていないコミットでも、G-6 の判定記録(「対象」に `PR #<番号>` またはコミットの識別子、判定者、結果が通過、挙動要約)があれば、同じ条件で数える。確定の形態が「委任」の記録は数えない | — |

- 承認した人が、作成を指示した者に含まれる場合は数えません。2人で指示した変更は、その2人の承認では成立しません(標準 第3章 3.5)
- PR 本文の「検証方法と結果」は作成側の記載であり、レビュアの挙動要約ではありません。集約は、2つを別々に数えます
- 名簿のアカウントの記載が正しいかは、機械で確かめません。内部監査で確かめます
- 承認した人が独立レビュアの席の責任者かどうかは、件数として別に表示します(欠落にはしません)

#### 独立した人の確認を経ないまま出荷する場合(例外承認)

**変更ごとに、例外承認(標準 第7章 7.3)の記録を要します**。対象は、G-6 を適用する体制では独立した人の確認を経ていない変更(G-6 を事後へ移した変更を除く。リスク区分を問わない)、G-6 が未達の体制では R1 の変更です。記録が対応づかなければ、証跡の集約は欠落として失敗します。対応づいた変更は、未回収の例外として保証の開示の項目5 へ載ります。

記録の置き場は、技術負債台帳(`docs/debt-ledger.md`)の区分「例外」の行だけです。次をすべて満たす行が対応づきます。

| 欄 | 書くこと |
| --- | --- |
| 対象 | `PR #<番号>`、またはコミットの識別子(先頭7桁以上)。**内容や他の欄に番号を書くだけでは対応づかない** |
| 状態 | `未返却`(有効)とだけ書く。書き足した値(`未返却(…)`)、返却済み・取り下げ・失効の行は対応づかない |
| 承認した者 | 例外承認の権限を持つ者の記名。人の名簿の人へ対応づく氏名・id・アカウントで書く。名簿に無い記名、作成を指示した者、AI の名義は対応づかない |
| 内容・受容した理由 | 満たさない基準の項目番号と、満たさない理由 |
| 返却の目安 | 回収の期限(日付 YYYY-MM-DD を含める。「未定」は記入なし)と回収責任者 |

例外承認の判定記録(`docs/gates/`)を作る場合も、台帳の行を必ず置きます。集約が対応づけるのは台帳の行です。承認した者が例外承認の権限を持つかは、機械では確かめません。

例外承認は未達を解消しません。未達の表示と、保証の開示への記載は残ります。例外承認は人確定です。エージェントが結論を起案しません。

#### 参照した D-0 の版

体制の変化点(`/process-change`)の後は、改訂後の版を参照して判定します。改訂前の版を参照した新しい判定記録は、証跡の集約で欠落になります。**成立済みの判定記録の版は、変化点の後も書き換えません**。

#### 判定基準チェックリストの自動分類と展開（ADR-0048）
- `scripts/vendor/tailoring-kb.json` の `"gates"` 配列を検索し、作成対象ゲート（例: `g-spec-cycle` / `G-4`）の `"criteria"` を抽出します。
- `templates/04-gate-record.md` を複製して作成する際、抽出したクライテリアを**「機械で自動検証できる基準」**と**「人の見識・判断が要る基準」**の2つに分類して、それぞれの表へ出力してください。
  1. **機械で検証できる基準** -> `## 機械が確認した項目 — 人は再確認しない` の表へ記入。また、確認の不備を防ぐため、「機械で確認した範囲」の列を必ず埋めてください。
     *(例: 「見たのは空欄でないことだけです。内容の妥当性は判定していません」など)*
  2. **人の判断が要る基準** -> `## 人が判断する項目` の表へ記入。判断の材料だけを書き、結論を勝手に書かないでください。
  - *どちらに振り分けるかは起稿者が合理的に判断し、振り分けた理由を「機械で確認した範囲」の列に説明として書いてください。*
- 展開した表の下部には、以下の標準適合ディスグレイマー（注意書き）を必ず併記してください：
  ```markdown
  > ⚠️ 注意: この一覧は標準第4章の判定基準表のみを機械抽出したものです。表外の規定・解説については、必ず出所（上記 URL）を参照してください。
  ```

### 4. 差し戻しの理由は項目番号で書く

「もう少し検討してください」は理由になりません。**どの判定基準のどの項目を満たしていないか**を書きます。基準のないゲートは、判定者の属人判断になり、滞留と素通しの両方を招きます。

### 5. 判定はエージェントが行わない

**このスキルが行うのは記録の作成だけです**。判定そのものは人が行います。

結果欄を先に埋めてはなりません。判定者に渡し、書いてもらいます。

リリース決裁(G-8)の記録では、決断の記録の「出荷判定者の異議(リリース決裁 G-8 の記録に限る)」欄を**出荷判定者が記載します**。異議が無い場合も「異議なし」と書きます。**この欄が空欄なら、記録を完成させません**。空欄は記載の欠落であり、事業決裁者は受容を記名しません。エージェントがこの欄を埋めてはなりません。

保証の開示が次のいずれかに当たる場合、出荷判定者は、異議の有無とあわせて**理由**を書きます。「異議なし」とする場合も同じです。当たるかどうかは、品質レポートの「出荷判定者の異議で検討する事項」に出ます。

| # | 事項 |
| --- | --- |
| 1 | 独立した人の確認を経ていない R1 の変更がある |
| 2 | 検出能力が未測定のまま、連続して出荷している |
| 3 | 独立した人の確認を経ていない変更の件数、または構成上の未達のゲートと逸脱の数が、前回の出荷より増えた(どちらか一方の増加で当たる) |
| 4 | 事後の抜き取りを、作成を指示した本人が行っている |

G-8 の記録の「対象」には、出荷のタグ(例: `v1.4.0`)を書きます。証跡の集約は、当該出荷の範囲で追加された G-8 の記録と、「対象」が終点のタグを指す G-8 の記録について、異議の欄が空欄なら欠落として失敗します。**G-8 の記録を書いた後に、集約をもう一度実行してください**(`ship-evidence` の手動実行。起点に前回のタグ、終点に今回のタグを指定する)。**事項に当たるのに、記載が「異議なし」「異議あり」の語だけで理由が無い場合も、空欄と同じ記載の欠落として失敗します**。機械が見るのは、異議の有無を表す語のほかに記載があるかどうかだけです。理由の内容は判定しません。

出荷判定者の席と事業決裁者の席の責任者が同一人物の体制(1〜2名)では、保証の開示の項目1 に「異議を書く者と、残存リスクを受容する者が同一である」と出ます。異議の欄の記載と受容の記名は省きません。

委任で先へ進めた変更の、期間ごとの保証の開示(`aggregate-evidence --period-from <起点> --period-to <終点>`、ワークフロー `assurance-period`)への受容と異議も、G-8 の判定記録に残します。「対象」へ期間を起点〜終点の形で書きます(例: `委任の期間 2026-09-01〜2026-09-30`)。「対象」に書く日付は起点と終点の2つだけにします。判定者の記名と判定の結果(通過 / 差し戻し)も確かめられます。結果が差し戻しの記録は、期間の開示を受容していないものとして扱われます。記録が無い期間の開示は、記載の欠落です。記録を書いた後に、同じ期間で集約し直します。

#### 判定記録は、出荷ごとに要る

証跡の集約は、**当該出荷の範囲で追加された判定記録**だけを、今回の出荷の記録として数えます。過去の出荷の判定記録が残っていても、今回の出荷の記録が1件も無ければ欠落です。

#### PR を経ていないコミットで、トレーラを書き忘れた場合

PR を経ていないコミットは、リスク区分をトレーラ `Risk:`、作成側の検証の記載をトレーラ `Verification:` に持ちます。書き忘れたコミットは書き換えません。**判定記録の「対象」へコミットの識別子(先頭7桁以上)を書き、「変更のリスク区分」の欄へ区分を、「検証方法と結果」の節を足して検証の記載を書いて確定します**。この節は、書き忘れを補う場合にだけ足します。リスク区分の確定は人が行い、「リスク区分を確定した者」へ記名します。

### 6. 記録を書いてからラベルを動かす

順序は「判定基準との突合 → **記録の作成** → `state:*` ラベルの遷移 → Issue / PR の事務」です。**逆にしてはなりません**。

ラベルを先に動かすと、受け取った側は判定が済んだものとして着手します。記録が後追いになれば、判定者が実際に基準と突き合わせたかどうかを誰も確かめられません。

**記録の作成をもって判定が成立します**。記録の無いまま次工程へ渡っている状態を見つけたら、着手せず判定者へ差し戻します。

## 判定に持ち込まないもの

判定者が見るのは、**当該ゲートの判定基準と、全ゲート共通の通過条件だけ**です。

| 持ち込まない | 扱う場所 |
| --- | --- |
| 次工程で作る成果物の未完成 | 次工程のゲート |
| 判定基準に無い懸念 | 判定前のコメント期間 |
| 投資を続けるかどうか | ステージ移行ゲート |

基準を満たしているのに次工程の材料が揃っていないことを理由に判定を保留すると、**工程は止まり、その停止はどの記録にも残りません**。

判定基準を満たさないまま進める必要がある場合に限り、例外承認の手続を踏みます。**「条件付き通過」という結果はありません**。

## 期限を超えたとき

判定の期限(G-2/G-3 は48時間、G-4 は24時間、G-6 は2営業日、G-7 は3営業日が目安)を超えた場合、**自動承認にしません**。エスカレーションします。

期限を過ぎたことも記録に残します。滞留は測定の対象です。
