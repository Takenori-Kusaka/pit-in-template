# 判断記録(ADR)を書く

## 何を記録するか

**あとから変えにくい決定**です。技術選定、方針、原則、外部との契約に関わる設計。

設計上の選択を伴った場合に、判断記録を残します(標準 第2章 2.6)。設計上の選択を伴わない日々の実装判断は対象外です。迷うときの目安(テンプレート独自): 「あとで変えるとしたら何が必要か」を考え、答えが「作り直し」に近ければ、設計上の選択です。

## 手順

### 1. 番号を採る

`context/decisions/` を見て次の連番を採ります。`0001-<英語のケバブケース>.md`。

### 2. テンプレートから起こす

`templates/02-adr.md` を写します。

### 3. 埋める

| 節 | 書くこと |
| --- | --- |
| ステータス | 採用(日付) / 廃止 / 置き換え(後継 ADR へリンク) |
| コンテキスト | 何が問題で、なぜいま決めるのか |
| 決定 | 何を決めたか。具体的に |
| 検討した選択肢 | **採らなかった案と、採らなかった理由** |
| 可逆性 | 後から変えられるか。変えるとしたら何が必要か |
| 非機能への影響 | 性能・可用性・セキュリティの充足の見込み(G-3 基準1) |
| 事業への影響 | 観測可能な事象で書く。様式の5項目に空欄を残さない(G-3 基準5) |
| 影響 | 何が変わるか。トレードオフ。仕組みの限界 |

### 4. 選択理由は人が書く(R1 の決定と例外承認)

**リスク区分 R1 の決定と例外承認では、「検討した選択肢」の採否の理由を AI が生成してはなりません**。 <!-- 根拠: 標準 第5章 5.7.3 -->
どの案を選ぶかの理由は、人が記入します。エージェントは、複数の案と、それぞれのリスクの見積を提示してよいです(標準 第5章 5.7.3)。

R1 の決定と例外承認では、「したがって案Bを推奨します」のような結論を書いてはなりません。 <!-- 根拠: 標準 第5章 5.5.5 -->

R2 までの決定では、設計案と判断記録の起案をエージェントが行ってよいです(標準 第5章 5.5.6)。確定は技術判断者(人)が行います。どの区分に当たるかは、人が確定します。

### 5. コミットする

```
docs: セッション管理の方式を決める

ADR: ADR-0007
```

### 6. 次の一手を示す

```bash
node scripts/gate/next.mjs
```

出力された次の一手を利用者へ示します。「人の判断待ち」が出たら、コマンドを実行せず、待つ席へ受信箱のラベルで渡します。

## 採用済みの ADR を書き換えない

決定を変えるときは**新しい ADR で置き換えます**。古い ADR のステータスを「置き換え」にして後継へリンクし、本文はそのまま残します。

書き換えると、当時なぜそう決めたのかが失われます。採らなかった選択肢を書き残すことは、後任者が同じ検討を繰り返さないための唯一の手段です。
