# 判断記録(ADR)を書く

## 何を記録するか

**設計上の選択**です。範囲は標準 第2章 2.6「判断記録の範囲」が定めます。次は例示であり、網羅ではありません。

- 依存の追加・変更(ライブラリ、フレームワーク、データストア、外部サービス)
- 外部インタフェース(公開するインタフェース、ほかのシステムとの連携の方式)
- データ形式(永続化の形式、交換の形式)
- 構成単位の境界(モジュール・サービスの分け方と、責務の割り当て)
- 非機能への影響(性能・可用性・セキュリティの見込みを変える選択)
- プロセスの構造の変更、安全重要度(CL)の引き下げ、記録済みの実装スタックの変更

次は判断記録に書きません。

- **原則と規約**。恒久層へ置きます(プロダクトの原則は `templates/12-product-principles.md` を写して `context/standards/principles.md` へ。用語集・設計標準は `context/standards/`)。原則の追加・変更・廃止は、判断記録で記録します
- 設計上の選択を伴わない日々の実装判断

**選択が戻せることを理由に、判断記録を省きません**。戻せるかどうかは「可逆性」欄に書き、G-3 の基準3 で判定者が評価します(標準 第2章 2.6)。

判断記録は独立の文書です。実装計画・機能仕様・ゲート判定記録・PR の本文へ統合しません(標準 第6章 テンプレ2)。

## 手順

### 1. 番号を採る

`context/decisions/` を見て次の連番を採ります。`0001-<英語のケバブケース>.md`。

### 2. テンプレートから起こす

`templates/02-adr.md` を写します。

### 3. 埋める

| 節 | 書くこと |
| --- | --- |
| 冒頭の行 | 状態(採用(日付))、置き換える決定(なし / ADR-MMM の決定 n / ADR-MMM(全部))、判定者、対象、期限(期限つきの実験として導入した場合) |
| コンテキスト | 何が問題で、なぜいま決めるのか |
| 決定 | 何を決めたか。具体的に。複数あれば「決定1」「決定2」と番号を付ける |
| 検討した選択肢 | **採らなかった案と、採らなかった理由** |
| 可逆性 | 戻せる選択か(はい / いいえ)。いいえなら、戻せなくなるもの(G-3 基準3) |
| 非機能への影響 | 性能・可用性・セキュリティの充足の見込み(G-3 基準1) |
| 事業への影響 | 観測可能な事象で書く。様式の5項目に空欄を残さない(G-3 基準5) |
| 影響 | 何が変わるか。トレードオフ。仕組みの限界 |

### 4. 選択理由は人が書く(R1 の決定と例外承認)

**リスク区分 R1 の決定と例外承認では、「検討した選択肢」の採否の理由を AI が生成してはなりません**。 <!-- 根拠: 標準 第5章 5.7.3 -->
どの案を選ぶかの理由は、人が記入します。エージェントは、複数の案と、それぞれのリスクの見積を提示してよいです(標準 第5章 5.7.3)。

R1 の決定と例外承認では、「したがって案Bを推奨します」のような結論を書いてはなりません。 <!-- 根拠: 標準 第5章 5.5.5 -->

R2 までの決定では、設計案と判断記録の起案をエージェントが行ってよいです(標準 第5章 5.5.6)。確定は技術判断者(人)が行います。どの区分に当たるかは、人が確定します。

### 5. コミットする

```
docs: セッション管理の方式を決める

ADR: ADR-0007
```

### 6. 次の一手を示す

```bash
node scripts/gate/next.mjs
```

出力された次の一手を利用者へ示します。「人の判断待ち」が出たら、コマンドを実行せず、待つ席へ受信箱のラベルで渡します。

## 採用済みの ADR を書き換えない

決定を変えるときは**新しい ADR で置き換えます**。採用後に書き換えてよいのは、旧い判断記録の**状態の行だけ**です。状態の行は本文に含めません。

書き換えると、当時なぜそう決めたのかが失われます。採らなかった選択肢を書き残すことは、後任者が同じ検討を繰り返さないための唯一の手段です。

### 置き換えと廃止(標準 第6章 テンプレ2「置き換えと廃止」)

状態の語彙は4つだけです。

| 状態 | 書き方 | 置き場 |
| --- | --- | --- |
| 採用 | 採用(YYYY-MM-DD) | `context/decisions/` |
| 一部置き換え | 一部置き換え(→ ADR-MMM の決定 n) | `context/decisions/`(移さない。効いている決定が残るため) |
| 置き換え | 置き換え(→ ADR-MMM) | `context/_archive/decisions/` へ移す(削除しない) |
| 廃止 | 廃止(YYYY-MM-DD) | `context/_archive/decisions/` へ移す(削除しない) |

1. 置き換える側(新しい判断記録)の「置き換える決定」へ、置き換える判断記録と決定の番号を書く(例: `ADR-0003 の決定2`、`ADR-0005(全部)`)
2. 同じ変更で、置き換えられた側の状態の行に後継の番号を書く
3. 全部の置き換えと廃止は、同じ変更で保管領域へ移す。移動は、置き換える判断記録(または廃止)を判定した G-3 の帰結の事務であり、読み込み実績に基づいて外す判断(AI維持管理者の棚卸し)ではない。外した日は状態を改めた日、理由は状態の行、外した者はその G-3 の判定者、復帰の条件は置き換えた判断記録が廃止されたとき(標準 第3章 3.11.4 要求事項7 の記録)。期間の経過では移さない
4. 両側の一致と置き場を確かめる

```bash
node scripts/gate/check-decisions.mjs
```

期限つきの実験として導入した判断記録は、期限の後に結果(継続・置き換え・廃止)を状態の行へ反映します。期限を過ぎて状態が変わらないものは `node scripts/gate/check-decisions.mjs --overdue` が一覧にし、四半期の振り返りの入力になります。扱いは技術判断者が決めます。

索引(一覧の文書)は課しません。置く場合は機械で生成し、手で保守しません。
