# 実装計画へ分解する

## 手順

### 1. 機能仕様を読む

`specs/F-NNN/spec.md` の受入基準を一覧にします。

### 2. タスクへ分解する

`templates/07-implementation-plan.md` を `specs/F-NNN/plan.md` として写します。

各タスクに次を書きます。

| 欄 | 内容 |
| --- | --- |
| ID | `Task-1` から連番 |
| 対応する受入基準 | 1つ以上。**対応のないタスクを作らない** |
| 変更の対象パス | 実行環境の書き込み範囲の設定に使う |
| 依存 | 先に完了している必要があるタスク |
| 並列可否 | 依存がなければ並列可 |

### 3. 粒度を確認する

**関心事が 1 つで、受入基準の束につき 1 Task** にします。`process.config.json` の `task` は規模の基準値です(遮断の上限ではありません)。

| 項目 | 既定の基準値 |
| --- | --- |
| 変更行数 | 400 |
| 変更ファイル数 | 15 |

基準値を超える見込みでも、行数に合わせて細切れにしません。確認が要る大きさ・範囲になるタスクは、実装計画の粒度の確認へ書き、PR の「規模の確認」の欄(実施者・読み切れたか・分割しなかった理由・保証の所在)を人へ渡します。超過は失敗にならず、区分の下限が R2 に上がります。

**基準値は製品のコードのファイルごとの max(追加, 削除)の合計に適用します。** テスト・fixture・snapshot は別に数えます。自動生成ファイル・ロックファイル・一括整形は算定から除外します。判断記録(ADR)・機能仕様・設計文書は行数の算定から除外し、判定完了時間の SLA で判定します(標準 第4章「L0 の既定値」)。

**この数値は暫定です。** 由来は2006年の調査であり、原典が測ったのはレビューの継続時間と欠陥検出率の関係です。運用開始後は、出荷の集約が出す規模の分布と超過の観測で、人が見直します。

### 4. 分解しすぎない

事前に細かく割り切ると、かえって手戻りが増えます。**分解は、依存関係と検証の単位が決まる粒度で止めます**。

### 5. 並行実行する場合

複数のエージェントを同時に走らせるなら、次を満たします。

- 作業ツリーを分離する。同一ディレクトリでの並行実行はファイルの上書きと索引破損を即座に起こす
- 共有される設定・登録・経路定義のファイルを、同時に変更する組み合わせを避ける
- 完了後に、同一機能の重複実装が生じていないかを確認する

### 6. 次の一手を示す

```bash
node scripts/gate/next.mjs
```

出力された次の一手を利用者へ示します。「人の判断待ち」が出たら、コマンドを実行せず、待つ席へ受信箱のラベルで渡します。

## 完了の条件

- [ ] 各タスクが1つ以上の受入基準に対応している
- [ ] どのタスクも1レビュー単位に収まる見込みがある
- [ ] 変更の対象パスが書かれている
- [ ] 価値責任者が承認した(G-4)
