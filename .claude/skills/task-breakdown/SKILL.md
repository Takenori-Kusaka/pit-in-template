# 実装計画へ分解する

## 手順

### 1. 機能仕様を読む

`specs/F-NNN/spec.md` の受入基準を一覧にします。

### 2. タスクへ分解する

`templates/07-implementation-plan.md` を `specs/F-NNN/plan.md` として写します。

各タスクに次を書きます。

| 欄 | 内容 |
| --- | --- |
| ID | `Task-1` から連番 |
| 対応する受入基準 | 1つ以上。**対応のないタスクを作らない** |
| 変更の対象パス | 実行環境の書き込み範囲の設定に使う |
| 依存 | 先に完了している必要があるタスク |
| 並列可否 | 依存がなければ並列可 |

### 3. 粒度を確認する

`process.config.json` の `task` が上限です。

| 項目 | 既定の上限 |
| --- | --- |
| 変更行数 | 400 |
| 変更ファイル数 | 15 |
| レビュー所要時間 | 30分で読み切れること |

**目安は行数ではなくレビュー可能性です**。上限を超える見込みなら分割します。

**行数の上限は実装コードの差分に適用します。** 自動生成ファイル・ロックファイル・一括整形は算定から除外します。判断記録(ADR)・設計文書には適用せず、レビュー所要時間で判定します(`CLAUDE.md`「タスクの粒度」)。

**この数値は暫定です。** 由来は2006年の調査であり、原典が測ったのはレビューの継続時間と欠陥検出率の関係です。運用開始後は自組織の実測へ置き換えます。

### 4. 分解しすぎない

事前に細かく割り切ると、かえって手戻りが増えます。**分解は、依存関係と検証の単位が決まる粒度で止めます**。

### 5. 並行実行する場合

複数のエージェントを同時に走らせるなら、次を満たします。

- 作業ツリーを分離する。同一ディレクトリでの並行実行はファイルの上書きと索引破損を即座に起こす
- 共有される設定・登録・経路定義のファイルを、同時に変更する組み合わせを避ける
- 完了後に、同一機能の重複実装が生じていないかを確認する

## 完了の条件

- [ ] 各タスクが1つ以上の受入基準に対応している
- [ ] どのタスクも1レビュー単位に収まる見込みがある
- [ ] 変更の対象パスが書かれている
- [ ] 価値責任者が承認した(G-4)
