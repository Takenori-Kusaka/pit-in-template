# タスクの粒度

`CLAUDE.md`「タスクの粒度」の詳細です。基準値は `process.config.json` の `task` が正本です。

**関心事が 1 つで、受入基準の束につき 1 Task** にします。規模の基準値は、遮断の上限ではなく、**超えたら人の確認を要する基準**です。既定値は次のとおりです。

| 項目 | 既定の基準値 |
| --- | --- |
| 変更行数 | 400行 |
| 変更ファイル数 | 15 |

1つの変更に複数の関心事を混ぜません。「30分で読み切れる」「100行を超えたら人へ確認」といった数値の指示は、AI の担い手へ与えません(テンプレート独自の決まり。標準 第6章の分割の指示は数値を含まないが、与えないとまでは定めていない)。AI が自主的に細切れにすると、分割しすぎない(下記)と衝突します。確認が要る大きさ・範囲になると分かったら、自分で分割せず、PR の「規模の確認」の欄を人へ渡します。

## 算定の方法と除外規定

対象は製品のコードの差分です。**ファイルごとの max(追加, 削除) を足します**(書き換えを追加+削除の 2 倍に数えません。純削除は削除行数)。

- **別に数える**: テスト・fixture・snapshot(`test/**`・`tests/**`・`__tests__/**`・`*.test.*`・`*.spec.*`・`fixtures/**`・`__snapshots__/**`)。基準値の判定には入れず、PR の検査の結果に出します。ただし**基準行数の5倍(暫定)を超えたら、別集計の側も `size:over` になります**(製品のコードをテストのパスへ移して基準値を避ける抜け道を塞ぐため)。置き場は構成 `task.nonProductPaths` で足せます(足すのは緩める向きで、閾値として扱う)
- **文書の置き場のコード**: `docs`・`specs`・`context`・`templates`・`evidence`・`profiles` に置いたコードの拡張子のファイルは、製品のコードとして数えます(強制層・構成のパスは対象外)
- **除外する**: 自動生成ファイル・ロックファイル・一括整形・内容の変わらない名前の変更・文書・記録・強制層・構成。機械的な変換(決定論的で、テストで正しさを検出でき、部分的に取り消せるもの)は、基底へ生成の印を入れてから除外されます
- **ファイル数**: 基準値を超えると `size:over` になりますが、数値自体の実証が無いため、規模の確認の記入だけを要します

**判断記録(ADR)・機能仕様書・設計文書は、行数の算定から除外し、判定完了時間の SLA で判定します**(標準 第4章「L0 の既定値」)。上限の根拠はソースコードのレビューの調査であり、散文の成果物は適用範囲の外であるためです。

## 基準値を超えたとき(ADR-0058)

G-5 の `pr-rules`(`scripts/gate/check-pr.mjs`)は、基準値(**基底ブランチの**構成)の超過を**失敗にしません**。超過した PR には次を課します。

1. 結果に `size:over` を出す
2. 区分の下限を **R2** へ引き上げる(作成を指示した者以外の名簿の人が確定し、記名する。独立した人の確認(G-6)が掛かる)
3. PR の本文の「規模の確認」(実施者・読み切れたか・分割しなかった理由・保証の所在)を要する

**欄が無い・実施者が AI の名義・「読み切れたか」が「いいえ」のときだけ失敗**します。読み切れない変更は、実装計画(plan.md)へ戻して関心事で分け直します(行数に合わせて細切れにしません)。

- 実施者は、作成を指示した者でもかまいません(1名体制)。その場合、独立した人の確認が無いことが記録に出続けます
- 担保水準 L1 以上の宣言(構成 `task.assurance`)に根拠が実在するときは、「保証の所在」の記入だけで足ります
- 基準値は `null`(基準なし)を取れます。担保水準 L2 の宣言と根拠が実在し、確約範囲・コア指定のパス(`delegation.protectedPaths` か `riskFloor.rules` のパス)が構成に宣言されているときだけ書け、R1・R2 の変更・そのパスに触れる変更には効きません。パスが宣言されていない構成では、コア外の変更かを確かめられないため、書けません
- 基底ブランチの台帳に、その PR を対象とする有効な例外承認の行が既にある場合は、従来どおり規模の確認を要しません(過去の記録を壊さない)。**新しい超過に例外承認は要りません**。例外承認は R2 以上の規範の逸脱のために残っています
- 超過は出荷の集約が数えます(規模の分布・`size:over` の件数・「読み切れたか」の内訳・判定完了時間)。基準値へは自動で反映しません

## この数値は暫定です

基準値 400 行は **2006年の調査**(2,500件のレビュー・320万行)に由来します。原典が測ったのは**レビューの継続時間と欠陥検出率の関係**であり、行数上限そのものを検証した測定ではありません。成立の前提は当時のC系プロダクトコードとツール支援レビューであり、**2010年代以降に独立して再検証した研究は確認されていません**。

ファイル数(15)には数値自体の実証がありません。**具体的な区切り位置は自組織で較正する対象です。**

**運用開始後は自組織の実測へ置き換えます。** 出荷の集約が出す観測を材料に、四半期ごとに観測し、更新は半期以上の周期で、判定完了時間の充足率が 8 割を下回らない最大の区間から基準値を導きます。差し戻し率・リバート率・本番インシデント率が悪化していないことを併せて確認し、悪化していれば戻します。**この手続を自動化してはなりません。** <!-- 根拠: 標準 第4章「上限を自組織の実測で較正する」 --> 能力依存の定数の再評価待ちは `/pit` の注記に出ます(値は自動で変えない)。

詳細は[第4章 変更単位の水準](https://takenori-kusaka.github.io/process-compass/phase4-process-design/gate-criteria/)を参照してください。

## 基準値を上げる・外すとき

基準値を上げる・外すのは、緩める向きの決定です。`/process-change`(種別 `settings`)で、決定した者の記名と理由を受け取って行います。較正の手続は、標準 第4章「上限を自組織の実測で較正する」によります。

上限を緩和できる手段と、できない手段は、標準 第4章「上限を緩和できる手段と、できない手段」が定めます。**仕様のレビューへの前倒しと、図による可視化は、緩和の根拠になりません**(同節)。逐行の確認を、仕様のレビューで代えません。
