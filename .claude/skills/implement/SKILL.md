# 実装する

## 前提

- `specs/F-NNN/spec.md` が承認済み(G-4)
- `specs/F-NNN/plan.md` にタスクが分解済み

どちらも欠けている場合、実装を始めないでください。

## 手順

### 1. ブランチを切る

```bash
git switch -c feature/F-012-task-3
```

### 2. テストを先に生成する

**実装コードを読ませずにテストを生成します**。受入基準だけを入力にします。

実装を読んだうえでテストを書くと、実装の誤りをそのまま正解とみなすテストが生成されます。テスト駆動開発が有効だった理由は、仕様と実装が切り離されていたことにあります。これは文脈と入力の**分離**です。分離を「独立」と呼びません。独立は、検証の担当者を実装の責任者から組織的に分けた場合にだけ成立します。

安全重要度が高い構成(`process.config.json` の `answers.q-criticality` が `cl2` 以上)では、生成されたテストの十分性を**人が判定**します。エージェントの自己判断で先へ進めないでください。

### 3. 実装する

`plan.md` の対象パスの範囲で実装します。範囲外のファイルを変更する必要が出たら、**計画の誤りとして人へ返してください**。範囲を自分で広げないでください。

承認済みの受入基準とスコープの内側にある作業上の選択は、協働の席でも**自分で決めて記録します**。選択のたびに人へ戻しません。記録先はコミットのメッセージ、または PR の「変更の概要」です。人へ戻すのは、人が確定する判断、受入基準・スコープ・公開インタフェース・データ形式を変える選択、取り消せない操作の3つです(`CLAUDE.md`「人へ戻す3つの場合」)。

### 4. 自己修正ループへ入る

自動検証の失敗を入力として修正を反復します。**ループへ入る前に、スクリプトでロックを始めてください**。

```bash
node scripts/gate/self-heal.mjs start --spec F-012 --task Task-3
```

ロックがある間、`.claude/hooks/guard-write.mjs` がテストへの書き込みを拒否します。渡された失敗をテスト側の変更で解消する経路を塞ぐためです。この遮断は段階に依らず有効です(探索ステージで強制層を無効にしても外れません)。ロックのファイル(`.claude/.self-heal`)への直接の書き込みも拒否します。ロックの外(手順2 のテストを先に書く作業)は遮断しません。

反復のたびに、修正の前に回数を数えます。

```bash
node scripts/gate/self-heal.mjs iterate
```

| # | 規則 |
| --- | --- |
| 1 | 反復上限は `process.config.json` の `task.selfHealMaxIterations`(既定3回)。上限に達すると `iterate` が終了コード3を返し、ロックが**保留**になる |
| 2 | 保留は**人の判断待ち**。人が受入基準へ戻る。実装の再試行を続けない |
| 3 | 同じ失敗を3回繰り返す場合、原因は実装ではなく受入基準の不備であることが多い |
| 4 | テストの修正を要すると判明したら、`stop --reason test-change` でループを終える(保留になる)。**ループの内側で続けない** |
| 5 | 反復回数と、拒否された操作の件数を記録する(`.claude/self-heal.log`・`.claude/denied.log`) |

ループを終えるときは、終え方を理由で選びます。

| 状態 | コマンド | 結果 |
| --- | --- | --- |
| 自動検証が通った | `node scripts/gate/self-heal.mjs stop --reason pass` | スクリプトがテストを実行し、通った場合だけロックを終える |
| 反復上限に達した | `node scripts/gate/self-heal.mjs stop --reason limit` | 保留。テストの遮断は続く |
| テストの修正を要する | `node scripts/gate/self-heal.mjs stop --reason test-change` | 保留。テストの遮断は続く |

保留を解くのは**人の操作**です(`node scripts/gate/self-heal.mjs release --by "<氏名>"`)。エージェントが保留を解く、ロックのファイルを削除する、またはロックを終えて反復を続けた場合、それは禁止事項3(テストの失敗をテスト側の変更で解消する)に該当します。保留の間は `state:needs-po` を付け、どの受入基準で失敗し続けているか・その基準が実装可能な粒度か・分割すべき点を提示します。

限界: フックは Claude Code の書き込み(Edit・Write)だけを遮断します。シェルからのファイル操作と、担い手による `release` の実行は、機械では止められません。操作は `.claude/self-heal.log` に残ります。

### 5. ローカルで検証する

```bash
node scripts/gate/g5-local.mjs --no-install   # CI(gate-g5)と同じ範囲。依存を取り直すなら --no-install を外す
```

個々の検査を選んで実行しない。CI より狭い範囲を見て「0件」と報告する誤りの元になる(#286)。PR の検査(pr-rules)まで確かめるときは `--base origin/main --pr <PR の JSON>` を足す。手元の結果は CI の代わりにならない。

### 6. コミットする

```
feat: 招待の失効を一覧へ表示する

Spec: F-012 / Task-3
Co-Authored-By: <エージェント名>
```

Author は指示した人間です。`Spec:` トレーラは必須です。

**PR を経ずにコミットする体制(ブランチ保護を置かない 1〜2名の構成)では、コミットのトレーラへ、リスク区分と検証の記載を書きます**。

```
Risk: R3
Verification: npm test 142件通過。evidence/ci-1234
```

`Verification:` には、実行した検証と結果の要点、または証跡の所在を1行で書きます。PR 本文の「検証方法と結果」に当たる記録です。複数行で書きたい場合は、コミットの本文へ「検証方法と結果」の段落を書き、トレーラはその旨を指します。人確定・協働の変更では人が書き、開発者の席の委任の範囲の変更では担い手が実行結果の証拠として書きます。`Risk:` には `R1`・`R2`・`R3` のいずれかを書きます。リスク区分は変更ごとに確定する記録であり、PR を経ないコミットは PR 本文の欄を持たないためです。区分の草案は書けますが、確定は人が行います。どちらかのトレーラが無いコミット、値が空のコミットは、出荷判定の証跡で欠落になります。**独立レビュー(G-6)を適用する体制(作成を指示した者以外の確認者を置ける体制)では、PR を経ていないコミットは、独立した人の確認を経ていない変更として欠落になります**。独立した人が確認して G-6 の判定記録(「対象」にコミットの識別子、判定者、挙動要約)を残すか、例外承認の記録(技術負債台帳の区分「例外」の行)を対応づけます。件名に `(#N)` を書いても、PR のマージコミットと一致しないコミットは PR の変更に数えられません。書き忘れたコミットは書き換えず、判定記録(`docs/gates/`)の「対象」へコミットの識別子を書き、「変更のリスク区分」の欄へ区分を、「検証方法と結果」の欄(表の行、または節)へ検証の記載を書いて補います。記録だけのコミット(`docs/gates/`、`evidence/`、技術負債台帳、体制図、`/process-change` が書いた構成と生成物だけを変えるコミット)には要りません。`CLAUDE.md` の手書き部分を変えたコミットと、`process.config.json` を `/process-change` を経ずに書き換えたコミットは、記録だけのコミットではありません。

### 7. Draft PR を出す

着手の宣言としてまず Draft で出します。CI が回り始めます。

`検証方法と結果` の欄は空のままにしてください。**人確定・協働の変更では、この欄は人が書き、Draft から Ready にするのも人です**。開発者の席の委任の範囲の変更だけは、手順8 のとおり担い手が書きます。Ready にするのは、既定では人です(テンプレートの既定の権限設定に `gh pr ready` が無いため。手順8 の4)。

`作成を指示した者` の欄は、指示した人が書きます。エージェントが推測で埋めないでください。出荷判定の証跡は、この欄の人による承認を、独立した人の確認に数えません。

### 8. 委任の範囲に当たる変更の扱い

自席が委任を宣言している場合でも、該当を自分で判定しません。機械の規則で判定します。

```bash
node scripts/gate/verify-gate-contract.mjs --delegation
```

該当した場合は、次の3つを行います。リスク区分が R1・R2 の変更と、区分が未記入の変更は、規則に当たっても委任の対象になりません。

| # | すること |
| --- | --- |
| 1 | **すべてのコミット**のトレーラへ `Delegated: <規則ID>` を書く。マージの経路が有効かどうかにかかわらず書く。変更ごとの検証を担い手へ委ねた変更として、変更単位で識別するためである。独立した人の事前の承認が無い委任の変更のうち、「人の事前確認を経ていない変更」と呼ぶのは、G-6 の判定を事後へ移した変更だけである。それ以外は、独立した人の確認を経ていない変更として数えられる(独立レビューを適用する体制では欠落) |
| 2 | 開発者の席の規則に当たる変更では、PR の `検証方法と結果` の欄へ、**実行結果の証拠**を書く。実行したコマンドと、観測した結果をそのまま書く。評価と推測は書かない。独立レビュアの席の規則だけに当たる変更(開発者の席はこの変更について協働)では、この欄は開発者の席の人が書く |
| 3 | PR のリスク区分を書く。R3 と記録した変更だけが、委任の対象になる。トレーラ Delegated を持つ変更を R1・R2 と記録すると、委任の範囲の逸脱として欠落になる |
| 4 | 開発者の席の規則に当たる変更で、Draft から Ready にする。**テンプレートの既定の権限設定(`.claude/settings.json` の許可リスト)に `gh pr ready` は無い**。権限設定は強制層であり、組織が許可を足すまでは人が Ready にする。担い手は設定を変えずに、Ready にしてよい状態であることを人へ報告する。許可を足した組織では、担い手が Ready にする |

PR を出した後の該当の判定は、ワークフロー(`.github/workflows/delegation.yml`)が行います。判定のコードと構成は**既定ブランチから**読まれます。PR の側で規則や構成を書き換えても、判定は変わりません。強制層(`.claude/**`、`.github/**`、`process.config.json`、`scripts/gate/**`、`docs/gates/**` など)に触れる変更は、常に対象外です。結果は、必須でないステータス `delegation-eligibility` として PR へ出ます。

| 判定の結果 | 扱い |
| --- | --- |
| 該当しない | 協働として扱い、人の確定を受ける。理由はステータスとジョブの出力にある |
| 開発者の席の委任に該当(開発者の席の規則にだけ該当する) | 変更ごとの検証は、担い手が実行結果の証拠で示す。独立レビュー(G-6)は、独立レビュアが人として事前に承認する。**現在のブランチ保護のまま**マージされる。人の事前確認を経ていない変更ではない |
| G-6 を事後へ移す委任に該当(独立レビュアの席の規則にも該当する)。マージの実行が無効(既定) | 協働として扱い、人の承認を待つ |
| G-6 を事後へ移す委任に該当。マージの実行を組織が有効化している | ワークフローがマージする。PR へ「人の事前確認を経ていない変更(G-6 の判定を事後の抜き取りへ移した変更)として、規則 <ID> により先へ進めた。承認ではない」と記録される |
| G-6 を事後へ移す委任に該当するが、開発者の席はこの変更について協働(独立レビュアの席の規則だけに当たる) | 開発者の席の責任者(人)が変更を検証して承認するまで、協働として扱う。承認の後、ワークフローを手動で実行する(PR の番号を指定)と判定し直す。人の記入を要しない変更ではない |

**エージェントは `gh pr merge` を実行しません**。必須承認を経ずにマージするのは、ワークフローだけです。機械は承認のレビューを付けません。ワークフローが先へ進めた変更は、承認済みの変更ではなく、独立レビュアの席の責任者が事後の抜き取りで確かめる変更です。

### 9. 次の一手を示す

```bash
node scripts/gate/next.mjs
```

出力された次の一手を利用者へ示します。「人の判断待ち」が出たら、コマンドを実行せず、待つ席へ受信箱のラベルで渡します。

## やってはならないこと

- テストの失敗を、テスト側の変更で解消する
- カバレッジ閾値・静的解析の重大度・検査の除外設定を、この変更単位で触る
- ロックのファイル(`.claude/.self-heal`)を自分で削除する、保留を自分で解く(`release`)、ロックを終えて反復を続ける
- `plan.md` の対象パスを自分で広げる
- 人確定・協働の変更で、`検証方法と結果` の欄を埋める。人確定・協働の変更を Ready にする。`作成を指示した者` の欄を推測で埋める
- 委任の範囲に当たるかどうかを自分で判定する。委任の変更を自分でマージする
- 委任の判定を通すために、変更を分割する、リスク区分を低く書く、トレーラだけを足す

## 反復が収束しないとき

閾値を緩めないでください。**原因はタスクの分解にあります**。次を人へ提示します。

- どの受入基準で失敗し続けているか
- その基準が実装可能な粒度になっているか
- 分割すべき点はどこか
