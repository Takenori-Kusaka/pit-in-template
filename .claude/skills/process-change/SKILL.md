# 体制の変化点を反映する

人が増える・減る・交代する。AI の担い手のモデルや指示資産が変わる。運用形態を変える。こうした変化のあと、**最初のゲート判定より前に**、D-0 体制図と構成を改めます(標準 第3章 3.13 / 第8章「再テーラリングの契機」)。

`/process-init` の再実行では、何が失効し、何が新たに生じたかを特定できません。このスキルは変化点の種別を入力に取り、差分を出します。

## 構成を書き換えるのは、このスキルだけです

**`process.config.json` を手で編集しないでください**。構成を書き換える経路は、このスキル(`generate-profile.mjs --change`)だけです。

- 変化点の記録(`changeLog[]`)の各記録は、適用後の構成の要約値(`stateHash`)と、直前の記録の要約値(`prevHash`)を持ちます
- 手で書き換えた構成は、最後の記録の要約値と一致しなくなり、契約検査(`verify-gate-contract`)が失敗します。記録の書き換え・切り詰め・差し替えも、連鎖の不一致として検出されます
- 手で書き換えた構成に対して、回答ファイルからの再生成(`--answers process.config.json`)と、次の変化点は、どちらも拒否されます。**手での編集を追認する経路はありません**。編集を戻してから、変えたい内容を変化点として反映します
- PR では、契約検査が基底ブランチの構成と比べます(`--base <ref>`、または環境変数 `GITHUB_BASE_REF`)。構成が変わっているのに `changeLog[]` の追記が無い変更と、基底の記録が先頭部分として保たれていない変更は失敗します
- **限界**: 要約値ごと書き換える改ざんは、ローカルの検査だけでは検出できません。過去の記録の書き換えは、基底ブランチとの比較で止まります。**構成を手で書き換えたうえで、要約値を計算し直した記録を追記する偽造は、基底ブランチとの比較も通ります**。要約値は鍵を持たないため、記録が `/process-change` を経たことも、記名した本人が決定したことも証明しません。これを止めるのは、構成が強制層であること(変更は AI維持管理者の承認を要する)と、人による PR の確認です

同じ内容を、D-0 体制図と構成へ二重に書かせません。**D-0 体制図のうち、構成から導ける欄(節1 の責任者の表と名簿、節3 の2行の決定者、節12 の担い手と運用形態・委任の範囲、節13 の改訂履歴)と、frontmatter の `version` は、このスキルが書きます**。人が書くのは、決定の理由と記名(入力の `reason` と `decidedBy`)だけです。

## このスキルが決めないこと

- **統制を緩める向きの変更を、エージェントが決めてはなりません**。人の確認を減らす、委任の範囲を広げる、ゲートを省略へ変える、のいずれも、決定した者の記名と理由を要します。名前と理由を推測で埋めないでください
- **決定できるのは、対象の席の責任者、または D-0 表1「体制と運用形態」の決定者(既定は事業決裁者の席の責任者)に限ります**。席を特定できない決定(ゲートの状態、軸の入力)は、後者に限ります
- **席の責任者の任免(任命・交代・空いた席への後任の配置)は、統制の向きにかかわらず決定です**。D-0 表1「体制と運用形態」の決定者の記名と理由を要します。決定者その人を替える変更(決定者の席の責任者の交代、`governance` の変更)は、前任の決定者の記名を要します。前任者が体制から外れている場合は、組織上の任命権者(名簿へ `external: true` と `appointer: true` で、この変化点より前に記載した人)の記名を要します。**新任の決定者が、自分の任命を自分の記名で確定することはできません**(標準 第3章 3.13.3)。人が体制から外れて席が空くことは発生であり、記名を要求しません
- **責任者・決定した者・適合性確認の実施者と承認者・通知先の欄へ、AI の名義を書いてはなりません**。スクリプトは、人の名簿(`people[]`)に無い名義、担い手の識別と同じ文字列、AI を示す語(モデル名、agent、bot、AI の表記。全角と片仮名の読みを含む)を含む名義を拒否します。同じ語を含む実在の氏名を通せるのは、人が確認した旨(`nameConfirmed`)を名簿へ書いた場合だけです。**エージェントの判断で `nameConfirmed` を付けてはなりません**
- **名義の検査には限界があります**。語の一致による検査であり、役職名や別の文字種で書いた名義は検出できません。名簿のアカウントの記載が正しいかも、機械では確かめません。名簿は人が記入するものとし、内部監査で確かめます
- **委任の規則の追加と範囲の拡大は、統制の弱化として扱います**。委任するという決定(席の責任者の `decidedBy`)とは別に、規則の変更を AI維持管理者の席の責任者が承認します(`ruleApprovedBy`。経路は `state:needs-platform`)。承認の記名があるまで、その規則では委任は働きません(席に有効な規則が1つも無ければ、席は協働として扱います)。席の責任者と同一人物でも、どの席で判断したかを記録に残します。範囲の縮小と規則の削除には、承認を要しません
- 人の名簿へ名前を足すのは人です。エージェントが、利用者から受け取っていない名前を名簿へ足してはなりません
- **名簿の既存の行を、別の人へ書き換えてはなりません**。同じ行(`id`)の氏名とアカウントを両方とも変える入力は拒否されます。その行を名簿へ足したときの値と比べて両方が異なることになる変更も、変化点を分けても拒否されます。別の人は新しい `id` の行として足し、席への任命は任免の手続で出します。氏名だけ、またはアカウントだけの変更は、同じ人の表記の変更として扱い、D-0 表1「体制と運用形態」の決定者の記名と理由を要します。決定者本人の行の変更は、組織上の任命権者、または本人以外の席の責任者1名の記名を要します(本人の記名では確定できません)。旧い値と新しい値は、変化点の記録(`rosterEdits`)・D-0 体制図の改訂履歴・品質レポートの項目7 に残ります。出荷判定者の席の責任者の行の変更は、責任者の交代と同じく即時通知の対象です。ある人の氏名・アカウント・`id` が、別の人の氏名・アカウント・`id` と重なる名簿は拒否されます
- 無効になった確認のやり直しの要否は、文脈オーナーが決めます。このスキルが出すのは候補だけです
- ブランチ保護の適用、認証情報の発行と失効、出荷判定者の席の責任者への通知は、人が行います

## 変化点の種別

| `kind` | 標準の番号 | 変化点 | 主に変わるもの |
| --- | --- | --- | --- |
| `accountable` | 1 | 責任者の増減・交代・長期の不在、兼務の変更 | `people[]`、`seats[].accountable` |
| `headcount` | 2 | 人数の境界の通過(3名未満と3名以上、10名) | `answers.q-team-size`、`people[]` |
| `mode` | 3 | 担い手の運用形態の変更、委任の範囲の変更 | `seats[].mode`、`delegation` |
| `performer` | 4 | AI の担い手の識別の変更(モデルの版・提供者、指示資産の恒久層、ツールと権限、実行基盤) | `seats[].performer`、`seats[].qualification` |
| `axis` | 5 | 軸B〜E の入力の変化(ステージ移行、規制への該当、委託への切替、安全重要度) | `answers` |
| `schedule-only` | — | 納期・目的・範囲・予算だけが変わり、上の1〜5 へ波及しない | なし。**変化点に数えない。起票された場合は「構成の変更なし」と記録する** |
| `outage` | — | 提供者の障害・利用上限で AI が使えない期間 | なし。**変化点に数えない。期間と、その間の扱い(人へ戻した / 止めた)を記録する** |
| `settings` | — | 個別の値の変更(アダプタ、CI の下限、変更規模の上限、強制層の緩和設定、配布先、確認者の調達先) | `adapters`、`ci`、`task`、`guard`、`platform`、`unmet[].reviewSourcing`。**変化点に数えない。D-0 の版は上げない** |
| `notice` | — | 即時通知の記録(後から通知先と通知日を書く)、承認権限の一時制限(標準 第7章 7.9)の発動 | なし。**変化点に数えない** |

種別 `mode` の起票は、対象の席の責任者が責任を持ちます。

次は変化点に数えません。このスキルを使いません。

- 短期の不在(D-0 の代行者による)
- 版を固定したままのセッションの再起動と、並列数の変更
- 個々の変更のリスク区分の判定(変更ごとの判定であり、体制の変化ではない)

**納期を理由に統制を外す要求は、`schedule-only` では扱えません**。統制を緩める向きの変更として、該当する種別で、決定した者の記名と理由をつけて反映します。`schedule-only` で構成が変わる入力を渡すと、スクリプトが拒否します。

## 手順

### 1. 現在の構成を読む

```bash
node -e "const c=require('./process.config.json');console.log(JSON.stringify({answers:c.answers,people:c.people,seats:c.seats,delegation:c.delegation,governance:c.governance,d0Version:c.d0Version,unmet:c.unmet.map(u=>u.gate),deviations:c.deviations.map(d=>d.gate??d.separationId)},null,2))"
```

`configured` が `false` なら、先に `/process-init` を実行します。

### 2. 変化点を聞く

種別・対象・変更後の値・発効日を利用者へ確認します。**推測で埋めないでください**。人の名簿(氏名とリポジトリ上のアカウント)、責任者の氏名、AI の担い手の識別(モデルの版・指示資産の版・権限の組)、適合性確認の記録は、利用者から受け取ります。

軸の回答を変えるときは、`scripts/vendor/tailoring-kb.json` の `questions` の文言をそのまま使います。知識ベースに無い質問と選択肢は、スクリプトが拒否します。

### 3. 変化点をファイルへ書く

**D-0 体制図を先に手で改訂する必要はありません**。責任者の表(節1)、担い手と運用形態(節12)、改訂履歴(節13)、frontmatter の `version` は、手順6 の適用でスクリプトが書き換えます。D-0 が未作成のときは、`templates/00-d0-governance.md` を `docs/D-0-governance.md` へ写し、frontmatter と、生成区間でない節(節2〜節11)を人が記入します。

```bash
cat > /tmp/change.json <<'JSON'
{
  "kind": "headcount",
  "date": "2026-10-01",
  "summary": "3人目が加わり、独立レビュアを置けるようになった",
  "answers": { "q-team-size": "size-3-9" },
  "people": [
    { "id": "p1", "name": "<氏名>", "accounts": ["<アカウント>"] },
    { "id": "p2", "name": "<氏名>", "accounts": ["<アカウント>"] },
    { "id": "p3", "name": "<氏名>", "accounts": ["<アカウント>"] }
  ],
  "seats": { "independent-reviewer": { "accountable": "<氏名>" } },
  "decidedBy": "<D-0 表1「体制と運用形態」の決定者の氏名>",
  "reason": "<任命の理由>"
}
JSON
```

| キー | 内容 |
| --- | --- |
| `kind` | 上表の種別。必須 |
| `date` | 発効日(YYYY-MM-DD)。省略すると実行日(手元の時刻帯の日付。協定世界時の日付ではない)。記録には、記録した時刻 `at`(オフセットつき)も残る。**暦に実在する日付で、今日以前、かつ最後の記録の日付以降に限る** |
| `summary` | 何が変わったかを1行で |
| `answers` | 変える軸の回答だけを書く。書かなかった回答は現在の値を引き継ぐ |
| `people` | 人の名簿。**書くと名簿の全体を置き換える**。`{ "id", "name", "external", "appointer", "accounts", "nameConfirmed" }`。`external: true` は外部の確認者(体制の人数に数えない)。`appointer: true`(`external: true` と併用)は組織上の任命権者。確認者ではなく、席の責任者にもしない。決定者が体制に残っている間に任命権者を名簿へ置くのは、決定者の記名を要する。席の責任者でない担い手(人)も記入する。`accounts` は、リポジトリ上のアカウントの配列。承認したアカウントを名簿の人へ対応づけるために使う。未記入の人の承認は、出荷判定の証跡で「独立した人の確認」に数えない。bot のアカウントと、1つのアカウントを2人へ書く記入は拒否される。`nameConfirmed: true` は、AI を示す語に当たる実在の氏名を、人が確認した旨。**利用者が明示した場合にだけ書く** |
| `seats` | 席(ロール ID)ごとに、変える欄だけを書く。`accountable` / `mode` / `performer` / `fallback` / `qualification` |
| `delegation` | `rules`(委任の規則)、`changeTypes`(標準変更カタログへ登録した変更種別)、`protectedPaths`(確約範囲とコア指定のパス)。**書いた一覧は、全体を置き換える** |
| `governance` | D-0 表1 の2行の決定者の席と、品質保証部門の通知先。`{ "structureDecider": "<席のロール ID>", "catalogRegistrar": "b4" または "<席のロール ID>", "qaNotice": "<部門の通知先>" }`。決定者の席を変えるのは、変更前の「体制と運用形態」の決定者に限る(記名と理由を要する)。`qaNotice` は任意。定めるのは厳しくする向き、外すのは緩める向き(`null` で外す) |
| `decidedBy` / `reason` | 決定した者の氏名と理由。**緩める向きと任免では必須**。緩める向きは、対象の席の責任者、または D-0 表1「体制と運用形態」の決定者に限る。任免は、変更前の決定者(体制から外れていれば組織上の任命権者)に限る |
| `takeover` | 席の責任者の交代の後、新しい責任者がその席の委任を引き継ぐ。値は席のロール ID。`decidedBy` は、その席の(新しい)責任者に限る。1つの入力で、適合性確認の承認し直し、その席の規則の決定の記名のし直し(前任の記名は `priorDecision` に残る)、委任への復帰を受け付ける。同じ席の `accountable` と同時には書けない(任命を先に反映する) |
| `ruleApprovedBy` | 委任の規則の追加・範囲の拡大を承認した者。**AI維持管理者の席の責任者に限る**。追加・拡大した規則と、承認待ちの規則へ記録される。規則の入力に書いた `approvedBy` は使わない |
| `sgRecord` | ステージを前へ戻す変更で、ステージ移行ゲート(SG)の判定記録の所在。**`docs/gates/` 配下の実在する判定記録(.md)**を書く |
| `notice` | 即時通知の記録。`{ "to": "<出荷判定者の席の責任者の氏名>", "at": "<通知日>" }`。前任者・決定者・品質保証部門への通知先は、構成から自動で記録される(`also`)。手順7 を参照 |
| `invalidatedChecks` | 無効になった確認と、やり直しの要否。手順5 で決めたものを書く |
| `recheckDue` | 失効した適合性確認・例外の、再確認の期日 |
| `d0Version` | D-0 体制図の新しい版。省略すると、末尾の数字を1つ進める(`1.2` → `1.3`)。人が先に frontmatter の版を上げていれば、その版を使う。**版を下げる指定は拒否される**。版を上げるとき、frontmatter の `approver` と `approved_at` は、この変化点の決定者と日付から書かれる |
| `outage` | 種別 `outage` でだけ使う。`{ "from", "to", "handling", "switched" }` |
| `settings` | 種別 `settings` でだけ使う。下記「個別の値を変える」 |
| `noticeFor` / `event` | 種別 `notice` でだけ使う。手順7 を参照 |

席の欄の値は次のとおりです。

| 欄 | 値 |
| --- | --- |
| `accountable` | 責任者。人の名簿の氏名または `id`。**記名の自然人に限る** |
| `mode` | `human`(人確定) / `collab`(協働) / `delegated`(委任)。**上限の宣言**であり、変更ごとのリスク区分の判定が下げる |
| `performer` | `{ "model": "<モデルの版>", "instructions": "<指示資産の版>", "permissions": "<権限の組>" }`。人が担う席は `null` |
| `fallback` | AI が使えないときの扱い。`human`(人へ戻す) / `stop`(止める) |
| `qualification` | 適合性確認の記録。`{ "confirmedAt", "performedBy", "approvedBy", "cases", "result", "performer" }`。`confirmedAt` は変化点の発効日以前の、暦に実在する日付に限る。`performer` には確認した担い手の識別を書く。**`performedBy`(実施者)は AI維持管理者の席の責任者、`approvedBy`(承認者)は当該の席の責任者に限る**(標準 第3章 3.4.2)。どちらも名簿と照合される。席の責任者が交代して承認が失効した場合は、`{ "approvedBy": "<新しい責任者の氏名>" }` だけを書くと、既存の確認の記録を承認し直す(確認の再実施は要らない) |

指示資産の版は、末尾へ `@<識別子>` を書くと、契約検査が実ファイル(`CLAUDE.md`・`AGENTS.md`・`.claude/`)と照合します。識別子は次で得ます。識別子を伴わない申告は照合されず、自己申告として表示されます。

```bash
node scripts/gate/verify-gate-contract.mjs --instructions-digest
```

#### 委任の範囲

委任の規則は、観測できる属性で登録します。

```json
"delegation": {
  "changeTypes": [{
    "id": "表示文言", "registeredBy": "<氏名>", "registeredAt": "2026-10-01",
    "basis": {
      "detection": "<第5章 5.4.6 の検知条件を何で計測するか>",
      "rollback": "<取り消しを実行した実績の所在>",
      "tests": "<既存のテストで検出できることの根拠>"
    }
  }],
  "protectedPaths": ["src/core/**"],
  "rules": [
    { "id": "DR-001", "seat": "dev-verifier", "changeType": "表示文言", "paths": ["src/i18n/**"], "excludePaths": [], "decidedBy": "<氏名>", "decidedAt": "2026-10-01", "reason": "<理由>" }
  ]
}
```

- `changeTypes` は、**標準変更カタログ(標準 第3章 3.7.4)に登録した変更種別**の一覧です。規則の `changeType` は、この一覧にあるものだけを受け付けます。任意の文字列は通りません
- **登録の根拠(`basis`)の3点が無い種別は、登録できません**(標準 第5章 5.5.4)。`detection` は 5.4.6 の検知条件を何で計測するか、`rollback` は取り消しを実行した実績の所在(条件4)、`tests` は既存のテストで検出できることの根拠(条件3)です。**機械が確かめるのは記入の有無だけです**。内容が足りるかは、登録する者が判定します。根拠を利用者から受け取らずに、エージェントが書いてはなりません
- 登録した者(`registeredBy`)は、D-0 表1「標準変更カタログへの登録」の決定者です(`governance.catalogRegistrar`)。既定は、1〜2名の体制では「体制と運用形態」の決定者、3名以上ではリリース判定会(B-4)です。B-4 の場合、登録した者が名簿にいることだけを確かめます。**B-4 の構成員であるかどうかは、機械では確かめません**。**B-4(既存のリリース会議への対応づけを含む)を置かない体制では、`governance` で `catalogRegistrar` を決定者の席(例: `biz-approver`)へ改めます**(変更前の決定者の記名と理由を要する)。登録の出力にも案内が出ます
- `protectedPaths` は、確約範囲とコア指定のパスです。登録したパスに触れる変更は、委任の対象になりません(標準 第5章 5.5.4 条件5)。**宣言するまで(キーが無いあいだ)は、条件5 を判定できないため、どの変更も委任に該当しません**。該当するパスが無い案件は、空の配列 `[]` を宣言します。最初の宣言と、パスを外す変更は、緩める向きの決定です(D-0 表1「体制と運用形態」の決定者の記名と理由を要する)。どのパスが確約範囲・コア指定に当たるかを、エージェントが決めてはなりません
- `paths` に、リポジトリの全域(`**`)、ルート直下の全体(`*`)、先頭の階層を特定しない指定(`**/*.md`)は書けません
- 強制層・構成の正本・判定の記録(`.claude/`、`.github/`、`scripts/gate/`、`process.config.json`、`docs/gates/` など)は、規則に当たっても委任の範囲へ入りません。確約範囲・コア指定のパスと重なる規則も同じです。こうしたパスを指す規則は登録できますが、出力に `[警告]` が出ます
- `decidedBy` は、対象の席の責任者、または D-0 表1「体制と運用形態」の決定者に限ります。責任者が交代したときは、新しい責任者が規則を確かめて記名し直すまで、席は協働へ下がります
- **規則の検査(全域の指定、変更種別、決定した者の名義)は、席を委任にするかどうかに依らず、書き込む前に行われます**。要件を満たさない規則を、先に登録しておくことはできません
- 独立レビュー(G-6)の判定の時点が事後へ移るのは、**独立レビュアの席が委任で、その席の規則に該当し、PR のリスク区分が R3 と記録された変更だけ**です。開発者の席の規則だけでは、G-6 の承認は免除されません

#### AI が使えない期間

次の形で記録します。構成は変わりません。

```json
{ "kind": "outage", "summary": "提供者の障害", "outage": { "from": "2026-10-01", "to": "2026-10-02", "handling": "human" } }
```

| 欄 | 値 |
| --- | --- |
| `from` / `to` | 期間。`to` は継続中なら省略する(「継続中」と記録され、保証の開示にも「継続中」と出る)。終了日を開始日より前にはできない |
| `closes` | 継続中の期間を、後から閉じる。開始の記録の `changeLog[]` の添字と、`to`(終了日)を書く。`handling` は、開始の記録と違う場合にだけ書く。**開始の記録は書き換えず、終了日を持つ記録を足します**。例: `{ "kind": "outage", "summary": "提供が戻った", "outage": { "closes": 5, "to": "2026-10-04" } }` |
| `handling` | その間の扱い。`human`(人へ戻した) / `stop`(止めた) |
| `switched` | 別の担い手へ一時的に切り替えた場合は `true`。**切り替えの間は担い手の識別が変わるため、委任を協働へ下げます**。切り替えが終わっても自動では戻りません。戻すときは、種別 `mode` で緩める向きの手続を経ます |
| `seats` | 切り替えた席のロール ID の配列。省略すると、委任を宣言している全席を協働へ下げる |

#### 個別の値を変える

アダプタ、CI の下限、変更規模の上限、強制層の緩和設定、配布先、確認者の調達先は、種別 `settings` で変えます。**`process.config.json` を直接編集しません**。

```json
{ "kind": "settings", "summary": "技術スタックを確定した", "settings": { "stack": "node" } }
```

| 欄 | 値 | 向き |
| --- | --- | --- |
| `stack` | アダプタ(`adapters/<stack>.json` があるもの) | 技術判断者の判断。判断記録(ADR)を残す |
| `projectId` / `profileName` | 案件 ID、プロファイル名 | — |
| `ci.coverageThreshold` | カバレッジの下限(0〜100) | **下げるのは緩める向き** |
| `ci.failOnSeverity` / `ci.allowedLicenses` | 失敗させる重大度、許可するライセンス | **重大度を外す、ライセンスを足すのは緩める向き** |
| `task.maxChangedLines` / `maxChangedFiles` / `selfHealMaxIterations` | 変更規模と反復の上限 | **上げるのは緩める向き** |
| `guard` | 強制層の緩和設定。`{ "enabled", "reviewBy", "reason" }`。消すときは `null` | **無効にする、期限を延ばすのは緩める向き**。期限と理由を要する |
| `platform.host` / `platform.hostUrl` | 成果物の配布先 | — |
| `reviewSourcing` | `{ "g6": "<確認者の調達先>" }`。`node scripts/init/set-review-sourcing.mjs` も、この経路で記録する | — |

緩める向きの決定をできるのは、AI維持管理者の席の責任者、または D-0 表1「体制と運用形態」の決定者です。カバレッジの下限は、較正していない値(導出値のまま)に限り、代償措置で導出値が上がると自動で追随します。導出値が下がっても、自動では下げません。

テンプレートや知識ベースを更新して、構成の導出が変わる場合も、空の `settings` で再導出します(`{ "kind": "settings", "summary": "テンプレートの更新を反映する" }`)。

| 不変条件に反する | AI を利用しない構成で CL2 以上、など。**1〜2名で CL1 以上・規制業になる変化点は拒否されません**(下記「出荷できない状態」) |

#### 出荷できない状態

安全重要度 CL1 以上、または規制業の案件で、体制が3名を割った場合、スクリプトは**拒否せずに反映し**、構成へ `shipBlocked: { reason, since }` を立てます。旧い構成のまま止めると、実態と構成が食い違うためです。出力に `[出荷不可]` が出ます。

- 契約検査・D-0 の検査・構成書・`CLAUDE.md` の生成区間に表示され、**出荷判定(G-7)の証跡の集約は失敗します**
- 体制を3名以上へ戻す変化点で解除されます。選択肢は、体制を確保する、危害の帰結を設計で下げて区分を下げる(記録を要する)、当該の機能を実施しない、の3つです。**どれを選ぶかをエージェントが決めてはなりません**
- 初期化(`/process-init`)で最初から 1〜2名 × CL1 以上を宣言する場合は、これまでどおり拒否されます

### 5. 向きに応じて進める

| 向き | 扱い |
| --- | --- |
| 厳しくする向きだけ | 即時に適用する。判定を待たない |
| 未達・逸脱の発生 | **即時に適用する。記名を要求しない**。旧い構成のまま止めない。未達のまま出荷するかどうかは、標準 第7章 7.3 の例外承認による(CL1 以上と規制業は不可) |
| 緩める向きを含む | **決定した者の記名と理由を利用者から受け取り**、`decidedBy` と `reason` へ書く。受け取るまで適用しない |
| ステージを前へ戻す | **ステージ移行ゲート(SG)の判定による**。D-0 表1「体制と運用形態」の決定者の記名を要する。判定記録(`docs/gates/` 配下の実在する判定記録)の所在を `sgRecord` へ書く |
| 任免の決定 | **変更前の決定者(体制から外れていれば組織上の任命権者)の記名と理由を利用者から受け取る**。向きは「任免の決定」と記録される。受け取るまで適用しない |
| 構成の変更なし | そのまま適用する。「構成の変更なし」が記録される |

**「発生」として扱うのは、人が実際に減った場合に限ります**(名簿の体制内の人が減った、または席の責任者が名簿から外れた)。見分けは次のとおりです。

| 変化 | 扱い |
| --- | --- |
| 人が離脱し、チーム規模の回答が下がった結果、G-7 が兼務になる、承認数が変わる | 発生。記名を要求しない |
| 人が離脱し、作成を指示する席の責任者のほかに、確認できる人が名簿に残っていない結果、G-6 が未達になる | 発生。記名を要求しない |
| 人が離脱し、空いた席を残った人が引き取る | 離脱は発生。**引き取り(後任の配置)は任免の決定であり、決定者の記名を要する**。離脱だけを先に反映してもよい |
| **誰も離脱していないのに、回答を「確認者なし」へ変える、独立レビュアの席を開発者と同じ人にする** | **緩める向きの決定**。記名と理由を要する。相手も作成の指示に関与するため確認者になれない、といった理由を、決定者が書く |
| 人が離脱したが、確認できる人が名簿に残っているのに、独立レビューを置かない | 緩める向きの決定 |
| 1名の体制で、全席を同じ人が兼ねる | 兼務には選択の余地がない。逸脱として記録される。ただし全席が未記入の状態からの記入そのものは任免であり、本人の記名と理由を要する(初回の記入) |
| 2名の体制で、相手がいるのに、AI維持管理者と AI運用担当者を同じ人が兼ねる | 緩める向きの決定 |

**1人 → 2人になったときは、席を書き換えるだけでは足りません**。回答 `q-external-reviewer` が「確認者なし(`reviewer-no`)」のままだと、G-6 は未達のまま残ります。作成を指示していない側の人が確認できるなら、`answers` で `reviewer-yes` へ改め、独立レビュアの席の責任者を相手にします。該当する場合、残作業に案内が出ます。

**AI の担い手の識別を変えると、適合性確認の記録は失効します**。新しい版を採用する前に確認を済ませておき、識別の変更と同じ変化点で記録を出すことはできます。その記録で委任を続けられるのは、次の4つをすべて満たす場合だけです。1つでも欠ければ、席は協働へ下がります(出力に `[即時反映]` と、欠けたものが出ます)。

1. 記録の担い手の欄(`performer`)が、新しい識別と一致する
2. 旧い記録の使い回しでない(確認日 `confirmedAt` が、旧い記録の確認日より後である)。旧い確認記録の欄を書き換えて出したものは受け付けられず、`[無効]` と出ます
3. 実施者が AI維持管理者の席の責任者、承認者が当該の席の責任者である
4. 当該の席の責任者が、新しい識別で委任を続ける決定として記名し、理由を書く(`decidedBy`・`reason`)

条件4 の記名は、**当該の席の責任者に限ります**。D-0 表1「体制と運用形態」の決定者の記名では、協働へ下がります。

**適合性確認を承認した席の責任者が交代した(離脱を含む)とき、承認は新しい責任者へ引き継がれません**。変化点は拒否されず、席は協働へ下がります。出力に「適合性確認の承認者が交代したため、承認が失効(記録は有効。新しい責任者の承認を要する)」と出ます。失効するのは承認であり、担い手の識別が変わっていなければ、確認の記録(事例と結果)は有効なまま残ります。**確認を実施した者が体制から外れても、記録は有効です**。確認の再実施は要りません。

席の規則も、前任の責任者の記名のままでは働きません。**新しい責任者が委任を引き継ぐときは、`takeover` で1つの入力にまとめます**。適合性確認の承認し直し、その席の規則の決定の記名のし直し、委任への復帰を、新しい責任者の記名と理由で受け付けます。AI維持管理者も交代していれば、新しい AI維持管理者の `ruleApprovedBy` を同じ入力へ書けます。

```json
{ "kind": "mode", "summary": "新しい責任者が開発者の席の委任を引き継ぐ", "takeover": "dev-verifier", "decidedBy": "<新しい責任者の氏名>", "reason": "<確認の記録と規則を読んで確かめたこと>" }
```

承認だけをし直して委任へは戻さない場合は、`{ "seats": { "dev-verifier": { "qualification": { "approvedBy": "<新しい責任者の氏名>" } } } }` を書きます(記名は要りません)。

**AI維持管理者の席の責任者が交代したとき、前任者が承認した規則は承認待ちへ戻ります**(出力に `[承認待ちへ戻る]`)。規則を消して足し直す必要はありません。席の委任の決定は変わらないため、宣言として保持され、新しい AI維持管理者が `ruleApprovedBy` だけを書いた変化点で委任へ戻ります。

```json
{ "kind": "mode", "summary": "新しい AI維持管理者が規則を承認し直す", "ruleApprovedBy": "<新しい AI維持管理者の氏名>" }
```

**委任は、2つめの記名で有効になります**。席の責任者が委任を宣言し(`seats.<席>.mode: "delegated"` と `decidedBy`・`reason`)、規則が AI維持管理者の承認待ちであるあいだ、宣言した意図と決定者は構成に保持されます(出力に `[宣言を保持]`)。承認待ちのあいだは協働として動きます。AI維持管理者の承認(`ruleApprovedBy`)だけを書いた変化点で、委任が有効になります(出力に `[委任を有効化]`)。**宣言し直す必要はありません**。宣言の後で、担い手の識別が変わった場合と、宣言した者がその席の決定者でなくなった場合は、保持していた宣言は取り下げられます(`[宣言の失効]`)。

席の責任者の宣言が無いまま、規則の承認だけが入った場合は、席は協働のまま残ります。出力に `[協働のまま]` と、残っている手続(席の責任者の記名と理由をつけて、席を委任にする)が出ます。

**未承認の規則を足しても、承認済みの既存の規則による委任は協働へ落ちません**。承認待ちになるのは、足した規則だけです。その規則では委任は働かず、席は、承認済みの規則の範囲で委任のままです。出力に、規則ごとの `[承認待ち]` が出ます。

**承認済みの規則の範囲を広げたときは、承認済みの範囲が有効なまま残り、広げた部分だけが承認待ちになります**(出力に `[拡大は承認待ち]`。構成では `pendingChange`)。AI維持管理者の承認(`ruleApprovedBy`)が入った変化点で、拡大が反映されます(`[拡大を反映]`)。承認だけの変化点で委任が広がる・有効になる場合も、向きは「緩める」として記録され、決定した者には拡大・委任を宣言した者が記録されます。

無効になった確認の候補を文脈オーナーへ示し、やり直しの要否を決めてもらいます。決まった内容を `invalidatedChecks` へ書きます。

```json
"invalidatedChecks": [{ "target": "PR #12 の独立レビュー", "redo": true }]
```

### 6. 適用する

```bash
node scripts/init/generate-profile.mjs --change /tmp/change.json
node scripts/gate/verify-gate-contract.mjs
node scripts/gate/check-d0.mjs
node scripts/gate/check-process-rules.mjs
```

次が書き換わります。**どれも手で編集しないでください**。

| ファイル | 書き換わるもの |
| --- | --- |
| `process.config.json` | 構成と、`changeLog[]` への追記(要約値つき) |
| `PROCESS-PROFILE.md` | 全体 |
| `CLAUDE.md` | 生成区間(`<!-- generated:process-rules -->`) |
| `docs/D-0-governance.md` | 生成区間(節1・節12・節13)、節3 の2行の決定者、frontmatter の `version` |

D-0 の検査は、生成区間が構成と一致することを確かめます。一致しない体制図は失敗します。D-0 だけを手で改訂した状態も、構成だけを変えた状態も、ここで検出されます。

構成を変えずに、生成物だけを作り直す場合は、次を実行します。構成が変わる再生成(引数で値を変える、回答を変える)は拒否されます。

```bash
node scripts/init/generate-profile.mjs --answers process.config.json
```

### 7. 即時通知を記録する

次の変化点は、**出荷判定者の席の責任者へ即時に知らせる対象**です(標準 第3章 3.13.6)。出力に `[即時通知]` が出ます。

| 対象 | 検出 | 通知する者 |
| --- | --- | --- |
| 人数の境界の通過 | チーム規模の回答が変わった | 文脈オーナー |
| 運用形態の変更 | いずれかの席の運用形態が変わった(引き下げを含む) | 対象の席の責任者 |
| 検出の層に数えている AI の担い手の識別の変更 | いずれかの席の担い手の識別が変わった(検出率の測定値が失効する) | AI維持管理者と AI運用担当者 |
| 承認権限の一時制限(標準 第7章 7.9)の発動 | 構成に現れないため、種別 `notice` で記録する | 発動を記録した者 |
| 独立レビュー(G-6)が成立から未達・成立しないへ変わる変化 | G-6 が適用・未達なしから、未達または適用しないへ変わった(2名のままの変化を含む) | 文脈オーナー |
| 出荷判定者の席の責任者の交代 | 出荷判定者の席の責任者が替わった、または空いた | 文脈オーナー |

通知先は出荷判定者の席の責任者です。**出荷判定者の席の責任者の交代では、前任者にも知らせます**。前任者が体制から外れている場合は、D-0 表1「体制と運用形態」の決定者へ知らせます。**出荷判定者の席が空いた場合は、前任者(名簿に残っていれば)、D-0 表1 の決定者、品質保証部門の通知先(`governance.qaNotice`)の順に通知先を決めます**。いずれも無ければ、「通知する者と通知先が同一」として自動で記録します(`notice.noTarget`)。通知先の記名は、名簿の人へ正規化して記録します(「山田太郎」は「山田 太郎」として記録)。品質保証部門の通知先を `notice.to` へ書けるのは、人の通知先が無い場合と、通知する者と人の通知先が同一の場合です。名簿の人でない名義は、そのまま記録し、表示で区別します。品質保証部門の通知先(`governance.qaNotice`)を定めていれば、すべての即時通知をそこへも送ります。前任者・決定者・部門の通知先は、構成から `notice.also` へ自動で記録され、`notice.at` の日にあわせて送ったものとして扱われます。

**通知する者と通知先がすべて同一人物の場合(1人体制など)は、通知の入力を求めません**。「通知する者と通知先が同一」と自動で記録し(`notice.self`)、出力と D-0 の改訂履歴に表示します。部門の通知先を定めている場合は、部門へ送った日(`notice.at`)を記録します。

**エージェントが通知を済ませたことにしてはなりません**。通知先と通知日は、利用者から受け取ります。

通知が済んでいれば、変化点の入力へ書きます。

```json
"notice": { "to": "<出荷判定者の席の責任者の氏名>", "at": "2026-10-01" }
```

適用の後で通知した場合は、過去の記録を書き換えず、種別 `notice` の記録を追記します。`noticeFor` は、対象の記録の `changeLog[]` の添字です(契約検査の注意と、適用時の残作業に出ます)。

```json
{ "kind": "notice", "summary": "出荷判定者の席の責任者へ知らせた", "noticeFor": 3, "notice": { "to": "<氏名>", "at": "2026-10-02" } }
```

承認権限の一時制限の発動は、次の形で記録します。

```json
{ "kind": "notice", "summary": "注入した欠陥を連続2回見逃した", "event": "restriction", "notice": { "to": "<氏名>", "at": "2026-10-02" } }
```

**通知先と通知日が未記入の即時通知は、出荷判定の証跡の集約が、記録の欠落として扱います**。

### 8. 残作業を利用者へ渡す

手順4 の「残作業」を、実行せずに提示します。ブランチ保護の適用コマンド、発行・失効させる認証情報、適合性確認、即時通知です。

- **委任の形は2つあります**。開発者の席の規則にだけ該当する変更は、変更ごとの検証を担い手が行い、独立レビュアが人として事前に承認します。現在のブランチ保護のままマージできます。独立レビュアの席の規則にも該当する変更(G-6 の判定の時点を事後へ移す委任)は、マージの実行が既定で無効であり、組織が有効化するまで協働として扱い、人の承認を待ちます。該当は、ワークフローが既定ブランチの構成と規則で判定します(行為する AI 自身には判定させません)。トレーラ `Delegated: <規則ID>` は、どちらの形でも書きます
- 委任の規則を登録したのに、確約範囲とコア指定のパス(`delegation.protectedPaths`)が未宣言の場合、残作業に「登録する(無ければ、空の一覧を明示する)」が出ます。未宣言のあいだ、どの変更も委任に該当しません
- 委任の規則を追加・拡大したときは、規則の変更を AI維持管理者へ引き渡します(`state:needs-platform`)。出力に `[承認待ち]` が出ているあいだ、その規則では委任は働きません。承認を受け取ったら、`ruleApprovedBy` を書いた変化点(種別 `mode`)で反映します。**差分が変更の主張と一致するかの確認までに留め、許容してよいかを判断しないでください**
- 安全重要度が上がり委任を適用できなくなったときは、**抜き取り待ちの委任の変更を、協働の手続で全件確認し直します**
- 責任者が未記入の席が、適用するゲートの判定者である場合、そのゲートは判定できる人がいないまま止まります。後任を置く、外部の確認者を置く、残った人が兼ねる、のいずれかを利用者に決めてもらいます

### 9. コミットする

トレーラは、メッセージの末尾の段落に書きます。`/process-change` が強制層(`.claude/guard.json`・`.claude/settings.json`)を書き換えた場合、コミットは記録だけのコミットに当たらないため、PR を経ずにコミットするなら `Risk` と `Verification` が要ります。`Verification` には、手順6 の3つの検査の結果を書きます。

```
chore: 体制の変化点を反映する(<種別>)

- <summary>
- 向き: <緩める / 任免の決定 / 厳しくする / 未達・逸脱の発生 / なし>。決定: <decidedBy>

Risk: R2
Verification: verify-gate-contract・check-d0・check-process-rules が通過
```

## 旧い構成からの移行

変化点の記録に要約値を持たない構成(このテンプレートの更新より前に生成した構成)は、契約検査が失敗します。**最初の `/process-change` で、要約値の連鎖が始まります**。

1. 変える内容が無ければ、空の `settings` を適用する(`{ "kind": "settings", "summary": "要約値の連鎖を始める" }`)。出力に `[連鎖の開始]` が出る
2. 連鎖より前の構成と記録は、書き換えの有無を検証できない。その旨が、連鎖の起点の記録(`chainStart`)として残る。以後は、連鎖より前の記録の書き換えも検出される
3. D-0 体制図へ、生成区間の目印(`templates/00-d0-governance.md` の節1・節12・節13)と、節3 の2行(「体制と運用形態」「標準変更カタログへの登録」)を写し、`node scripts/init/generate-profile.mjs --answers process.config.json` で区間を書き込む。連鎖が始まった後は、目印の無い体制図を D-0 の検査が失敗させる
4. 既存の委任の規則がある場合は、規則の変更種別を `delegation.changeTypes` へ登録する(種別 `mode`)。登録が無いあいだ、その規則では委任は有効にならない
5. 名簿へ、リポジトリ上のアカウント(`accounts`)を記入する
6. 名簿(`people[]`)が未記入の構成は、現在の体制の名簿を先に記入する。人が減ったかどうかは、名簿の変化から確かめる。名簿が無いあいだは、人の離脱を「発生」として扱えず、緩める向きの決定も受け付けられない

## やってはならないこと

- **`process.config.json` を手で編集すること**。要約値(`stateHash`・`prevHash`)を書き換えて、検査を通すこと
- **成立済みの判定記録(`docs/gates/`)を書き換えること**。変化点より前の記録は、当時の D-0 の版を参照したまま残す。変化点をまたぐ未完了の判定は、新しい体制の判定者が引き継ぐ
- D-0 体制図の生成区間を手で編集すること
- 最初のゲート判定より後へ、反映を先送りすること。改訂前の D-0 を参照した判定記録は、出荷判定の証跡の集約が欠落として扱う
- 決定した者の氏名と理由を、推測で書くこと。**自分(AI)の名義を書くこと**
- 人の名簿へ、利用者から受け取っていない名前やアカウントを足すこと。離脱していない人を名簿から外して、未達・逸脱を「発生」に見せること
- 通知先と通知日を、利用者から受け取らずに書くこと
- `changeLog[]` の記録を消すこと、書き換えること
- 適合性確認を経ていない担い手を、委任で運用すること。担い手の識別が変わったら確認は失効し、再確認と、席の責任者の記名があるまで協働が上限になる
- 委任の規則に当たるかどうかを、エージェントが自分で判定すること
- 未達・逸脱の発生を、記名が無いことを理由に反映せず、旧い構成のまま進めること
- 拒否を回避するために、種別や回答を書き換えること
