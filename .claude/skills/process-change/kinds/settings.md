# 種別 settings: 個別の値を変える

変化点に数えません。D-0 の版は上げません。主に変わるもの: `adapters`、`ci`、`task`、`guard`、`platform`、`unmet[].reviewSourcing`。**`process.config.json` を直接編集しません**。

```json
{ "kind": "settings", "summary": "技術スタックを確定した", "settings": { "stack": "node" } }
```

- 緩める向きの決定をできるのは、AI維持管理者の席の責任者、または D-0 表1「体制と運用形態」の決定者。記名と理由を利用者から受け取る(`decidedBy`・`reason`)
- **基準値(カバレッジの下限・失敗させる重大度・除外設定)の変更は、標準では技術判断者の承認を要する**(第4章 G-5「基準値と除外設定の変更」)。機械が受け付ける記名は上の行のとおりで、技術判断者の承認の有無は確かめない。記名する者が技術判断者でない場合は、技術判断者の承認を得たことを理由(`reason`)に書く
- カバレッジの下限は、較正していない値(導出値のまま)に限り、代償措置で導出値が上がると自動で追随する。導出値が下がっても、自動では下げない
- テンプレートや知識ベースの更新で構成の導出が変わる場合も、空の `settings` で再導出する(`{ "kind": "settings", "summary": "テンプレートの更新を反映する" }`)
- **製品のすべてのスタックを宣言する**(標準 第4章 G-5「製品のすべてのスタック」)。`stack` のアダプタが受けるのは、そのスタックと `projectDir` の組だけ。複数のスタックやアダプタの外の言語は、`none` を選び、`adapters/none.json` に全スタックのコマンドと `stacks`(`[{ "stack", "path", "coverageSummary" }]`)を人が書く。`coverageSummary` の無い要素は基準3 の未実施として G-5 が失敗する(要素ごとに基準値と比べ、合算しない)。宣言を検出の結果で埋めない。アダプタ(`stacks` を含む)の変更も、製品のコードと別の PR に分ける(閾値・除外設定と同じ扱い)。製品でないパスの除外は `.github/stack-exclusions.json`(パス・区分 `non-product`・理由・名簿の人の記名 `decidedBy`)で、統制の設定の変更として別の PR に分ける。AI は記名しない。よくある誤検出の型は、`projectDir` を下の階層に置いたときの直下の道具の設定(`eslint.config.js`・workspace の `package.json`)と、Sphinx の `docs/conf.py`。製品でなければ、そのファイルを除外の一覧へ載せる
- ライセンスの許可リストの恒久の追加は法務の所管。技術判断者・AI維持管理者の裁量で行わない

## 閾値の変更は、製品のコードと別の PR にする(第4章 G-5「基準値と除外設定の変更」)

`ci`・`task`・`guard` を変える変化点を、製品のコードの変更と同じ PR に入れると、G-5 の `pr-rules`(`scripts/gate/check-pr.mjs`)が失敗します。閾値だけの PR として出します。変更規模の上限は**基底ブランチの**構成から読まれるため、上限を上げた PR がマージされるまで、新しい上限は効きません。

## 規模の基準値を変えるとき

基準値の値は暫定です。自組織の実測による較正(観測は四半期、更新は半期以上。充足率が8割を下回らない最大の区間)は人が判断します。**較正の手続を自動化しません**。出荷の集約が、規模の分布・`size:over` の件数・「読み切れたか」の内訳・超過 PR の判定完了時間を出します(基準値へ自動で反映しません)。

超過したまま一度だけレビューする場合も、基準値を上げません。PR の「規模の確認」の欄を書きます(例外承認は要りません)。例外承認は、R2 以上の規範を満たさない場合のために残っています。

## 担保水準の宣言(task.assurance)

```json
{ "kind": "settings", "summary": "担保水準 L1 を宣言した", "settings": { "task": { "assurance": { "level": "L1", "basis": "docs/assurance/f-001.md", "declaredBy": "<氏名>", "declaredAt": "YYYY-MM-DD", "reviewAt": "YYYY-MM-DD" } } }, "decidedBy": "<氏名>", "reason": "<理由>" }
```

- 水準は自己申告でなく、条件の充足を示す記録の所在(`basis`)で宣言します。`basis` が実在しなければ、書き込みを拒否します
- L1 以上で根拠が実在するとき、規模の確認は「保証の所在」の記入だけで足ります
- 見直し日を過ぎた宣言は L0 として扱い、G-5 が通知します

### L2 の宣言の根拠を読む(確かめる者: 変化点の決定者)

標準は L2 の採点の運用が稼働していることを機械で検証することを課しません(標準 第4章「担保水準」、標準の ADR-0124 決定6)。機械が確かめるのは `basis` のパスの実在と見直し日だけです。根拠が条件の充足を**記録で示しているか**は、`task.assurance` を L2 へ変える変化点の決定者(`decidedBy`)が、書き込みの前に根拠の中身を読んで確かめます。L2 の宣言を伴う変化点の記録を AI の担い手が起案するときも、この確認は人が行い、AI は確認済みと書きません。

1. `basis` の文書を開き、次の2つの条件のそれぞれについて、条件を満たす運用の**記録**(採点の出力・閾値・審査深度を変えた実績・取り消しの手順と実施の記録など)の所在が書かれているかを読む
   - 変更のリスクを機械的に採点し、閾値で審査深度を変える運用が稼働している
   - 取り消し可能性が担保されている
2. 所在の書かれた記録を開き、記録が条件の文に当たる事実を示しているかを読む。方針・計画・「稼働している」の記述だけで、運用の記録を示していない根拠は、条件を満たさない
3. 片方でも示されていなければ、L2 を宣言しない(L1 以下で宣言するか、記録を揃えてから宣言する)。示されていれば、`reason` に、読んだ記録の所在を条件ごとに書く(例: `L2: 採点 docs/assurance/risk-scoring-log.md、取り消し docs/assurance/rollback-drill.md を読んで確かめた`)
4. 見直し日(`reviewAt`)にも同じ手順で読み直す。規模の基準なし(`null`)が効いた PR には、G-5 が「担保水準の根拠の中身は機械で確かめていない」旨を毎回出す。これは、この手順の確認が機械の外にあることの開示である <!-- テンプレート独自: 標準は「変化点の決定者が根拠の中身を表の条件に照らして読む」を定め、読む手順と reason の書き方は定めない -->

## 能力依存の定数の再評価待ち

`/process-change` の出力の末尾と `/pit` の注記が、再評価待ちの能力依存の定数の件数を出します(`node scripts/gate/recalibration.mjs`)。契機は、種別 `performer` で記録したモデル・指示資産の版の変更と、半期の暦だけです。**値は自動で変えません**。人が「残す・外す・移す」を `docs/calibration-register.md` へ記名で記録します(`| RC-NN | 残す・外す・移す | YYYY-MM-DD | 氏名 | 移した先の保証 |`)。「外す」と「移す」は、外した後に失わない保証(移した先)を必ず書く。空の行は再評価の記録に数えない。
