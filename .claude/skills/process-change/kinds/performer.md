# 種別 performer: AI の担い手の識別と名義の変更

標準の番号: 4。モデルの版・提供者、指示資産の恒久層、ツールと権限、実行基盤のいずれかが変わったとき、または担い手の名義(専用・共有)を変えるとき。主に変わるもの: `seats[].performer`、`seats[].qualification`、`seats[].performerAccount`(下の「担い手の名義を変える」)。キーの一覧: `../reference/input.md`

```json
{
  "kind": "performer",
  "summary": "開発者の席の担い手のモデルの版を上げる",
  "seats": {
    "dev-verifier": {
      "performer": { "model": "<モデルの版>", "instructions": "<指示資産の版>@<識別子>", "permissions": "<権限の組>" },
      "qualification": { "confirmedAt": "2026-10-01", "performedBy": "<AI維持管理者の席の責任者>", "approvedBy": "<当該の席の責任者>", "cases": "<用いた事例>", "result": "<結果>", "performer": { "model": "<新しい識別>", "instructions": "<同>", "permissions": "<同>" } }
    }
  },
  "decidedBy": "<当該の席の責任者>",
  "reason": "<新しい識別で委任を続ける理由>"
}
```

- 指示資産の版は、末尾へ `@<識別子>` を書くと、契約検査が実ファイルと照合する。識別子は `node scripts/gate/verify-gate-contract.mjs --instructions-digest` で得る。識別子を伴わない申告は自己申告として表示される
- `.claude/` の指示資産(スキル・補助ファイルを含む)を変えると識別子も変わる
- 担い手の識別の変更は即時通知の対象(検出率の測定値が失効する。通知する者は AI維持管理者と AI運用担当者。`notice.md`)
- 適合性確認の記録・識別・権限の組は、利用者から受け取る。推測で書かない

## 適合性確認は失効する

**AI の担い手の識別を変えると、適合性確認の記録は失効します**。新しい版を採用する前に確認を済ませておき、識別の変更と同じ変化点で記録を出すことはできます。その記録で委任を続けられるのは、次の4つをすべて満たす場合だけです。1つでも欠ければ、席は協働へ下がります(出力に `[即時反映]` と、欠けたものが出ます)。

1. 記録の担い手の欄(`performer`)が、新しい識別と一致する
2. 旧い記録の使い回しでない(`confirmedAt` が、旧い記録の確認日より後)。旧い記録の欄を書き換えて出したものは受け付けられず、`[無効]` と出る
3. 実施者が AI維持管理者の席の責任者、承認者が当該の席の責任者である
4. 当該の席の責任者が、新しい識別で委任を続ける決定として記名し、理由を書く(`decidedBy`・`reason`)

条件4 の記名は、**当該の席の責任者に限ります**。D-0 表1「体制と運用形態」の決定者の記名では、協働へ下がります。

- 保持していた委任の宣言は、担い手の識別が変わると取り下げられる(`[宣言の失効]`。`mode.md`)
- 層1 項目4「AI の利用の拡大」の水準が `認めない` で始まる組織では、この種別でも席を委任にする入力(`mode: "delegated"`)は拒否される(構成の錠。`mode.md`)。担い手の識別の変更そのものは拒否されない
- 適合性確認を経ていない担い手を委任で運用しない。再確認と席の責任者の記名があるまで、協働が上限
- 認証情報: 担い手が専用の名義(担い手のためのアカウント・アプリ)で動く場合は、交代した担い手のトークンを失効させ、新しい担い手へ別のトークンを発行する(人が行う。残作業に出る)。担い手が人の認証情報で動く場合(名義の共有。標準 第3章 3.5.3)は、人の認証情報を失効させる操作は求めない。名義の申告(下の「担い手の名義を変える」)と照合(env-check)をやり直す
- 一時的な切り替え(障害の間だけ別の担い手を使う)は、この種別でなく `outage.md` の `switched`

## 担い手の名義を変える

担い手の**名義**は、担い手の操作を GitHub がどのアカウントの操作として記録するかです(標準 第3章 3.5.3「人と AI の担い手の名義」)。構成の `seats[].performerAccount` に書きます。

```json
{
  "kind": "performer",
  "summary": "開発者の席の担い手を、AI 専用のアカウントで動かす",
  "seats": { "dev-verifier": { "performerAccount": { "kind": "dedicated", "account": { "login": "<担い手のログイン名>", "id": 12345678 } } } }
}
```

| 値 | 意味 |
| --- | --- |
| `{ "kind": "dedicated", "account": { "login", "id" } }` | 専用。担い手の実行環境から使える認証情報で、名簿の人のアカウントとして承認・レビュー・`records` への push を作れない。ログイン名と数値の識別子(`gh api users/<ログイン名> --jq .id`)は人が確かめて書く。**担い手のアカウントを人の名簿に書かない**(契約検査が名簿の login・id との重なりを落とす) |
| `{ "kind": "shared", "person": "<名簿の id>" }` | 共有。名簿の人のアカウントで動く。実行環境の設定で拒否していても共有として申告する(拒否は抑止であり分離ではない) |
| `null`(欄を消す) | 未申告。担い手を宣言した席では、その席の責任者と名義を共有するものとして扱う |

- **変化点4 に数えます**。ただし名義は担い手の識別(モデル・指示資産・権限の組)に含めないため、**適合性確認は失効しません**。即時通知(識別の変更に限る)も出ません
- **専用と共有・未申告のあいだの切り替えは、どちらの向きも記名を要します**。当該の席の責任者が記名し、理由を書きます(`decidedBy`・`reason`。D-0 表1 の決定者の記名では受け付けません)。**AI の担い手が決めない**。専用から共有・未申告へは緩める向きです(ADR-0107 決定4)。共有・未申告から専用へは、列挙に無い離脱・G-6 の承認の印・効力を持つ記録の帰属の確認を外す変更のため、同じく記名を要します(ADR-0107 が定めていない逆向きを、記名を要する側に倒した)
- 専用の申告は、その席の担い手の環境での env-check の照合(`--seat <ロール>` を付けたもの)で確かめるまで、述べられる名では「名義の照合が無い」列挙に無い離脱として数えます。照合で名簿の人に当たった席は、申告が専用でも、その人と名義を共有する席として扱います
- 共有と未申告は列挙に無い離脱として表示し続けます(標準 第1章 1.10.2)。名義を共有する人の G-6 の承認は印を付けて数え、件数を保証の開示の項目1 に出します。例外承認・停止の解除などの効力を持つ記録は、記名者本人の操作だけでは帰属に数えず、名義を共有していない人の承認(帰属の確認)を要します
- 申告を変えたら、担い手の実行環境で `node scripts/gate/adoption-trial.mjs env-check --by <氏名> --seat <ロール>` を人が実行し(`--seat` を省いた照合は席ごとの判定に使わない)、認証したアカウントを名簿と照合します。名簿の人に当たった担い手を専用として扱いません。照合は実行した環境と時点に限ります
- 名義の値は利用者から受け取ります。**推測で書かない**。env-check の所見から、構成を書き換えない(提案を示し、人がこの種別で反映する)

## 退出の予行の記録(変化点ではない)

別の提供者のモデルで、評価用の基準集合の回帰評価を行った記録です(標準 第3章 3.12.3 の要求事項7)。**構成を変えないため、この種別でも `/process-change` でもなく**、AI運用担当者が `docs/exit-rehearsal.json` へ追記して PR で入れます(監査に提示できるよう、リポジトリへコミットする。`evidence/` は無視の対象のため置かない)。出荷判定の証跡の集約が読み、依存先の一覧と単一障害点の一覧(代替の無い依存先・退出を試していない依存先・自組織に無い資産)へ出します。

```json
{ "rehearsals": [ { "model": "<現行のモデルの版>", "provider": "<現行の提供者>", "alternative": { "provider": "<試した別の提供者>", "model": "<試したモデル>" }, "at": "2026-09-20", "baseline": "<基準集合の所在(リポジトリ内のパス)>", "diff": "<差分の記録の所在>", "approvedBy": "<代替として承認した AI運用担当者。承認しない場合は書かない>" } ] }
```

- 同じ提供者の世代交代の評価は、退出の予行に数えない(`provider` と `alternative.provider` が同じ記録は数えない)
- `approvedBy` が AI運用担当者の席の責任者のとき、その代替を「3.12.3 を通過した代替」に数える。AI の名義は数えない
- `baseline` がリポジトリ内に無い(URL など)場合は「自組織に無い資産」と出る
- 記録の値(差分の中身・評価の十分性)は機械が判定しない。値は利用者から受け取り、推測で書かない
- 予行の差分を AI の採点で求めた場合は、`"grading": "ai"` と、較正の記録 `judge`(下の「AI の採点者の較正の記録」と同じ形)を書く。無ければ「未測定」と出る(標準 第3章 3.12.13 の要求事項1 (a))

## モデルの導入の記録(変化点ではない)

新しいモデルを導入する前の回帰評価と、AI運用担当者の記名による承認の記録です(標準 第3章 3.12.3 の要求事項1〜4)。AI運用担当者が `docs/model-adoption.json` へ追記して PR で入れます。出荷判定の証跡の集約が読み、依存先の一覧の「導入の承認」へ出します。記録の無い構成は「導入の記録なし」と出ます(欠落にはしない)。

```json
{ "adoptions": [ { "model": "<導入するモデルの版>", "provider": "<提供者>", "replaces": "<現行のモデルの版。新規なら null>", "baseline": "docs/eval-baseline/", "evaluatedAt": "2026-10-03", "diff": "<現行モデルとの差分の記録の所在>", "approvedBy": "<AI運用担当者の席の責任者>", "approvedAt": "2026-10-04", "change": "<差し替えの PR の番号かコミット>", "grading": "ai | deterministic | human", "judge": { "<AI の採点者の較正の記録>": "grading が ai のとき" }, "unmeasuredAcceptance": { "by": "<層1 の権限者>", "until": "2026-12-31" }, "revisedAfterResults": [ { "case": "<事例の id>", "beforeResult": "<改める前の正解による結果>", "failToPass": false, "removed": false } ] } ] }
```

- 正解の目録は、基準集合の所在(`baseline`)の `answers.json` に置く。事例ごとに確定の記録を書く(標準 第3章 3.12.3 の要求事項11〜14・16):

```json
{ "cases": [ { "id": "C-1", "kind": "expected-output | verdict | rubric", "source": "external | past-judgment | new", "sourceRef": "<外部の観測・過去の判定の所在>", "seat": "<事例が再現する判断の席の role>", "confirmedBy": "<確定した人>", "at": "2026-09-20", "draft": { "model": "<草案を作ったモデルの版>" }, "revisions": [ { "from": "", "to": "", "reason": "", "confirmedBy": "", "at": "" } ] } ], "blindConfirmation": { "count": 0, "agreement": null } }
```

- `confirmedBy` は事例が再現する席の責任者(席が無い・AI運用担当者の席の事例は技術判断者)。AI の名義・一括の承認だけの事例は「確定なし」と出る。草案が無ければ `draft` は `null`。盲検の確定を行わなければ `blindConfirmation` は `"なし"`
- **確定・採点の欄を AI が埋めない**。草案は草案と書き、正解を確定した記録として書かない(CLAUDE.md の常駐の規則)

### AI の採点者の較正の記録(`judge`)

標準 第3章 3.12.13 の要求事項2〜8 の記録です。

```json
{ "identity": { "model": "<採点のモデルの固定した版。latest などの別名は不可>", "prompt": "<採点の指示の版>", "settings": "<推論の設定>" }, "readingRule": { "rule": "<どの指標がどの値に届かなければ用いないか>", "draftedBy": "<AI運用担当者>", "decidedBy": "<技術判断者>", "at": "<評価の前の日>" }, "sample": { "method": "random | stratified", "sizeRule": "<件数の決め方>", "upweighted": 0 }, "raters": [ { "name": "<人の採点者>", "at": "" } ], "arms": { "<比べるモデル>": { "model": "", "table": { "<人の判定×AI の判定>": 0 }, "indicator": { "name": "kappa など", "value": 0.0 }, "interval": "", "simple": 0.0 } }, "swapChanges": null, "lengthControl": "なし", "reached": true }
```

- 比べる双方(現行と候補)の `arms` を分けて書く。偶然の一致を除く指標(`indicator`)の無い記録は「未測定」と出る。未測定で導入するときは `unmeasuredAcceptance` に層1 の権限者の受容を書く。未測定かつ比べるモデルと同じ版で採点した差分は、受容があっても導入の根拠に数えない
- 一致の読み方を回帰評価の日より後に定めた記録は、統制を緩める向きの変更として出る

## 検出の層に数える条件2〜5 の確認(附属書H H.4)

AI の確認を検出の層(保証の開示の項目6 の AI の層)に数えるには、条件2〜5(入力の分離、検証側の指示の保護、合否条件に入れない、指摘の内容と採否の記録)の確認の記録が要ります。置き場は適合性確認と同じ `seats[].qualification.conditions` です。確認の記録だけを足すときは、適合性確認の記録を書き換えずに次の形で出します。

```json
{ "kind": "performer", "summary": "条件2〜5 の確認(四半期の棚卸し)", "seats": { "dev-verifier": { "qualification": { "conditions": { "checkedAt": "2026-10-01", "checkedBy": "<AI維持管理者の席の責任者>", "approvedBy": "<当該の席の責任者>" } } } } }
```

- 記録が無い、確認した者・承認した者の席が違う、確認日が判定の日の92日前より古い席がある AI の層は(標準は「四半期の棚卸し」と定める。附属書H H.4。92日はこのテンプレートの実装の値)、出荷の集約が「条件未確認」と出し、検出の層に数えない
- 機械が見るのは記録の有無・日付・記名の席までである。中身(文脈が渡っていないこと、記録の内容)は AI維持管理者が人として確かめる
