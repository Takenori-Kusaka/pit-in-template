# 種別 headcount: 人数の境界の通過

標準の番号: 2。境界は3名未満と3名以上、10名。主に変わるもの: `answers.q-team-size`、`people[]`。キーの一覧: `../reference/input.md`

```json
{
  "kind": "headcount",
  "date": "2026-10-01",
  "summary": "3人目が加わり、独立レビュアを置けるようになった",
  "answers": { "q-team-size": "size-3-9" },
  "people": [
    { "id": "p1", "name": "<氏名>", "accounts": ["<アカウント>"] },
    { "id": "p2", "name": "<氏名>", "accounts": ["<アカウント>"] },
    { "id": "p3", "name": "<氏名>", "accounts": ["<アカウント>"] }
  ],
  "seats": { "independent-reviewer": { "accountable": "<氏名>" } },
  "decidedBy": "<D-0 表1「体制と運用形態」の決定者の氏名>",
  "reason": "<任命の理由>"
}
```

## 手順の要点

- 回答の文言は `scripts/vendor/tailoring-kb.json` の `questions` のものに限る(知識ベースに無い値は拒否)
- 名簿の体制内の人数は、チーム規模の回答の範囲に収める(1〜2名 / 3〜9名 / 10名以上)。食い違うと拒否される
- 席を新たに埋めるのは任免の決定(`accountable.md`)。決定者の記名と理由を要する
- 人数の境界の通過は即時通知の対象(通知する者は文脈オーナー。`notice.md`)

## 増えたとき

- 3名以上になると、3名未満の例外(出荷判定者の兼務など)が失効する。差分の「失効するもの」に出る
- **3名以上では、兼務禁止の組(開発者 × 独立レビュア、開発者 × 出荷判定者、出荷判定者 × 事業決裁者、AI維持管理者 × AI運用担当者。10名以上では価値責任者 × 技術判断者)を同じ人に記入すると、記名があっても拒否される**
- 独立レビュー(G-6)が適用になると、ブランチ保護(ルールセット)が `checks-only` から `team` / `regulated` へ替わる。適用は人が行う(残作業に出る)
- **1人 → 2人になったときは、席を書き換えるだけでは足りない**。回答 `q-external-reviewer` が「確認者なし(`reviewer-no`)」のままだと、G-6 は未達のまま残る。作成を指示していない側の人が確認できるなら、`answers` で `reviewer-yes` へ改め、独立レビュアの席の責任者を相手にする。回答が `reviewer-no` のまま独立レビュアの席へ開発者と別の人を記入すると、矛盾として拒否される

## 減ったとき

- **人が実際に減った結果として生じた未達・逸脱は「発生」**。記名を待たず即時に反映する。旧い構成のまま止めない
- 誰も離脱していないのに回答を「確認者なし」へ変える、確認できる人が残っているのに独立レビューを置かない、は**緩める向きの決定**(記名と理由)。見分け方の表: `../reference/direction.md`
- 安全重要度 CL1 以上・規制業の案件で3名を割ると、拒否されずに `shipBlocked`(出荷できない状態)が立つ(`../reference/dry-run.md`)
- 離脱していない人を名簿から外して、未達・逸脱を「発生」に見せない
