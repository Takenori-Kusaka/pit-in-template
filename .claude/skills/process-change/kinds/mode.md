# 種別 mode: 運用形態の変更、委任の範囲の変更

標準の番号: 3。主に変わるもの: `seats[].mode`、`delegation`。起票は対象の席の責任者が責任を持つ。キーの一覧: `../reference/input.md`

- 運用形態は**上限の宣言**(`human` / `collab` / `delegated`)。変更ごとのリスク区分の判定が下げる。運用形態の変更は即時通知の対象(`notice.md`)
- 出荷判定者・事業決裁者・AI維持管理者・AI運用担当者の席、CL1 以上・規制業の案件は委任にできない。拒否の文に、その席で宣言できる上限が出る

## 委任の範囲

委任の規則は、観測できる属性で登録します。

```json
"delegation": {
  "changeTypes": [{
    "id": "表示文言", "registeredBy": "<氏名>", "registeredAt": "2026-10-01",
    "basis": { "detection": { "rejectionRate": "<差し戻し率の算出の所在>", "reworkRate": "<手戻り率の算出の所在>" }, "rollback": "<取り消しを実行した実績の所在>", "tests": "<既存のテストで検出できることの根拠>", "enforcement": { "selfCorrection": "<自己修正のループの停止条件を強制する手段の所在。使わなければ 該当なし(理由)>", "aiReviewRound": "<AI の確認側と作成側の往復の停止条件を強制する手段の所在。使わなければ 該当なし(理由)>" } }
  }],
  "protectedPaths": ["src/core/**"],
  "rules": [
    { "id": "DR-001", "seat": "dev-verifier", "changeType": "表示文言", "paths": ["src/i18n/**"], "excludePaths": [], "decidedBy": "<氏名>", "decidedAt": "2026-10-01", "reason": "<理由>" }
  ]
}
```

- `changeTypes` は、標準変更カタログ(標準 第3章 3.7.4)に登録した変更種別。規則の `changeType` は、この一覧にあるものだけを受け付ける
- **登録の根拠(`basis`)の4点が無い種別は登録できない**(標準 第5章 5.5.4)。機械が確かめるのは記入の有無だけ。**根拠を利用者から受け取らずに、エージェントが書かない**
- 登録の根拠には、4点目として、実行の単位ごとの強制の手段の所在(または「該当なし」と理由)を書く。例: 「自己修正は `self-heal.mjs start` を呼んだ単位だけが停止条件に掛かる。ロックの外の反復は、採用者の CI の `<検査名>` が止める」。このテンプレートは、4点目の記入の有無を確かめない。強制するのは `start` を呼んだ単位だけである(標準 第3章 3.12.10 要求事項5)
- 登録した者(`registeredBy`)は、D-0 表1「標準変更カタログへの登録」の決定者(`governance.catalogRegistrar`)。標準は、リリース判定会(B-4)を置く体制では B-4、置かない体制では決定の権限を持つ者(人)と定める(第5章 5.5.4)。このテンプレートの既定は人数で分ける(1〜2名では「体制と運用形態」の決定者、3名以上では B-4)。B-4 の構成員であるかは機械では確かめない。**B-4 を置かない体制では、`governance` で `catalogRegistrar` を決定者の席へ改める**(変更前の決定者の記名と理由)
- `protectedPaths` は確約範囲とコア指定のパス。触れる変更は委任の対象にならない(条件5)。**キーが無いあいだは、どの変更も委任に該当しない**。該当するパスが無い案件は `[]` を宣言する。最初の宣言と、パスを外す変更は緩める向きの決定。どのパスが当たるかを、エージェントが決めない
- `paths` に、全域(`**`)、ルート直下の全体(`*`)、先頭の階層を特定しない指定(`**/*.md`)は書けない
- 強制層・構成の正本・判定の記録(`.claude/`、`.github/`、`scripts/gate/`、`process.config.json`、`docs/gates/` など)は、規則に当たっても委任の範囲へ入らない。こうしたパスを指す規則は登録できるが `[警告]` が出る
- `decidedBy` は、対象の席の責任者、または「体制と運用形態」の決定者。責任者が交代したら、新しい責任者が記名し直すまで席は協働へ下がる(`accountable.md` の `takeover`)
- 規則の検査は、席を委任にするかどうかに依らず、書き込む前に行われる
- G-6 の判定の時点が事後へ移るのは、**独立レビュアの席が委任で、その席の規則に該当し、PR のリスク区分が R3 と記録された変更だけ**。開発者の席の規則だけでは、G-6 の承認は免除されない

## 席ごとの上限の表に照らす(標準 第5章 5.5.6。IMPL-0599)

委任の規則を登録する前に、決定者が、規則の範囲が対象の席の「委任できる範囲」の列の内側かを確かめます。機械が確かめるのは、席の運用形態の上限(事業決裁者・AI運用担当者は人確定、出荷判定者・AI維持管理者は協働まで。IMPL-0691)だけです。列の中身は自由な文であり、機械は読みません。

1. 対象の席の行を、標準 第5章 5.5.6 の表から引く。委任できる範囲が「なし」の席には、規則を登録しない
2. 規則の `paths` と `changeType` が、その席の列の文の内側にあるかを、決定者が読んで確かめる。例: 開発者(検証)の席は「登録した変更種別の実装と挙動検証」、独立レビュア席は「判定の時点が事後へ移る」まで
3. 表の外の割当て(列に無い範囲の委任、協働の列に無い起案)が要るときは、範囲の決定者が、その割当てと理由を判断記録(ADR)に残す。表の列を拡げる条項は足さない。表の割当ては暫定(EV-0050)であり、委任の条件に反する変更が出た席は、その変更種別を範囲から外す
4. 列の内側かどうかは機械で確かめない。確かめる者は、委任の範囲を決定した者(D-0 表1)と、プロセス内部監査

## 導入の置き場を委任から外す(標準 第5章 5.5.4 の委任の対象の属性。IMPL-1032)

委任の対象にできる変更は、新たな外部呼び出し・データ構造・権限を導入しないものに限ります。機械は、依存の目印のファイル(マニフェスト・ロックファイル)の追加の行だけを確かめます(IMPL-0840)。マイグレーションや権限の設定のように、置き場が採用者の構成ごとに違うものは、機械が一覧を持ちません。置き場を、委任の規則の `excludePaths` に書きます。

- (a) **`excludePaths` は規則ごとに持つ。すべての委任の規則に置く**。規則を足すときも置く。置いていない規則の範囲では、その置き場の変更が委任に当たりうる
- (b) `excludePaths` は、**委任から外す**ものであり、禁止ではない。外した変更は、委任の経路を通らず、人の判定(協働)へ戻る
- (c) **置き場が変わったら登録を改める**。マイグレーションの置き場・権限の設定の置き場を移したときは、規則の `excludePaths` を同じ変化点で書き換える。範囲の縮小は厳しくする向きで、即時に適用される
- 例は書かない。置き場は採用者の構成ごとに違い、一覧は推測になる。実在する置き場を、決定者が自分の構成から読んで書く
- 機械が確かめるのは、置き場に書いた分だけである。書いていない規則・置き場の外の導入は、確かめない。確かめる者は、登録する者と、事後の抜き取り

## 引き上げと登録の判断点(標準 第5章 5.4.5・5.5.4、第7章 7.7.8)

運用形態を引き上げる入力と、変更種別を登録する入力は、拡大の判断点です。入力を作る前に、次を利用者に確かめます。

- 引き上げの根拠は、自組織の実測値にする。外部の性能指標(ベンチマークのスコア)だけを根拠にしない。理由(`reason`)に外部の指標しか書けないときは、入力を作らない
- 判断点で、企画書で選んだ下流の指標を、比較の基準値と比べた結果を理由に書く。指標の値も基準値も、利用者から受け取る。エージェントが推測で書かない。基準値の置き方が「見積り」「基準値なし」のときは、改善を主張する理由を書かない
- 緊急のセキュリティ修正は、変更種別として登録しない。標準 第7章 7.4 のファストトラックで扱う。急ぐ変更を登録した種別に含めない。機械は登録した種別の内容を確かめないため、利用者の入力で確かめる
- 変更種別の登録(`delegation.changeTypes` を足す入力)は、5.4.5 の引き上げの判定を兼ねる(標準 第5章 5.4.5・5.5.4)。登録の判定者(`governance.catalogRegistrar`)に、当該の種別について条件2〜7 のそれぞれを照らした結果を受け取り、変化点の入力の `reason` に、条件ごとに照らした結果を書く(書式は例示にとどめる。例: 「条件2: …/条件3: …」)。条件1(3か月)は登録の経路では課さない。条件2〜4 は判定の時点までに記録がある期間で照らし、期間の下限は課さない
- 条件5 は、D-0 の「AI を用いない実施の記録」(節12)に、登録する種別の名を対象領域とする数える行が、登録の日以前にあること。行が無いときは、先に人が行を追記してから登録する。**照らした結果も行も、利用者から受け取らずにエージェントが書かない**。機械は条件2〜7 の照らしを確かめない(manual。登録の判定の記録に照らしが残るかは、標準の内部監査が確かめる)

## 条件に反する変更が出たとき(標準 第8章「事後監査の手続」)

- 委任の条件に反する変更が見つかったら、その変更を差し戻さず、切替の適用範囲を狭める入力を作る(範囲の縮小と規則の削除は、厳しくする向きで即時に適用される)
- 条件に反する変更の件数を期ごとに数える記録は、準拠テンプレートに無い。利用者から期ごとの件数を受け取り、2期連続で出ていれば、席の運用形態を協働へ戻す入力(`seats.<席>.mode` を `collab`)を作る。切替を停止してリリース前の判定へ戻す。エージェントが件数を推測しない

## 規則の追加・拡大は、2つめの記名で有効になる

- **委任の規則の追加と範囲の拡大は、統制の弱化**。委任する決定(席の責任者の `decidedBy`)とは別に、AI維持管理者の席の責任者が承認する(`ruleApprovedBy`。経路は `state:needs-platform`)。範囲の縮小と規則の削除には承認を要しない
- **決定した者と規則の承認者が同一人物の変化点は、人数に依らず記録つきで受け付けられる**(ADR-0054。どの席で判断したかを記録する)。ただし第5章 5.5.7 の2つの記名が1人に集まり、1つの変化点で1人が委任を有効にできる。`decidedBy`(保持していた宣言・規則の決定者を含む)と `ruleApprovedBy` が同一人物なら `[注意]` が出て、D-0 節13 に「**決定した者と同一人物**」、`/pit` と出荷の集約にも出る。別の自然人で行うには、対象の席の責任者(開発者 A)が `decidedBy` に記名し、AI維持管理者 B が承認する(3名の例: 独立レビュア・事業決裁者・AI維持管理者 B)。確約範囲(`protectedPaths`)の最初の宣言は事業決裁者の決定なので、先に別の変化点で宣言しておく。**同一人物の承認を認めない組織は、層1 の錠(次項)で委任の登録そのものを止める**
- **層1(`docs/quality-assurance-policy.md`)の項目4「AI の利用の拡大」の受容できる水準が `認めない` で始まる組織では、委任の登録は拒否される**(構成の錠)。席を委任にする・規則と変更種別を足す・規則を承認する入力が当たる。委任を解く入力(協働へ戻す、規則を削除する)は錠のもとでも受け付ける(厳しくする向き)。委任を認めるには、層1 の記名者が水準を改めて版を上げる(体制の変化点)。構成の側だけで錠を外せない。語「認めない」を含むが欄の先頭でない層1 は錠にならない(`/pit` と出荷の集約が「人が確かめる」と出す)
- 席の責任者が委任を宣言し、規則が承認待ちのあいだは、宣言と決定者が保持され(`[宣言を保持]`)、協働として動く。`ruleApprovedBy` だけを書いた変化点で委任が有効になる(`[委任を有効化]`)。**宣言し直す必要はない**。宣言の後で担い手の識別が変わった場合と、宣言した者が決定者でなくなった場合は、宣言は取り下げられる(`[宣言の失効]`)
- 宣言が無いまま規則の承認だけが入った場合は、協働のまま(`[協働のまま]`)
- **未承認の規則を足しても、承認済みの規則による委任は協働へ落ちない**。承認待ちになるのは足した規則だけ(`[承認待ち]`)
- 承認済みの規則の範囲を広げたときは、承認済みの範囲が有効なまま残り、広げた部分だけが承認待ちになる(`[拡大は承認待ち]`。構成では `pendingChange`)。承認が入った変化点で反映される(`[拡大を反映]`)。承認だけの変化点でも、向きは「緩める」として記録される
- **AI維持管理者の席の責任者が交代したとき、前任者が承認した規則は承認待ちへ戻る**(`[承認待ちへ戻る]`)。規則を消して足し直す必要はない

```json
{ "kind": "mode", "summary": "新しい AI維持管理者が規則を承認し直す", "ruleApprovedBy": "<新しい AI維持管理者の氏名>" }
```

## 残作業

- 規則の変更を AI維持管理者へ引き渡す(`state:needs-platform`)。**差分が変更の主張と一致するかの確認までに留め、許容してよいかを判断しない**
- 委任の変更のマージの経路(`../reference/apply.md`)
- 委任に当たるかは機械が判定する。エージェントが自分で判定しない
