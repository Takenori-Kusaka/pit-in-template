# 種別 mode: 運用形態の変更、委任の範囲の変更

標準の番号: 3。主に変わるもの: `seats[].mode`、`delegation`。起票は対象の席の責任者が責任を持つ。キーの一覧: `../reference/input.md`

- 運用形態は**上限の宣言**(`human` / `collab` / `delegated`)。変更ごとのリスク区分の判定が下げる。運用形態の変更は即時通知の対象(`notice.md`)
- 出荷判定者・事業決裁者・AI維持管理者・AI運用担当者の席、CL1 以上・規制業の案件は委任にできない。拒否の文に、その席で宣言できる上限が出る

## 委任の範囲

委任の規則は、観測できる属性で登録します。

```json
"delegation": {
  "changeTypes": [{
    "id": "表示文言", "registeredBy": "<氏名>", "registeredAt": "2026-10-01",
    "basis": { "detection": "<第5章 5.4.6 の検知条件を何で計測するか>", "rollback": "<取り消しを実行した実績の所在>", "tests": "<既存のテストで検出できることの根拠>" }
  }],
  "protectedPaths": ["src/core/**"],
  "rules": [
    { "id": "DR-001", "seat": "dev-verifier", "changeType": "表示文言", "paths": ["src/i18n/**"], "excludePaths": [], "decidedBy": "<氏名>", "decidedAt": "2026-10-01", "reason": "<理由>" }
  ]
}
```

- `changeTypes` は、標準変更カタログ(標準 第3章 3.7.4)に登録した変更種別。規則の `changeType` は、この一覧にあるものだけを受け付ける
- **登録の根拠(`basis`)の3点が無い種別は登録できない**(標準 第5章 5.5.4)。機械が確かめるのは記入の有無だけ。**根拠を利用者から受け取らずに、エージェントが書かない**
- 登録した者(`registeredBy`)は、D-0 表1「標準変更カタログへの登録」の決定者(`governance.catalogRegistrar`)。既定は、1〜2名では「体制と運用形態」の決定者、3名以上ではリリース判定会(B-4)。B-4 の構成員であるかは機械では確かめない。**B-4 を置かない体制では、`governance` で `catalogRegistrar` を決定者の席へ改める**(変更前の決定者の記名と理由)
- `protectedPaths` は確約範囲とコア指定のパス。触れる変更は委任の対象にならない(条件5)。**キーが無いあいだは、どの変更も委任に該当しない**。該当するパスが無い案件は `[]` を宣言する。最初の宣言と、パスを外す変更は緩める向きの決定。どのパスが当たるかを、エージェントが決めない
- `paths` に、全域(`**`)、ルート直下の全体(`*`)、先頭の階層を特定しない指定(`**/*.md`)は書けない
- 強制層・構成の正本・判定の記録(`.claude/`、`.github/`、`scripts/gate/`、`process.config.json`、`docs/gates/` など)は、規則に当たっても委任の範囲へ入らない。こうしたパスを指す規則は登録できるが `[警告]` が出る
- `decidedBy` は、対象の席の責任者、または「体制と運用形態」の決定者。責任者が交代したら、新しい責任者が記名し直すまで席は協働へ下がる(`accountable.md` の `takeover`)
- 規則の検査は、席を委任にするかどうかに依らず、書き込む前に行われる
- G-6 の判定の時点が事後へ移るのは、**独立レビュアの席が委任で、その席の規則に該当し、PR のリスク区分が R3 と記録された変更だけ**。開発者の席の規則だけでは、G-6 の承認は免除されない

## 規則の追加・拡大は、2つめの記名で有効になる

- **委任の規則の追加と範囲の拡大は、統制の弱化**。委任する決定(席の責任者の `decidedBy`)とは別に、AI維持管理者の席の責任者が承認する(`ruleApprovedBy`。経路は `state:needs-platform`)。席の責任者と同一人物でも、どの席で判断したかを記録に残す。範囲の縮小と規則の削除には承認を要しない
- 席の責任者が委任を宣言し、規則が承認待ちのあいだは、宣言と決定者が保持され(`[宣言を保持]`)、協働として動く。`ruleApprovedBy` だけを書いた変化点で委任が有効になる(`[委任を有効化]`)。**宣言し直す必要はない**。宣言の後で担い手の識別が変わった場合と、宣言した者が決定者でなくなった場合は、宣言は取り下げられる(`[宣言の失効]`)
- 宣言が無いまま規則の承認だけが入った場合は、協働のまま(`[協働のまま]`)
- **未承認の規則を足しても、承認済みの規則による委任は協働へ落ちない**。承認待ちになるのは足した規則だけ(`[承認待ち]`)
- 承認済みの規則の範囲を広げたときは、承認済みの範囲が有効なまま残り、広げた部分だけが承認待ちになる(`[拡大は承認待ち]`。構成では `pendingChange`)。承認が入った変化点で反映される(`[拡大を反映]`)。承認だけの変化点でも、向きは「緩める」として記録される
- **AI維持管理者の席の責任者が交代したとき、前任者が承認した規則は承認待ちへ戻る**(`[承認待ちへ戻る]`)。規則を消して足し直す必要はない

```json
{ "kind": "mode", "summary": "新しい AI維持管理者が規則を承認し直す", "ruleApprovedBy": "<新しい AI維持管理者の氏名>" }
```

## 残作業

- 規則の変更を AI維持管理者へ引き渡す(`state:needs-platform`)。**差分が変更の主張と一致するかの確認までに留め、許容してよいかを判断しない**
- 委任の変更のマージの経路(`../reference/apply.md`)
- 委任に当たるかは機械が判定する。エージェントが自分で判定しない
