# 構成を書き換えるのは、このスキルだけ

`/process-change` の入口の詳細です。

## 要約値の連鎖

- 変化点の記録(`changeLog[]`)の各記録は、適用後の構成の要約値(`stateHash`)と、直前の記録の要約値(`prevHash`)を持つ
- 手で書き換えた構成は、最後の記録の要約値と一致しなくなり、契約検査(`verify-gate-contract`)が失敗する。記録の書き換え・切り詰め・差し替えも、連鎖の不一致として検出される
- 手で書き換えた構成に対して、回答ファイルからの再生成(`--answers process.config.json`)と、次の変化点は、どちらも拒否される。**手での編集を追認する経路は無い**。編集を戻してから、変えたい内容を変化点として反映する
- PR では、契約検査が基底ブランチの構成と比べる(`--base <ref>`、または環境変数 `GITHUB_BASE_REF`)。構成が変わっているのに `changeLog[]` の追記が無い変更と、基底の記録が先頭部分として保たれていない変更は失敗する
- 構成の閾値(`ci`・`task`・`guard`)を、製品のコードと同じ PR で変えると、G-5 の `pr-rules` が失敗する(禁止事項6)。種別 `settings` の変化点は、製品のコードと別の PR にする

## 限界

要約値ごと書き換える改ざんは、ローカルの検査だけでは検出できません。過去の記録の書き換えは、基底ブランチとの比較で止まります。**構成を手で書き換えたうえで、要約値を計算し直した記録を追記する偽造は、基底ブランチとの比較も通ります**。要約値は鍵を持たないため、記録が `/process-change` を経たことも、記名した本人が決定したことも証明しません。これを止めるのは、構成が強制層であること(変更は AI維持管理者の承認を要する)と、人による PR の確認です。

## D-0 体制図との分担

同じ内容を、D-0 体制図と構成へ二重に書かせません。**D-0 体制図のうち、構成から導ける欄(節1 の責任者の表と名簿、節3 の2行の決定者、節12 の担い手と運用形態・委任の範囲、節13 の改訂履歴)と、frontmatter の `version` は、このスキルが書きます**。人が書くのは、決定の理由と記名(入力の `reason` と `decidedBy`)だけです。D-0 が未作成のときは、`templates/00-d0-governance.md` を `docs/D-0-governance.md` へ写し、frontmatter と、生成区間でない節(節2〜節11)を人が記入します。

## 旧い構成からの移行

変化点の記録に要約値を持たない構成(このテンプレートの更新より前に生成した構成)は、契約検査が失敗します。**最初の `/process-change` で、要約値の連鎖が始まります**。

1. 変える内容が無ければ、空の `settings` を適用する(`{ "kind": "settings", "summary": "要約値の連鎖を始める" }`)。出力に `[連鎖の開始]` が出る
2. 連鎖より前の構成と記録は、書き換えの有無を検証できない。その旨が、連鎖の起点の記録(`chainStart`)として残る。以後は、連鎖より前の記録の書き換えも検出される
3. D-0 体制図へ、生成区間の目印(`templates/00-d0-governance.md` の節1・節12・節13)と、節3 の2行(「体制と運用形態」「標準変更カタログへの登録」)を写し、`node scripts/init/generate-profile.mjs --answers process.config.json` で区間を書き込む。連鎖が始まった後は、目印の無い体制図を D-0 の検査が失敗させる
4. 既存の委任の規則がある場合は、規則の変更種別を `delegation.changeTypes` へ登録する(種別 `mode`)。登録が無いあいだ、その規則では委任は有効にならない
5. 名簿へ、リポジトリ上のアカウント(`accounts`)を記入する
6. 名簿(`people[]`)が未記入の構成は、現在の体制の名簿を先に記入する。人が減ったかどうかは、名簿の変化から確かめる。名簿が無いあいだは、人の離脱を「発生」として扱えず、緩める向きの決定も受け付けられない
