# 企画書(事業意図)

`docs/project-brief.md` として置きます。企画承認(G-1)の判定対象です。

**前提条件**: D-0(体制図)が承認済みであること。未承認では審議を開始できません。

企画は6つの観点で評価します。**下の並びは書く順序です**。財務を最初に置きません。

## 戦略整合(観点1)

| 項目 | 記載 |
| --- | --- |
| 対応する戦略目標 | 「成長」等の一般語は不可。組織が定めた目標を識別できる形で書く |
| 対応が成立しなくなる条件 | どの前提が変われば、この案件が戦略目標へ寄与しなくなるか |

## 自社が勝てる理由(観点2)

自社の何の資産・能力が、他社にはなく、この案件の成否を左右するか。**「知見がある」「実績がある」は不可**。何の知見・何の実績かを書きます。

| 項目 | 内容 |
| --- | --- |
| 現在の代替手段 | **「ない」と書かない**。手作業でも代替手段である |
| その代替手段が使われ続ける条件 | 移行の費用・ライセンス・調達要件など、乗り換えが起きない側の事情 |

## 品質の約束と保証範囲(層2 / G-1 基準2)

組織が品質を保証すると主張するための層2 です。事業決裁者が G-1 で、層1(`docs/quality-assurance-policy.md`。テンプレ11)に照らして承認します。**案件ごとの論証は書きません**(論証は標準 附属書H の標準の論証を使う)。

| 項目 | 記載 |
| --- | --- |
| 想定する利用者・目的・利用状況・制約 | <誰が、何のために、どう使うか> |
| 壊してはならない品質条件 | <下の「壊してはならない品質条件(識別子)」の表による、と書く。条件が無い案件は理由を書く> |
| 保証範囲と範囲外 | <層1 の項目1 に照らして、この案件で組織が保証する範囲と、しない範囲。保証しない案件は「組織として保証しない」と書く。層1 が無い組織は「層1 なし」と書く> |
| この案件に掛かる外枠 | <層1 の項目3 のうち、この案件に適用される法令・契約・規格> |

- 4欄の空欄は `check-g1` が検出する。記述の内容は機械が判定しない
- 「組織として保証しない」「層1 なし」と書いた案件も進めてよい。その案件の変更は保証の主張の成立条件2(または1)を満たさず、出荷は「品質保証の対象外」と出る(出荷は止まらない)
- 保証範囲は出荷の時点で決めない。確かめられた範囲が後から約束になるため

### 壊してはならない品質条件(識別子)

業務規則、権限、データ、安全、法令、性能のうち該当するものを、**条件ごとに識別子 `QC-NN` を振り**、観測可能な事象で書きます。G-2 の受入基準とテストから、識別子で参照させます(受入基準の行・テストの名前かコメントに `QC-01` と書く)。

| 識別子 | 条件(観測可能な事象) | 区分 |
| --- | --- | --- |
| QC-01 | <例: 権限の無い利用者は、他の利用者の招待を取り消せない> | <権限> |

- 識別子の欠落と重複は `check-g1` が検出する。出荷判定の証跡の集約が、受入基準とテストからの参照を突合する(標準 第4章 G-7「壊してはならない品質条件の突合」)
- 受入基準とテストの両方から参照される条件の件数は保証の開示の項目4、テストから参照されない条件・どこからも参照されない条件は項目5(残存リスク)へ自動で載る。**識別子を持たない条件は記載の欠落**
- 参照の妥当性(参照したテストが条件を確かめているか)は機械では判定しない。G-6 の独立レビュアが確かめる
