# F-001 <機能の名前>

`specs/F-001/spec.md` として置きます。

## 背景

誰の、どんな問題を解くのか。1〜3段落。

## 受入基準

EARS 記法で書きます。**曖昧語は使えません**(標準 第4章 G-2 基準2)。検出語の正本は標準 第4章 G-2 の表です。`node scripts/gate/spec-lint.mjs --terms` で一覧を出せます。CI の `spec-lint` が、この節の中の検出語を検出します。

| # | 型 | 受入基準 |
| --- | --- | --- |
| 1 | イベント駆動 | 招待の有効期限を過ぎた場合、システムは一覧に「失効」と表示しなければならない |
| 2 | 望ましくない事象 | 失効した招待に対して取り消しを実行した場合、システムは HTTP 409 を返さなければならない |
| 3 | ユビキタス | システムは招待トークンをログへ出力してはならない |

各基準には、**違反すると失敗するテストが1つ以上**必要です。

`#` の列が受入基準の識別子です。**識別子は機能の中で一意**とし、確定の後に振り直しません。実装計画の「対応する受入基準」とテスト(`F-NNN/AC-N`)は、この識別子で受入基準を引きます(標準 第4章 G-4 基準6)。G-4 では、どのタスクにも現れない受入基準の一覧を機械が出し、判定者が見ます(`node scripts/gate/spec-lint.mjs --gate G-4 specs/F-NNN`)。

## スコープ外

書かれていない事項は、実装されるか否かが不定になります。やらないことを明記します。

- 招待の再発行(F-013 で扱う)

## 前提

この機能が成り立つと、確かめないままみなして置くこと。崩れたら受入基準も変わります。各行を案件層のコンテキスト(`context/projects/`)へ登録し、その ID を書きます(標準 第4章 G-2 基準3)。

| # | 前提 | 案件層の ID | 崩れたときの影響 |
| --- | --- | --- | --- |
| 1 | 招待の有効期限は、運用中に変えない | <登録済みの ID> | 基準1が実装できない |

**この欄に書いたものは、すべて確かめていないものとして読みます**。確かめた事実(コード・スキーマ・問い合わせで確かめたこと)は、この欄に書かず、背景や受入基準などの本文に書きます。確かめていない推測を本文に事実として書くと、登録されていない暗黙の前提として G-2 基準3 で差し戻されます。「確かめた / 想定」を区別する列は置きません(標準 第4章 G-2「前提の欄(基準3)」)。

## 未確定事項

曖昧なまま残っている点を書きます。**1件でも残っていると、G-2・G-4 の判定を始めません**(標準 第4章 G-2・G-4 の前提条件。`node scripts/gate/spec-lint.mjs --gate G-2 specs/F-NNN` が数えます)。空にできる欄ではなく、**閉じたら消す欄**です。閉じ方は次の3つです。

- 決めて、受入基準・スコープ外などの本文に書く
- 確かめて、本文に書く
- 確かめないまま前提として引き受け、前提の表へ移す(案件層の ID と崩れたときの影響を書く)。引き受けるのは G-2 の判定者(S0 では G-4 の判定者)で、判定記録の「引き受けた前提」に ID を残す

責任者と期限を付けて残したまま通すことはしません。残したまま進めるなら、例外承認(標準 第7章 7.3)によります。

- [NEEDS CLARIFICATION] <確定していない点>
