# ゲート判定記録

`docs/gates/<ゲート>-<対象>-<日付>.md` として置きます。例: `docs/gates/g4-F-012-2026-08-08.md`

## 判定の基本ルール

1. **記録をもって成立する（必須条件）**:
   ゲート判定は、**この判定記録ファイルを作成しレポジトリにコミットした（証跡を残した）時点で初めて公式に成立（通過/差し戻し）**します。
   - GitHub Issue や PR の操作（クローズなど）は事務手続きであり、判定の成立要件ではありません。記録が未作成の期間は「未判定（保留）」扱いとなります。
2. **単独責任（説明責任）**:
   判定は単一の責任者（判定者）が非同期で行います。合議制（会議で全員のハンコを集める）にして責任を霧散させないでください。
3. **判定に持ち込んではならないもの**:
   - **次工程の材料の未完成**: 例として、「Devのテストコードが未作成だから」という理由で G-4（機能仕様承認）を差し戻してはなりません。G-4 の目的は「仕様とタスク分解の承認」であり、実装が完了していることは要求されません。
   - **当該ゲートの判定基準に無関係な項目**: 属人的な好みや、該当ゲートのチェックリストにない項目を差し戻し理由にしないでください。基準なきゲートは素通しと滞留の両方を招きます。

## 確認した項目（チェックリスト）

**対象とするゲートのチェックリストのみを残し、他のゲートの項目は削除してください。**

### 全ゲート共通の通過条件（常に必須）
- [ ] 0. 当該の工程に関係する前提の充足状態が「前提台帳（assumptions.md）」に記録されており、安全リスクアセスメントまたはADRに基づいてAC-1（リスクあり）以上のものについて受容の決裁が取られている

---

### G-1 企画承認 (Project Approval)
- [ ] 1. 開発（プロジェクト）を実施するビジネス価値や背景が明確に定義されている
- [ ] 2. ターゲットとする顧客、解決する課題、期待される効果が言語化されている
- [ ] 3. 開発体制（D-0 意思決定体制図）が定義され、役割の割り当てと兼務状況が確定している
- [ ] 4. プロセス構成（PROCESS-PROFILE.md、process.config.json）が初期化され、適用するゲートが確定している
- [ ] 5. 品質要求レベル、CIカバレッジ閾値、許容ライセンスの初期値が合意されている
- [ ] 6. 安全リスクアセスメント（該当する場合）が完了し、暫定安全区分が特定されている

### G-2 要件合意 (Requirements Agreement)
- [ ] 1. 要件が、客観的かつ機械的/客観的に検証可能な「受入基準（Acceptance Criteria）」の形式で書かれている
- [ ] 2. EARS 記法（条件 + 期待動作）に準拠して書かれている
- [ ] 3. 適切に/柔軟に/可能な限りなどの「曖昧語」がすべて排除されている（spec-lint適合）
- [ ] 4. スコープ外の事項（やらないこと）が明確に定義されている
- [ ] 5. 暗黙の前提やトレードオフが「前提台帳（assumptions.md）」および「案件層コンテキスト」に記録されている
- [ ] 6. 合意した範囲がスコープ3層（マニュアル層、プロセス・ツール層、プログラム層）へ割り当てられている

### G-3 技術設計判断 (Technical Design Decision)
- [ ] 1. 提案された技術設計・アーキテクチャが、既存のコードベースや全体方針と整合している
- [ ] 2. 設計の「可逆性（Reversibility）」が評価され、仮に誤っていた場合に撤回可能か、または不可逆な決定に対するヘッジ策が明記されている
- [ ] 3. 非機能要件（性能、セキュリティ、保守性、テスト容易性など）に対する設計上の配慮がなされている
- [ ] 4. 1つの案に固執せず、複数の選択肢（代替案）が比較検討されている
- [ ] 5. 採った選択肢と「採らなかった選択肢とその理由」が ADR（判断記録）に過不足なく記述されている

### G-4 機能仕様承認 (Functional Specification Approval)
- [ ] 1. AIエージェントが自走して実装するために、必要な仕様が1機能（F-NNN）単位で確定している
- [ ] 2. 実装計画（plan.md）において、AIエージェントへの指示（対象パスやコンテキスト）が、1回で高精度に実装できる適切なサイズ（1タスク目安100行/上限400行程度）に分解されている
- [ ] 3. すべてのタスクが、G-2 で合意したどの受入基準（AC）に対応するかが明確に紐づけられている（紐づきのないタスクがない）
- [ ] 4. 各タスクを検証するためのテスト方針（テストの種類、配置場所）が、実装に先立って定義されている
- [ ] 5. AIが勝手に書き込み範囲を広げないよう、ファイル編集の許可パス（対象パス）が最小限に絞られている

### G-6 独立レビュー (Independent Review)
- [ ] 1. 実装を指示した本人（およびAIエージェント）以外の、独立した第三者（人間）によってレビューが実施されている
- [ ] 2. 単なるコードの文字面だけでなく、ローカル環境等で「実際の挙動」が動くことを確認している
- [ ] 3. 独立レビュア自身が、レビュー対象の挙動とコードを十分に理解した上で、**自分の言葉で**1〜2文の「挙動要約」を判定記録に記入している（AI自動生成は厳禁）
- [ ] 4. コア機能の変更である場合、チーム内の理解保持者の数（コア理解保持者数）がカウントされ、技術空洞化リスクがないことが確認されている

### G-7 出荷判定 (Shipping Judgment)
- [ ] 1. 今回の出荷（リリース）対象となるすべての機能について、必要なすべてのゲート判定記録（G-1〜G-6）が `docs/gates/` に完備している
- [ ] 2. 各ゲートの判定記録に、判定者、判定日、判定結果（通過）が漏れなく記録されている
- [ ] 3. 開発プロセス中に適用されたテーラリング（省略・未達・逸脱など）について、その事実と代償措置、承認されたADR等の証跡がすべて紐付け・完備されている
- [ ] 4. 品質保証（QA）部門または開発ラインから完全に独立した品質責任者が、プロセスの適合性を単独で確認・署名している

### G-8 リリース決裁 (Release Approval)
- [ ] 1. 品質保証部門による出荷判定（G-7）が「通過」で完了している
- [ ] 2. 今回のリリースに伴うビジネスリスク、ダウンタイム、運用影響、ロールバック手順が整理され、合意されている
- [ ] 3. ユーザーへの告知、サポート体制、ビジネス側での受け入れ準備が整っている
- [ ] 4. 事業決裁者（決裁権限規程どおりの職位）が、最終的なリリース実施の判断を承認し、署名（決裁）している
