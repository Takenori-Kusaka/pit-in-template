# 欠陥の台帳

`docs/defect-ledger.md` として置きます。出荷判定(G-7)の基準2(未解決の欠陥)の入力です(標準 第4章 G-7「基準1・2 の記録」)。標準の様式番号を持ちません。欠陥管理の道具(Issue の追跡など)を使う組織は、出荷の前にこの形へ書き出します。

**台帳が無い出荷は、基準2 を確かめられないため記載の欠落**になります。既知の欠陥が無い場合も、表を空にして「既知の欠陥なし」と書いた台帳を置きます。

## 台帳

| ID | 現象 | 重大度(Sev1 / Sev2 / Sev3) | 優先度 | 状態(未解決 / 解決済み) | コア機能(はい / いいえ) | 回避策(文書の所在) | 検出の時点(出荷前 / 運用) | 発生日 | AI 起因(あり / なし / 特定できない) | 原因の変更 | 登録した変更種別 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| | | | | | | | | | | | |

- 重大度は技術側が観測可能な事実で決める(Sev1: 停止・データの破損・認証認可の破れで回避策が無い / Sev2: 文書化した回避策がある / Sev3: 業務は継続できる)。優先度は事業側が決める
- 出荷判定の証跡の集約が、事業ステージ別の欠陥トリアージ基準の区分ごとに未解決の件数を出す(S1 の Sev1 はコア機能とそれ以外に分けて数える)。**出荷の可否を機械は判定しない**。出荷判定者が基準と突合する
- 回避策は文書化されていなければ存在しないものとして扱う
- 運用で発生した Sev1・Sev2(ポストモーテムを書く障害)も、この台帳に行を足す。解決した後も行を消さない
- 検出の時点は、出荷の前のゲート・検証で見つけた欠陥を「出荷前」、出荷の後に運用で発生した事象(事後検証の対象)を「運用」と書く。空欄は「運用」として数え、その旨が `/pit` の注記に出る
- 発生日・AI 起因・原因の変更・登録した変更種別は、検出の時点が「運用」の Sev1・Sev2 の行で書く(標準 第5章 5.4.6)。AI 起因は、事後検証で特定した原因の変更に AI の関与の記録(コミットのトレーラなど)があれば「あり」、無ければ「なし」、原因を特定できなければ「特定できない」。**空欄は「特定できない」と同じく扱う**。登録した変更種別は、原因の変更が当たる種別(`delegation.changeTypes[]` の ID)を書く。空欄は、すべての登録した変更種別に当たるものとして扱う
- 委任の判定(`scripts/gate/check-delegation.mjs`)が、判定のたびにこの台帳を読む。検出の時点が「運用」(または空欄)の Sev1・Sev2 の行に当たる登録した変更種別の委任が止まる。AI 起因が「あり」の行は、事象の日より後に登録し直すまで止まる。**「特定できない」と空欄の行は、原因を特定して「あり」か「なし」へ改めるまで止まる。登録し直しでは解けない**。発生日の無い行は、前後を確かめられないため止め続ける。台帳が無い構成では、登録した変更種別の委任はすべて止まる
- 出荷の前に見つけた欠陥(検出の時点が「出荷前」)は、委任の停止に数えない。停止に数えると、検出が罰になり、重大度を低く書く誘因になる(標準 第5章 5.4.6 の停止は、事後検証の対象の事象に限る)
- この台帳と運用引き継ぎ文書(`docs/handover.md`)は委任の停止の入力である。**委任の範囲に入れない**(規則の範囲に含めても、委任の判定はこの2つに触れる変更を委任に該当させない。標準 第5章 5.4.6)

## 引き下げの点検の記録(第5章 5.4.6)

5.4.6 の第2区分の検知(差し戻し率・手戻り率)について、人が行う2つの記録をここに残します。

| 日付 | 変更種別 | 検知(差し戻し率 / 手戻り率) | 扱い(L1 で数え直し / 誤発火) | 内容 | 記録した者 |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

- 「L1 で数え直し」は、引き下げで L1 へ戻した種別について、L1 の運用での比率を数え直した結果を書く。登録し直す判定の材料になる
- 「誤発火」は、検知が発火したが、実際には自動化の偏りが生じていなかったと判断した事象を書く。判断の根拠(読んだ差し戻しの記録・変更)を内容の欄に書く。**誤発火と判断しても、停止は登録の判定まで解けない**
- 記録した者は人の氏名を書く。AI の名義を書かない
