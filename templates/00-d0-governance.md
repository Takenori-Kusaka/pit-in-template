# D-0 意思決定・エスカレーション体制図

`docs/D-0-governance.md` として置きます。**規模によらず必須**です。人数が少ないほど兼務が増え、誰が決めるかが曖昧になります。

frontmatter が埋まっていない、または `next_review` を過ぎている場合、`gate-entry` ワークフローが失敗し、企画承認(G-1)の審議を開始できません。

この様式が満たすべき条件は3点です。いずれかを欠いた体制図は、判断が必要な場面で機能しません。

| # | 条件 | 欠いた場合に起きること |
| --- | --- | --- |
| 1 | 決定の種類ごとに、決定者が1名に特定されている | 決定が下されない、または下された決定が覆る |
| 2 | 各層の権限境界が数値で書かれている | 判断のたびに上位へ確認が発生する |
| 3 | 境界を超えたときの通知先と応答期限が書かれている | 逸脱が上位へ届かないまま蓄積する |

## 1. 役割の割り当て(現任者)

同じ人が複数の役割を兼ねる場合、**そのことを明記します**。空欄や「未定」を残さないでください。

**個人名が載るのはこの表と、節13(改訂履歴)の「決定した者」だけです**。以降の表は役割名で書きます。人事異動のたびに変わるのはこの表になります。

役割(席)ごとに、結果責任を負う**責任者**を1名置きます。**責任者は記名の自然人です。AI を書いてはなりません**。席の作業を実際に行う担い手と、その運用形態は節12 にあります。

**この表は手で書きません**。責任者と人の名簿は、`/process-change` で構成(`process.config.json`)へ記入します。下の区間は構成から生成され、`/process-change` が書き換えます。同じ内容を体制図と構成へ二重に書かせないためです。構成を正とします。

人の名簿(`people[]`)には、この表に載る人と、席の責任者でない担い手(人)を記入します。**名簿へ名前を足すのは人です**。席の責任者(`seats[].accountable`)、変化点を決定した者、適合性確認の実施者と承認者は、名簿と照合されます。AI の名義(モデル名、agent、bot、AI の表記を含む名義)と、名簿に無い名義は拒否されます。外部の確認者は `external: true` として記入し、体制の人数に数えません。組織上の任命権者(前任の決定者が体制から外れたときに、決定者を任命する人。標準 第3章 3.13.3)は、`external: true` と `appointer: true` で記入します。任命権者は確認者ではなく、席の責任者にもしません。AI を示す語に当たる実在の氏名は、人が確認したうえで `nameConfirmed: true` を書いた場合に限り通り、その旨が出力に表示されます。

名簿には、リポジトリ上のアカウント(`accounts`)も記入します。出荷判定の証跡は、承認したアカウントを名簿の人へ対応づけてから、独立した人の確認に数えます。対応づかない承認は数えません。**名義の検査は語の一致によるもので、役職名や別の文字種で書いた名義は検出できません。アカウントの記載が正しいかも、機械では確かめません**。名簿は人が記入するものとし、内部監査で確かめます。

安全重要度 CL1 以上、または規制業の案件で、体制が3名を割った場合、構成は**出荷できない状態**(`shipBlocked`)になります。体制を3名以上へ戻すまで、出荷判定(G-7)の証跡の集約は失敗します。

**席の責任者の任命・交代・空いた席への後任の配置は、決定です**。節3「体制と運用形態」の決定者の記名と理由を要します(緩める向きでない交代にも要します)。人が体制から外れて席が空くことは発生であり、記名を待ちません。決定者の席の責任者を替える変更と、節3 の決定者を変える変更は、前任の決定者の記名を要します。前任者が体制から外れている場合は、組織上の任命権者の記名を要し、その旨が節13 に出ます。初期化の直後(どの席にも責任者が記入されたことがない状態)の初回の記入は、体制の人数に依らず、名簿と全席を1回の変化点で出し、その変化点で節3「体制と運用形態」の決定者の席に記入する人の記名と理由で受け付けます(標準 第3章 3.13.3)。

`check-d0` は、この区間が構成と一致することを確かめます。一致しない体制図は失敗します。

## 2. 兼務の可否

| 組み合わせ | 可否 |
| --- | --- |
| 価値責任者 × 文脈オーナー | 可 |
| 技術判断者 × 開発者 | 可 |
| 技術判断者 × AI 維持管理者 | 可 |
| 価値責任者 × 技術判断者 | 5名未満のみ可 |
| 事業決裁者 × 価値責任者 | 小規模のみ可 |
| **作成を指示した本人 × 独立レビュア(同一成果物)** | **不可**(例外なし。満たせない場合は G-6 を未達として記録する) |
| **開発ライン × 出荷判定者(同一案件)** | **不可**。ただし3名未満は下記の例外による |
| **AI 維持管理者 × AI 運用担当者** | **不可**。1〜2名の体制で成立しない場合は、逸脱として下記へ記録する(例外ではない) |
| **出荷判定者 × 事業決裁者(同一案件)** | **不可**。異議を書く者と、残存リスクを受容する者が同一になり、受容が自己完結する。1〜2名の体制で成立しない場合は、逸脱として下記へ記録し、保証の開示の項目1 へ表示する(例外ではない) |

### 出荷判定者の兼務(3名未満の例外)

`process.config.json` の `gates.g7.params.approverMode` が `value-owner-merged` の場合、この構成は兼務を前提としています。**兼務表を無視して埋めないでください**。次の4つをすべて満たす場合に限り、兼務のまま運用できます(標準 第3章 3.5.2 / ADR-0029)。

- [ ] 体制が3名未満である(3名以上になった時点で例外は失効する)
- [ ] G-7 の判定記録を必須とし、基準の各項目との突合を記録に残している
- [ ] リリース後の抜き取り確認を定常作業として置いている
- [ ] 下の表に、兼務している人と代償措置を記入している

| 兼務する役割 | 担当者 | 代償措置の実施状況 | 解消の見込み |
| --- | --- | --- | --- |
| 開発ライン × 出荷判定者 | | | |

**代償措置は独立性の回復ではありません**。判定が甘くなる可能性は残ります。記録と抜き取りが行うのは、甘さを後から検出できる状態にすることだけです。この逸脱は `process.config.json` の `deviations[]` とプロセス構成書にも表示され続けます。

### 1〜2名の体制で成立しない兼務禁止(逸脱の記録)

1〜2名の体制では、AI 維持管理者 × AI 運用担当者、出荷判定者 × 事業決裁者の兼務禁止が成立しない場合があります。**出荷判定者の兼務の例外を、この組へ広げません**。代償措置は定められていません。逸脱として次の表へ記録し、表示し続けます(標準 第3章 3.5)。3名以上の体制では、この兼務は認められません。

| 兼務する役割 | 担当者 | 解消の見込み |
| --- | --- | --- |
| AI 維持管理者 × AI 運用担当者 | | |
| 出荷判定者 × 事業決裁者 | | |

該当しない場合は「該当なし」と書きます。この逸脱も `process.config.json` の `deviations[]` とプロセス構成書に表示され続けます。

「体制と運用形態」の決定者は、統制を緩める向きの変更(人の確認を減らす、委任の範囲を広げる、ゲートを省略へ変える、ステージを前へ戻す)を決定できる者です。標準の本文が「D-0 体制図の決定の権限を持つ者」と書く場合、この行の決定者を指します。既定は事業決裁者です。

「標準変更カタログへの登録」の決定者は、委任の範囲となる変更種別を登録する者です。既定は、1〜2名の体制では「体制と運用形態」の決定者、3名以上の体制ではリリース判定会(B-4)です。**3名以上でも B-4(既存のリリース会議への対応づけを含む)を置かない体制では、登録する者を「体制と運用形態」の決定者へ改めます**(`/process-change` の `governance` で `{ "catalogRegistrar": "biz-approver" }` を、変更前の決定者の記名と理由をつけて反映します)。B-4 のままでは、機械は登録した者が名簿にいることだけを確かめます。

品質保証部門の通知先(任意): <部門の通知先。定めた場合は、すべての即時の通知をここへも送る。部門を置かない組織は「定めない」と書く>

**ほかの行は手で書きます**(例外承認・要件・受入基準の確定・出荷の可否など)。`/process-change` の種別はありません。手で書く行を記入・変更しても、frontmatter の `version` は上げません。版を上げるのは体制の変化点を反映する `/process-change` だけです(構成の `d0Version` と一致しない版は `check-d0` が失敗させます)。変更は PR で入れ、経緯は PR と履歴に残します。

**最後の2行の「決定」の欄は、構成(`process.config.json` の `governance`)から `/process-change` が書き込みます**。機械が決定者の記名を照合するときは、構成を読みます。決定者を変えるときは、`/process-change` の `governance` で、変更前の決定者の記名と理由をつけて反映します。B-4 の構成員であるかどうかは、機械では確かめません。

「市場・顧客仮説の検証の実施」の行を空にしないでください。企画書の欄は答えを書く場所ではなく、**答えを作る活動を駆動する装置**です。検証を発注する主体を体制の側が持たなければ、書き手には作文しか残りません。

- **事業決裁者・出荷判定者・AI 維持管理者・AI 運用担当者の席に、委任を書いてはならない**。事業決裁者と AI 運用担当者の席は人確定に限る
- 安全重要度 CL1 以上、または規制業の案件では、どの席にも委任を書かない
- 委任を書く席は、該当を判定する機械の規則の所在(`process.config.json` の `delegation.rules` の規則 ID)を書く。所在を書けない席は協働を上限とする
- 委任の規則には、標準変更カタログ(標準 第3章 3.7.4)に登録した変更種別と、対象のパスを書く。リポジトリの全域に当たる指定は書かない。変更種別は、構成の `delegation.changeTypes[]` に登録したものに限る。登録するのは、節3「標準変更カタログへの登録」の決定者である
- 変更種別の登録には、登録の根拠を3点書く(`basis`)。第5章 5.4.6 の検知条件を何で計測するか(`detection`)、取り消しを実行した実績の所在(`rollback`)、既存のテストで検出できることの根拠(`tests`)。**3点の記録が無い種別は登録しない**。機械が確かめるのは記入の有無だけであり、内容は登録する者が判定する(標準 第5章 5.5.4)
- 確約範囲・コア指定の内側や、強制層・構成の正本を指す規則は、登録はできるが警告が出る。判定では常に委任の範囲の外になる
- 確約範囲とコア指定のパスを、構成の `delegation.protectedPaths[]` へ宣言する。宣言したパスに触れる変更は、委任の対象にならない。宣言するまでは、どの変更も委任に該当しない。該当するパスが無い案件は、空の配列を宣言する
- 委任の規則の追加と範囲の拡大は、統制の弱化として扱う。席の責任者の決定に加えて、AI 維持管理者が規則の変更を承認する(`state:needs-platform`)。承認の記名があるまで、委任は有効にならない。同一人物が兼ねる場合も、どの席で判断したかを節13 へ記録する
- 独立レビュー(G-6)の判定の時点が事後へ移るのは、独立レビュアの席が委任で、規則に該当し、リスク区分が R3 と記録された変更に限る
- 委任の形は2つある。開発者の席の規則にだけ該当する変更は、変更ごとの検証を担い手が行い、独立レビュアが人として事前に承認する。現在のブランチ保護のままマージできる。独立レビュアの席の規則にも該当する変更(G-6 の判定の時点を事後へ移す委任)は、マージの実行が既定で無効であり、組織が有効化するまで協働として扱い、人の承認を待つ。該当は、ワークフローが既定ブランチの構成と規則で判定する(行為する AI 自身には判定させない)
- 席の責任者が委任を宣言し、規則が AI 維持管理者の承認待ちであるあいだ、宣言した意図と決定者は保持される。承認待ちのあいだは協働として動く。承認が入った変化点で、委任が有効になる(宣言し直す必要はない)
- 未承認の規則を足しても、承認済みの既存の規則による委任は協働へ落ちない。承認待ちになるのは、足した規則と、広げた規則の広げた部分だけである。**承認済みの規則の範囲を広げた場合、承認済みの範囲は有効なまま残る**
- AI 維持管理者の席の責任者が交代すると、前任者が承認した規則は承認待ちへ戻る。新しい責任者が承認し直す(規則を消して登録し直すことは要しない)。承認し直した変化点で、席の委任は戻る(席の責任者の委任の決定は変わらないため)
- 人の担い手は個人名で書かない。「責任者本人」または委譲先の役割名で書く
- AI の担い手は、モデルの版・指示資産の版・権限の組で識別する。席名やペルソナの付与は適合性確認に数えない
- 適合性確認の実施は AI 維持管理者の席の責任者、承認は当該の席の責任者が行う(標準 第3章 3.4.2)
- 適合性確認を経ていない担い手は、協働を上限とする。**担い手の識別が変わった時点で、確認の記録は失効する**
- **適合性確認を承認した席の責任者が交代した(離脱を含む)とき、承認は新しい責任者へ引き継がれない**。失効するのは承認であり、担い手の識別が変わっていなければ、確認の記録(事例と結果)は有効なまま残る。新しい責任者が記録を読んで承認し直すまで、協働を上限とする。確認の再実施は要しない。**確認を実施した者が体制から外れても、確認の記録は有効なまま残る**
- 席の責任者の交代の後、新しい責任者が委任を引き継ぐときは、適合性確認の承認し直し、その席の規則の決定の記名のし直し、委任への復帰を、新しい責任者の記名と理由で1つの変化点として出せる(`/process-change` の `takeover`)
- 担い手の識別を変えるとき、同じ変化点で出した適合性確認で委任を続けられるのは、次をすべて満たす場合に限る。記録の担い手の欄が新しい識別と一致する。確認日が旧い記録の確認日より後である。実施者が AI 維持管理者の席の責任者、承認者が当該の席の責任者である。当該の席の責任者が、新しい識別で委任を続ける決定として記名し、理由を書く(節3 の決定者の記名では足りない)。1つでも欠ければ、協働へ下がる
- AI が使えないとき(利用上限への到達、提供の停止)の扱いを、席ごとに「人へ戻す」「止める」のいずれかで書く

**委任しても、判定者は席の責任者のままです**。移るのは判定の時点です。AI の確認は検出の層であり、承認として扱いません。責任者が作成を指示した者と同一人物であれば、AI を何体に分けても独立は成立しません。

運用形態・担い手・委任の範囲を変えるときは `/process-change` を使います。`check-d0` が、この区間と構成(`process.config.json` の `seats[]`・`delegation`)の一致を確かめます。`verify-gate-contract` が、委任できない席への委任、適合性確認と責任者を欠く委任を検出して失敗させます。

- 変化点の種別は、節14「更新の契機」の1〜5 の番号で出る
- **「構成の変更なし」も1行として記録される**。記録が無い状態は、検討して変更を不要とした状態と区別できない
- 決定した者は記名の自然人とする。統制を緩める向きの変更(人の確認を減らす、委任の範囲を広げる、ゲートを省略へ変える)は、理由を併記する。**緩める向きの決定を AI が行ってはならない。AI の名義の記名を受け付けない**
- 緩める向きの決定をするのは、対象の席の責任者、または節3「体制と運用形態」の決定者(既定は事業決裁者)に限る
- **席の責任者の任免(任命、交代、空いた席への後任の配置)は、統制の向きにかかわらず決定である**。節3「体制と運用形態」の決定者の記名と理由を要する。決定者の席の責任者の交代と、節3 の決定者の変更は、前任の決定者の記名を要する。前任者が体制から外れている場合は、組織上の任命権者の記名を要し、「決定者の任命を、組織上の任命権者の記名で行った」と出る。新任の決定者が自分の任命を自分の記名で確定することはできない。向きは「任免の決定」と出る
- 離脱と後任の任命は分けて出す。離脱(席を空ける)だけの変化点は記名なしで反映される。後任の任命は、別の変化点として決定者の記名と理由をつけて出す
- 事業ステージを前へ戻す変更は、記名と理由だけでは足りない。ステージ移行ゲート(SG)の判定による。判定記録は、`docs/gates/` 配下の実在する判定記録を指す
- 発効日は、暦に実在する日付で、今日以前、かつ最後の記録の日付以降に限る。通知日は、通知の対象になった変化点の日付以降、今日以前に限る
- 版を下げる変更は受け付けない。本書が無い状態では、変化点を適用しない
- 統制を厳しくする向きの変更は、即時に適用される。委任の範囲を狭める変更を含む
- **人の離脱で成立しなくなった統制は、緩める向きの決定ではなく、未達・逸脱の発生である**。記名を待たず、即時に未達・逸脱として構成へ反映される。決定した者の欄は「決定なし(発生)」と出る
- **発生として扱うのは、人が実際に減った場合に限る**(名簿の体制内の人が減った、または席の責任者が名簿から外れた)。人が減っていないのに、回答や席の入力で独立レビューや承認数を下げる変更は、緩める向きの決定であり、記名と理由を要する
- 3名以上の体制で、兼務を禁じる2つの席(作成を指示する開発者と独立レビュア、開発ラインと出荷判定者、AI 維持管理者と AI 運用担当者。10名以上では価値責任者と技術判断者)の責任者を同じ人にする変更は、拒否される
- AI が使えない期間(提供者の障害、利用上限への到達)は、変化点に数えない。ただし期間と、その間の扱い(人へ戻した / 止めた)が、ここへ1行として記録される。一時的に別の担い手へ切り替えた場合は、その間、委任を協働へ下げる。開始だけを記録した期間は「継続中」と出る。終わったら、終了日を書いた記録を足して閉じる(開始の記録は書き換えない)
- **即時に知らせる対象**(人数の境界の通過、運用形態の変更、検出の層に数えている AI の担い手の識別の変更、承認権限の一時制限の発動、独立レビュー(G-6)が成立から未達・成立しないへ変わる変化、出荷判定者の席の責任者の交代)では、出荷判定者の席の責任者へ知らせ、通知先と通知日を記録する。出荷判定者の席の責任者の交代では、前任者にも知らせる(前任者が体制から外れていれば、節3「体制と運用形態」の決定者へ)。品質保証部門の通知先を節3 に定めていれば、すべての即時の通知をそこへも送る。知らせるのは、変化点を起票する責任を持つ者である(標準 第3章 3.13.6)
- 通知する者と通知先が同一人物である場合(例: 1人体制)は、通知の入力を求めず、「通知する者と通知先が同一」と記録する。品質保証部門の通知先を定めている場合は、そこへ送った日を記録する
- 対象の行で通知先と通知日が無い場合は「未記入」と出る。未記入の通知は、出荷判定の証跡の集約が記録の欠落として扱う。対象でない行は「対象外」と出る
- 無効になった確認には、仕掛かり中の成果物のうち、作成を指示した者と確認する者の関係が変わったものを書く(変化点の入力の `invalidatedChecks`)
- **成立済みの判定記録は書き換えない**。変化点をまたぐ未完了の判定は、新しい体制の判定者が引き継ぐ

構成の `changeLog[]` の各記録は、適用後の構成の要約値と、直前の記録の要約値を持ちます。**`process.config.json` を手で編集しないでください**。手で書き換えた構成、記録を経ない再生成、記録の書き換え・切り詰めは、契約検査(`verify-gate-contract`)が検出して失敗させます。PR では、基底ブランチの構成とも比べます。要約値ごと書き換える改ざんは、ローカルの検査だけでは検出できません。要約値を計算し直した記録を追記する偽造は、基底ブランチとの比較も通ります。構成は強制層であり、変更には AI 維持管理者の承認を要します。

## 14. 更新の契機

体制の変化点。変化点の後、最初のゲート判定より前に改訂します。

1. 責任者の増減・交代・長期の不在、兼務の変更
2. 人数の境界の通過(3名未満と3名以上、10名)
3. 担い手の運用形態の変更、委任の範囲の変更
4. AI の担い手の識別の変更(モデルの版・提供者、指示資産の恒久層、ツールと権限、実行基盤)
5. 軸B〜E の入力の変化(ステージ移行、規制への該当、委託への切替、安全重要度)

次は体制の変化点に数えません。

| 数えないもの | 扱い |
| --- | --- |
| 目的・範囲・納期・予算の変更のうち、上の1〜5 へ波及しないもの | スコープの変更とエスカレーションの手続による。納期だけの変更は変化点に数えない。起票された場合は「構成の変更なし」と節13 へ記録する |
| 短期の不在 | 節9 の代行者による |
| 版を固定したままのセッションの再起動と、並列数の変更 | 手続を課さない |
| 提供者の一時的な障害と切り替え | 標準 第3章 3.12.5 の切り替えの手続による。切り替え先が無い場合は、節12 の「AI が使えないときの扱い」による。期間とその間の扱いを節13 へ記録する。切り替えの間は、委任を協働へ下げる |

**納期を理由に統制を外す要求は、納期の変更として扱いません**。統制を緩める向きの変更として、決定した者の記名と理由を要します。

- ステージ移行ゲートの判定時
- Sev1 事象の事後レビュー時
