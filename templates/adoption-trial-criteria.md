# 導入前の検証: 合否の基準

`docs/adoption-trial/criteria.md` として置きます(標準 附属書I I.11 の要件①)。**実行の前に採用者が書き、コミットします**。導入前の検証のコマンド(`node scripts/gate/adoption-trial.mjs run`)は、このファイルがコミットされていない、記入日時がコミットより後、コミットの後に書き換えた、のいずれかの状態では実行しません。結果に合わせて基準を決めた記録と区別できないためです。

- 記入者は採用者(採用判断者、または品質保証部門)。**AI の名義を受け付けません**。AI は欄を推測で埋めません
- 基準の値を本標準は定めません。採用者が自組織の受容の水準から決めます
- 人の層の見つける者は、運用で G-6 を担う人(席に就く予定の人)です。**G-6 を2名で行う体制(構成 `review.reviewerCount` が 2)では、2名で見つけます**。見つける者の記録(`findings-human.json`)に `finders` と、指摘ごとの `by` を書きます。検出率は2名の和集合で、各人の検出数は参考値として記録に出ます。全員が注入した者と別の人であることを要します
- **実環境の統制の確認(要件⑦)は、場面集とは別の事実です**。場面集は一時の複製と模擬の `gh` で止まることを確かめます。実環境でマージを止めるブランチ保護(ルールセット)の適用、`gate-g5` が PR のレビューを読めること、`ship-evidence` が成果物を取れることは、採用者が自分のリポジトリの実環境で `node scripts/gate/adoption-trial.mjs env-check --by <氏名>` を実行して確かめ、記録(`docs/adoption-trial/env-check.json`)をコミットします。模擬の `gh` では各項目が「読めない」と出て、記録と出荷の集約に「未確認」が残ります

| 項目 | 値 |
| --- | --- |
| 適用候補 | <リポジトリと開発ラインの名前> |
| 記入日時 | YYYY-MM-DD HH:MM |
| 記入者 | <採用者の氏名(役職)> |

## 合否の基準

| 項目 | 基準 |
| --- | --- |
| 欠陥注入: 人の層の検出率の下限 | <例: 60%> |
| 欠陥注入: AI の層の扱い(下限、または「検出の層に数えない」) | <例: 検出の層に数えない> |
| 場面集: 止まるべき11場面のうち止まる数 | <例: 11> |
| 類型E: 人へ戻したときに処理できる量の下限 | <例: 1週 5件> |
| 類型F: 別の提供者での差分の許容の範囲 | <例: 基準集合の失敗の増加が 2 件以内> |
| 成立判定: 層1・D-0 の全行記入で成立条件1 が成立する | 成立 |
| 実環境の統制の確認(ルールセットの適用・PR のレビューの取得・ship-evidence の成果物の取得) | <例: 3 項目とも確認済み(採用者のリポジトリの実環境の gh で env-check を実行し、記録をコミットする)> |
